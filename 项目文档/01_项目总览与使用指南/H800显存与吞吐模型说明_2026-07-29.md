# H800 显存与吞吐模型说明

> 结论日期：2026-07-29  
> 范围：当前目录中的冻结模型、离线回放结果和 H800 数据  
> 口径：区分“离线指标最好”“配置推荐最好”和“已经统一工程封装”

## 1. 先说结论

| 任务 | 当前建议 | 一句话结论 |
|---|---|---|
| 显存预估与安全过滤 | **physical-shares** | 当前 H800 稠密文本模型上安全性最好的显存模型；同时输出中心值和保守 P95 |
| 吞吐配置排序与最终选型 | **V4b 双头模型** | 当前 H800 回放中排序最稳、最终配置后悔值最低；最新 Qwen2.5 回放里绝对误差也最低 |
| 只看旧公共留出集的吞吐绝对值 | V4 单头模型 | 在一组较早的公共留出集上 MAPE 略优于 V4b，但排序和选配置不如 V4b |
| 吞吐工程统一接口 | V5 结构化模型 | 已进入统一 `Predictor` 主线、可扩展到多卡型，但目前不是 H800 离线指标冠军 |

因此，按当前证据，H800 的推荐组合是：

```text
候选训练配置
    ↓
physical-shares 预测显存中心值和 P95
    ↓ 只保留 P95 不超过 95% 卡容量的候选
安全候选集合
    ↓
V4b 在过滤后的候选集合内重新计算 set-aware 吞吐分数
    ↓
选择预测吞吐最高的配置
```

这里有一个容易混淆的地方：

- **显存模型和吞吐模型不是同一个模型**，训练目标、特征和损失函数都不同。
- 显存模型先负责“能不能安全跑”，吞吐模型再负责“安全候选里哪个更快”。
- V4b 是当前 H800 **指标上的综合最优吞吐模型**；V5 是当前 **工程封装主线**。两者不是同一个含义。

## 2. 显存模型：physical-shares

### 2.1 模型要解决什么问题

physical-shares 对每个训练配置输出两个值：

1. `memory_center`：显存占用的中心预测，适合看“预计会占多少显存”。
2. `memory_p95`：带尾部保护的保守预测，适合做 OOM 安全过滤。

最终准入规则为：

```text
memory_p95 <= 0.95 × GPU 显存容量
```

当前实验链路报告的 H800 容量为 `139.83 GiB`，因此准入安全线约为：

```text
0.95 × 139.83 ≈ 132.84 GiB
```

### 2.2 建模主线：物理基线 × 数据驱动修正

模型不是直接拿配置特征回归最终显存，而是分两层：

```text
第一层：用训练机制计算解析显存基线
第二层：用回归模型学习解析基线与真实 reserved memory 之间的倍率残差
```

#### 第一层：解析显存基线

解析基线由 9 类显存构成：

1. 参数常驻显存；
2. 梯度显存；
3. 优化器状态显存；
4. 保存的激活值；
5. gradient checkpointing 的重算工作区；
6. attention 工作区；
7. logits 工作区；
8. ZeRO collective 通信工作区；
9. ZeRO Stage 3 的实时参数工作区。

这些分量会根据以下配置发生变化：

- Full / LoRA；
- gradient checkpointing；
- ZeRO stage；
- GPU 数；
- micro batch size；
- gradient accumulation；
- sequence cutoff；
- 模型参数量和网络结构。

解析总显存记为：

```text
M_analytic = Σ M_component
```

#### 第二层：28 维倍率残差回归

真实 PyTorch reserved memory 与解析值不会完全相同，因为还包含：

- CUDA allocator 预留；
- 临时张量和算子 workspace；
- 分布式通信峰值；
- 框架实现细节；
- 解析公式未覆盖的交互效应。

模型对成功运行样本学习下面的目标：

```text
y = log(M_observed_reserved / M_analytic)
```

最终中心预测为：

```text
M_center = M_analytic × exp(β0 + zᵀβ)
```

其中 `z` 一共 28 维：

- 19 个训练机制、规模及交互特征；
- 9 个解析显存分量在总解析显存中的占比。

回归器使用带正则的 ridge，当前 `alpha = 1`。训练时按场景做等权，避免候选配置较多的场景支配模型；原生校准数据权重为 1，历史数据权重为 0.25。

### 2.3 P95 和 OOM 保护怎么产生

中心值解决的是平均误差，但准入更关心漏掉 OOM 的风险。因此模型还会基于 out-of-fold 残差构造尾部保护：

```text
M_p95 = M_center × exp(max(q95_success, guard_oom, 0))
```

其中：

- `q95_success`：成功样本残差的 conformal 95% 分位数；
- `guard_oom`：从真实 OOM 样本反推出的最低保护倍率；
- 尾部校准优先使用与当前配置最相近的 selector，样本不足时依次退化到 `mode × GC` 和全局池。

这使模型能同时利用：

- 成功任务提供的真实显存数值；
- OOM 任务提供的“显存至少超过某个安全边界”的删失信息。

### 2.4 训练集和验证集规模

当前 physical-shares 冻结模型的数据规模为：

| 用途 | 数量 | 说明 |
|---|---:|---|
| 历史观测 | 594 | 低权重历史数据 |
| 原生校准观测 | 158 | 当前原生链路数据 |
| 训练观测合计 | **752** | 历史与原生合并 |
| 中心回归成功样本 | **624** | 有真实 reserved memory 的成功任务 |
| 尾部校准 OOM 样本 | **128** | 用于 OOM guard |
| 公共留出集 | **167** | 120 个成功任务 + 47 个 OOM |

这里的 752 是观测总数；中心回归只使用其中 624 个成功观测，128 个 OOM 主要进入尾部和准入安全校准。

### 2.5 当前准确度

#### 旧 H800 稠密文本公共留出集

| 模型 | 中心 MAPE | P90 绝对误差 | false-safe OOM | 安全失败数 |
|---|---:|---:|---:|---:|
| legacy 11D | 22.20% | 42.21% | 12 / 47 | 16 |
| native augmented | 12.29% | 23.76% | 2 / 47 | 6 |
| **physical-shares** | **5.55%** | **10.75%** | **0 / 47** | **0** |

physical-shares 的中心 signed bias 为 `+1.52%`，没有明显系统性低估；P95 覆盖率为 `96.67%`。

#### 2026-07-29 新冻结回放

在 64 条新结果（63 success、1 OOM）上：

| 模型 | 中心 MAPE | P90 绝对误差 | P95 覆盖率 | false-safe OOM |
|---|---:|---:|---:|---:|
| legacy 11D | 23.41% | - | - | - |
| native augmented | 4.40% | - | 96.83% | - |
| **physical-shares** | **6.74%** | **13.37%** | **100%** | **0 / 1** |

native augmented 在这批数据上的中心 MAPE 略低，但 physical-shares 的 P95 安全结果更好，且没有安全失败。因此当前仍以 physical-shares 作为安全优先模型。

#### 新模型泛化

- Qwen3-32B 稠密文本 LoRA：中心 MAPE `8.26%`；
- 9 / 9 个成功任务被 P95 覆盖；
- 7 / 7 个 Qwen3-32B Full / LoRA OOM 被拒绝；
- Qwen2.5 正式回放：61 success、1 OOM，中心 MAPE `6.83%`，P90 `13.38%`，P95 覆盖率 `100%`。

### 2.6 显存模型的适用边界

当前最重要的限制是：

1. **适合 H800 稠密文本模型，不应直接用于视觉语言模型。**  
   Qwen3-VL LoRA 回放中中心 MAPE 达到 `66.80%`，P95 覆盖为 `0 / 10`，并出现错误放行 OOM。

2. **P95 是安全优先的，可能偏保守。**  
   例如 Qwen2.5-14B Full 的中心 MAPE 只有 `2.18%`，但安全候选召回率只有 `33.33%`，可能导致某些场景没有任何候选通过。

3. **新架构需要重新校准。**  
   当前 Qwen3.5 只有 2 个显存观测点，只能算初步通过，不能视为充分验证。

## 3. 吞吐模型：V4b 双头 set-aware 模型

### 3.1 为什么不是只做一个绝对值回归

吞吐任务实际有两个目标：

1. 预测某个配置大约有多少 token/s；
2. 在同一个用户场景的候选配置中，把真正更快的配置排到前面。

这两个目标并不完全一致。一个模型可以绝对值误差较小，但候选间的细微顺序判断错误；对于最终配置推荐，后者往往更重要。

V4b 因此使用两个独立的 head：

- **absolute head**：学习绝对吞吐尺度；
- **rank head**：学习同场景候选之间的相对顺序。

### 3.2 两个 head 如何训练

#### Absolute head

absolute head 使用 70 维 full-factor 特征，直接拟合 log step time / log throughput 的绝对尺度，使用 robust joint ridge：

```text
a_i = absolute_head(x_i)
```

主要参数为：

- `alpha = 1`；
- pairwise 辅助损失权重 `0.25`；
- 历史样本权重 `0.25`。

#### Rank head

rank head 使用相同的 70 维特征，但训练目标是同场景候选对的 log-throughput 差值：

```text
r_i - r_j ≈ log(T_i) - log(T_j)
```

主要参数为：

- `alpha = 0.01`；
- 历史样本权重 `0.25`。

### 3.3 set-aware 融合

对同一用户场景内、经过显存过滤后的安全候选集合，V4b 先计算：

- absolute head 的输出 `a_i`；
- rank head 的输出 `r_i`。

然后进行组内中心化融合：

```text
log(T̂_i)
  = mean(a)
  + λ × (a_i - mean(a))
  + (1 - λ) × (r_i - mean(r))
```

H800 当前使用：

```text
λ = 0.25
```

含义是：

- 整个候选集合的绝对吞吐尺度由 absolute head 的均值锚定；
- 候选之间的差异，25% 来自 absolute head，75% 来自 rank head。

如果一个场景只剩一个安全候选，则退化为 absolute head。

### 3.4 70 维特征大概包括什么

特征可分为六类：

1. **训练机制和离散配置**  
   Full / LoRA、GC、ZeRO stage 等。

2. **并行与 batch 配置**  
   GPU 数、micro batch size、gradient accumulation、global batch size。

3. **模型架构**  
   参数量、层数、hidden size、attention 结构等。

4. **序列与数据负载**  
   cutoff、每 step token 数、样本长度分布和预运行数据画像。

5. **物理代理量**  
   FLOPs、HBM 访问、优化器开销、通信量、理想计算时间等。

6. **关键交互项**  
   配置、模型规模、序列长度与硬件负载之间的组合效应。

### 3.5 训练集和验证集规模

当前 V4b H800 冻结产物的数据规模为：

| 用途 | 数量 |
|---|---:|
| 严格历史候选 | 134 |
| 原生校准候选 | 104 |
| 训练候选合计 | **238** |
| 训练场景 | **63** |
| 训练候选对 | **1,200** |
| 公共留出候选 | **79** |

训练场景与留出场景没有重叠。这里的“候选对”是在同一场景内部构造的相对快慢比较。

### 3.6 为什么当前认为 V4b 最好

#### 较早的 H800 新模型公共回放

23 个成功任务、12 类配置、3 个场景、21 个候选对：

| 模型 | MAPE | pairwise accuracy | top-1 regret | 达到真实最优 90% 的场景 |
|---|---:|---:|---:|---:|
| V4 | **20.87%** | 85.71% | 4.48% | 2 / 3 |
| **V4b** | 22.88% | **95.24%** | **0%** | **3 / 3** |
| V5 | 42.53% | 95.24% | 2.99% | 3 / 3 |

这批数据中 V4 的绝对 MAPE 略好，但 V4b 的排序和最终选型明显更好。

在严格的模型文件生成后数据子集上：

| 模型 | MAPE | pairwise accuracy | top-1 regret |
|---|---:|---:|---:|
| V4 | 18.10% | 76.92% | 6.71% |
| **V4b** | **16.21%** | **92.31%** | **0%** |
| V5 | 26.57% | 90.00% | 8.98% |

一个典型例子是 Qwen3-32B 的 MBS 饱和场景，真实最优为 MBS=4：

- V4 选到 MBS=16，regret `13.43%`；
- V5 选到 MBS=8，regret `8.98%`；
- V4b 正确选到 MBS=4。

#### 最新 Qwen2.5 冻结回放

23 个成功任务、8 个场景、27 个候选对：

| 模型 | MAPE | P90 绝对误差 | pairwise accuracy | top-1 命中 | regret |
|---|---:|---:|---:|---:|---:|
| V4 | 11.12% | 20.44% | 100% | 8 / 8 | 0% |
| **V4b** | **9.71%** | **16.29%** | **100%** | **8 / 8** | **0%** |
| V5 | 11.99% | 22.18% | 100% | 8 / 8 | 0% |

这批最新回放中，V4b 不仅排序无损，绝对误差也是三个模型里最低。因此，若要为当前 H800 选择一个综合吞吐模型，V4b 是更合适的答案。

### 3.7 V4、V4b 和 V5 应该如何理解

| 版本 | 当前定位 | 优点 | 主要问题 |
|---|---|---|---|
| V4 | 旧单头基线 | 一部分旧留出集的绝对 MAPE 最低 | 排序和 MBS 饱和场景不够稳 |
| **V4b** | H800 当前离线综合冠军 | 双头融合，排序稳，最新 Qwen2.5 绝对值也最好 | 尚未成为统一 Predictor 的默认实现 |
| V5 | 工程统一主线 | 结构清晰、参数少、支持卡型 adapter、便于扩展 | 当前 H800 回放指标未超过 V4b |

V5 不是“效果最差的旧模型”，而是另一种取舍：

- 采用 5 个正值物理分量：compute、HBM、optimizer、communication、launch；
- 使用 smooth roofline；
- 用 35 个共享特征和卡型 adapter 学习效率修正；
- 通过 absolute、pairwise、listwise 联合目标训练；
- 当前数据覆盖 H800 和 4090，共 391 个成功候选、148 个场景、1,268 个候选对。

它的优势主要是工程统一和未来跨卡型扩展，不代表当前 H800 排名指标已经最好。

### 3.8 吞吐模型的适用边界

1. **V4b 是集合相关模型。**  
   显存过滤改变候选集合后，必须在剩余候选上重新计算 set-aware 融合，不能先算完 V4b 再简单删除 OOM 候选。

2. **原始产物中的部分工作负载特征曾依赖运行后计数器。**  
   真正用于预估时必须使用运行前可获得的数据集静态画像；最新回放已经按 pre-run 画像执行，但旧指标解读时仍要注意该差异。

3. **Qwen3.5 目前不能认为已经验证。**  
   Full 和 LoRA 各只有一个配置，没有形成候选排序；即使排除首 step 编译开销，三个吞吐模型的绝对误差仍然很大。

4. **V4b 目前是“最新证据下应重新晋级的 challenger”。**  
   较早的嵌套验证没有稳定证明它优于 V4，所以旧产物里曾被标为 rejected challenger；后续未见模型和 Qwen2.5 回放才给出了更强支持。它尚未自动等同于线上默认模型。

## 4. 两个模型怎样串起来

推荐的 H800 推理流程如下。

### 第一步：生成候选

对用户给出的模型、数据集和训练目标枚举：

- Full / LoRA；
- GPU 数；
- MBS；
- gradient accumulation；
- GC；
- ZeRO stage；
- cutoff 等候选。

### 第二步：显存安全过滤

对每个候选运行 physical-shares：

```text
analytic components
    → residual center
    → conformal/OOM tail
    → memory_center + memory_p95
```

只保留：

```text
memory_p95 <= 0.95 × H800 capacity
```

### 第三步：在安全候选中计算吞吐

对过滤后的每个场景重新运行 V4b：

```text
absolute head + rank head
    → set-aware group centering
    → predicted throughput
```

### 第四步：输出推荐和风险信息

建议最终同时返回：

- 推荐配置；
- 预测 token/s；
- 显存中心值；
- 显存 P95；
- 安全余量；
- 模型是否超出已验证分布；
- 若没有候选通过，明确说明是 P95 过于保守还是所有候选确实危险。

## 5. 当前端到端表现

在最新 Qwen2.5 回放中，经过 physical-shares 过滤后：

- 17 个成功任务被准入；
- 形成 5 个可排序场景、18 个候选对；
- V4b MAPE 为 `10.75%`；
- pairwise accuracy 为 `100%`；
- top-1 regret 为 `0%`。

不过，physical-shares 的保守 P95 使 1 个场景没有候选通过。因此端到端在 8 个场景中只能完成 7 个场景的选择：

```text
有候选时：7 / 7 精确选中 top-1
按全部场景计：7 / 8 达到真实最优的 90%
```

这说明当前系统下一步最值得优化的未必是吞吐排序，而是：

- 在不增加 false-safe OOM 的前提下，提高显存 P95 对安全成功配置的召回率；
- 尤其处理 Qwen2.5-14B Full 一类中心值准、但 P95 偏保守的 selector。

## 6. 最终建议

### 如果现在只针对 H800 稠密文本模型

采用：

```text
physical-shares + V4b
```

- physical-shares 用于中心显存预测、P95 安全过滤和 OOM 拒绝；
- V4b 用于安全候选内的吞吐预测、排序和最终选配置。

### 如果要接当前统一 Predictor

需要认识到当前工程现状：

- 显存应接 physical-shares；
- 吞吐统一接口当前以 V5 为主；
- 若要把离线最优的 V4b 变成默认，需要完成统一接口接入、只使用 pre-run 特征、冻结回归测试以及 shadow 对比。

### 暂不建议直接覆盖的范围

- Qwen3-VL 等视觉语言模型的显存推荐；
- 样本极少的 Qwen3.5 吞吐结论；
- 未经新卡型 adapter 或校准的非 H800 卡型；
- 使用运行后才知道的动态计数器做“预运行”吞吐预测。
