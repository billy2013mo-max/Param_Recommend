# H800 统一资源配置预测器使用说明

> 初版日期：2026-07-30；当前绑定更新：2026-08-11  
> 当前链路：统一有界显存 V3 + 最小卡数策略 + 结构化吞吐 V5  
> 发布状态：`active_recommendation`；推荐结果已切到 V3 + V5，但不允许自动发起训练

## 1. 当前默认入口

当前稳定入口是 `H800ResourcePredictor`，默认显存门禁为 `unified_v3`，输出
schema 为：

```text
sft_h800_unified_v3_throughput_v5_prediction/v1
```

端到端流程为：

1. 接收同一业务场景下的完整候选配置；
2. 根据数据画像构造有效序列和解析显存参考；
3. 用统一有界 V3 预测 reserved memory 中心；
4. 用独立共享风险头构造准入上界，过滤可能超过安全线的候选；
5. 对通过显存门禁和支持域检查的候选运行结构化吞吐 V5；
6. 找到仍有安全候选的最小 GPU 数；
7. 在该 GPU 数内选择 V5 预测有效吞吐最高的配置。

当前产品策略仍是：

```text
minimum_admitted_gpu_count_then_throughput_v5
```

跨卡数吞吐榜会保留用于诊断，但不会自动执行 1→2→4 扩卡。

主要文件如下。

| 内容 | 路径 |
|---|---|
| 稳定入口 | `offline_experiments/scripts/h800_resource_predictor.py` |
| V3 + 吞吐 V5 适配层 | `offline_experiments/scripts/h800_unified_v3_throughput_v5_predictor.py` |
| 示例请求 | `offline_experiments/examples/h800_unified_v3_throughput_v5_request.json` |
| 当前入口测试 | `offline_experiments/tests/test_h800_unified_v3_throughput_v5_predictor.py` |
| V3 显存产物 | `offline_experiments/artifacts/h800_unified_bounded_memory_candidate_v3.json` |
| V3 特征模型目录 | `offline_experiments/artifacts/h800_bounded_memory_v2_model_inventory_v1.json` |
| 吞吐 V5 产物 | `offline_experiments/artifacts/structured_throughput_modeling.json` |
| 旧显存门禁，仅回滚 | `offline_experiments/artifacts/h800_challenger_modeling.json` |

当前默认路径不加载 `joint_throughput_modeling.json`，也不加载它绑定的旧显存
artifact。数据集标识只用于定位运行前静态画像；吞吐 V5 拟合的是长度分布、有效
token、attention pair、模型结构和并行机制等结构特征，不把 `dataset_id` 当成可拟合
的身份特征。旧 physical-shares + V4b 只在显式整链路回滚时加载。

## 2. V3 显存门禁的数学含义

给定候选配置 $x$，先用模型结构、训练机制、GPU 数、MBS、有效序列和数据画像
构造解析显存参考 $M_{\mathrm{ref}}(x)$，单位为 bytes/GPU。

中心头和风险头分别预测 log-ratio 校正：

$$
C(x)=M_{\mathrm{ref}}(x)\exp(f_c(z(x))),
$$

$$
R(x)=M_{\mathrm{ref}}(x)\exp(f_r(z(x))).
$$

其中：

- $C$：reserved memory 中心预测；
- $R$：独立风险头输出；其拟合同时使用精确 success 与右删失 OOM 约束；
- $z$：机制、资源、物理占比和数据画像特征。

当前准入上界为：

$$
U(x)=\max\left(C(x),\;1.0170738699\,R(x)\right).
$$

H800 安全线为：

$$
L_{\mathrm{safe}}
=0.95M_{\mathrm{capacity}}
=142{,}635{,}080{,}089.6\ \mathrm{bytes}
\approx132.84\ \mathrm{GiB}.
$$

显存门禁为：

$$
A_{\mathrm{memory}}(x)=\mathbb I[U(x)\le L_{\mathrm{safe}}].
$$

这里必须区分中心和上界：中心回答“最可能需要多少显存”，上界回答“按当前风险
校准，应该用多少显存做放行判断”。$U$ 不是统计意义上的 P95。JSON 中保留的
`operational_p95_reserved_bytes` 只是旧消费者兼容别名，其值等于 $U$。

历史显存锚点在 V3 中禁用，不能覆盖 V3 的拒绝或放行：

```text
memory.anchor_override_applied = false
memory.admission_source = unified_v3_center_risk_upper
```

## 3. 输入

输入可以是 JSON 数组，也可以是包含 `candidates` 的对象：

```json
{
  "candidates": [
    {
      "request_id": "candidate-a",
      "comparison_group": "qwen3-14b-full-short512-gbs64",
      "hardware_id": "h800",
      "model_id": "qwen3_14b",
      "training_mode": "full",
      "dataset_id": "short_512",
      "dataset_category": "short",
      "target_gbs": 64,
      "cutoff_len": 512,
      "gpu_count": 4,
      "physical_mbs": 8,
      "zero_stage": 3,
      "gradient_checkpointing": false,
      "packing": false,
      "dtype": "bf16"
    }
  ]
}
```

主要字段如下。

| 字段 | 是否必需 | 含义 |
|---|---|---|
| `request_id` | 建议 | 候选唯一标识 |
| `comparison_group` | 建议 | 固定业务场景下可相互比较的候选组 |
| `model_id` | 必需 | 当前必须存在于 V3 特征模型目录 |
| `training_mode` | 必需 | `full` 或 `lora` |
| `dataset_id` | 必需 | 已加载的数据画像 ID |
| `dataset_category` | 自定义数据建议 | `short`、`multiturn`、`longtail` 或 `longcontext` |
| `target_gbs` | 必需 | 目标 global batch size |
| `cutoff_len` | 必需 | 单序列截断长度 |
| `gpu_count` | 必需 | GPU 数量 |
| `physical_mbs` | 必需 | 每卡 micro batch size；也接受 `mbs` |
| `zero_stage` | 必需 | 单卡为 0；多卡为 1、2 或 3 |
| `gradient_checkpointing` | 可省略 | 默认 `false`；也接受 `gc` |
| `packing` | 可省略 | 默认 `false`；当前 `true` 会被支持域拒绝 |
| `dtype` | 可省略 | 默认 `bf16`；当前仅 BF16 在支持域内 |
| `kernel_path` | 可省略 | 默认使用 H800 FA3 路径 |
| `lora_rank` | 可省略 | 默认 32 |

同一 `comparison_group` 内，模型、数据画像、训练方式、GBS、cutoff、packing 和
dtype 必须一致；GPU 数、MBS、ZeRO、GC 和 kernel 可以变化。对于
`packing=false`，还必须满足：

```text
target_gbs % (gpu_count * physical_mbs) == 0
```

目录外模型目前会 fail closed，返回 `memory_prediction_unavailable`。MoE、VL、
非 Qwen 架构会被标记为 `unsupported`，不会进入吞吐排序。

## 4. 输出

### 4.1 报告级字段

| 字段 | 含义 |
|---|---|
| `schema` | 当前输出契约 |
| `release.mode` | `active_recommendation` |
| `release.automatic_execution_allowed` | 固定为 `false` |
| `activation_record` | 本次启用范围、授权和回滚门禁 |
| `runtime_binding` | H800 runtime 绑定和吞吐基函数兼容性审计 |
| `memory_gate` | V3 中心、风险头、上界公式和安全线比例 |
| `throughput_model` | V5 目标、单输出契约和数据集身份特征开关 |
| `model_artifacts` | V3 显存、特征目录、吞吐 V5 及其推理实现 |
| `predictions` | 每个候选的完整结果 |
| `ranking_groups` | 每组排序和最终选择 |
| `report_sha256` | 报告防篡改校验和 |

### 4.2 候选显存字段

| 字段 | 含义 |
|---|---|
| `analytic_reference_bytes` | 有效序列下的解析参考 $M_{\mathrm{ref}}$ |
| `reserved_center_bytes` | 中心预测 $C$ |
| `risk_guard_bytes` | 风险头输出 $R$ |
| `risk_guard_multiplier` | 当前为 1.0170738699 |
| `admission_upper_reserved_bytes` | 准入上界 $U$ |
| `operational_p95_reserved_bytes` | 旧接口兼容别名，等于 $U$，不是 P95 |
| `safe_limit_bytes` | 95% H800 容量线 |
| `headroom_to_safe_limit_bytes` | $L_{\mathrm{safe}}-U$；负数表示越线 |
| `admitted` | 同时通过 V3 显存门禁和支持域时为 `true` |
| `rejection_reason` | 显存越线、支持域外或预测不可用等原因 |
| `gib` | 对应字段的 GiB 版本 |

只有 `memory.admitted=true` 的候选才会得到吞吐 V5 结果。V5 使用同一个
`predicted_effective_tokens_per_second` 同时表示绝对有效吞吐和候选排序分数，并
同时输出 `predicted_step_seconds`。这与 V4b 的独立 absolute/rank 双头不同。

## 5. 运行方式

命令行：

```bash
PYTHONPATH=offline_experiments/scripts \
python offline_experiments/scripts/h800_resource_predictor.py \
  offline_experiments/examples/h800_unified_v3_throughput_v5_request.json \
  --output /tmp/h800_unified_v3_throughput_v5_prediction.json
```

Python：

```python
from h800_resource_predictor import H800ResourcePredictor

predictor = H800ResourcePredictor()
report = predictor.predict(candidates)
selected = report["ranking_groups"][0]["selected_request_id"]
```

如果需要显式回滚：

```bash
PYTHONPATH=offline_experiments/scripts \
python offline_experiments/scripts/h800_resource_predictor.py request.json \
  --memory-gate legacy_physical_v1 \
  --output /tmp/h800_legacy_rollback.json
```

该参数回滚的是“旧 physical-shares 显存 + V4b 吞吐”整条链路，不会把旧显存和
当前 V5 混用。

## 6. 数值例子

示例请求的安全线都是 132.84 GiB：

| 候选 | V3 中心 | V3 准入上界 | 安全线距离 | V5 预测有效吞吐 | V5 名次 |
|---|---:|---:|---:|---:|---:|
| 4 GPU、MBS 8、ZeRO-2、GC 开 | 98.02 GiB | 98.02 GiB | 34.82 GiB | 4691.48 tokens/s | 1 |
| 4 GPU、MBS 8、ZeRO-3、GC 关 | 99.43 GiB | 112.76 GiB | 20.08 GiB | 4620.81 tokens/s | 2 |
| 4 GPU、MBS 4、ZeRO-2、GC 关 | 117.17 GiB | 121.15 GiB | 11.69 GiB | 3806.58 tokens/s | 3 |
| 4 GPU、MBS 4、ZeRO-3、GC 关 | 85.77 GiB | 94.08 GiB | 38.76 GiB | 2952.68 tokens/s | 4 |

第三项是本次替换最直观的 case：旧门禁给出 134.80 GiB 并拒绝；V3 给出
117.17 GiB 中心和 121.15 GiB 上界，距离安全线仍有 11.69 GiB，因此进入
吞吐 V5。严格结论只是“按当前 V3 规则应放行”；单个 case 不能证明所有分布外配置
都安全。

这个例子也能看出更换吞吐模型不是改名：V4b 原先把 ZeRO-3、MBS=8、GC 关排在
第一；V5 把 ZeRO-2、MBS=8、GC 开排在第一。当前默认选择已经以后者为准。

## 7. 新业务数据画像

新增画像文件名必须为：

```text
<dataset_id>.qwen3_nothink.jsonl
```

每行保存 tokenizer/template 处理后的静态统计，不保存原文，例如：

```json
{
  "sample_id": "stable-hash",
  "total_tokens": 1479,
  "label_tokens": 1150,
  "turns": 12,
  "assistant_turns": 6
}
```

调用时传入额外画像目录：

```bash
PYTHONPATH=offline_experiments/scripts \
python offline_experiments/scripts/h800_resource_predictor.py request.json \
  --additional-dataset-profile-dir /path/to/customer_profiles \
  --output /tmp/prediction.json
```

请求中应同时绑定真实 tokenizer 和模板版本。新增画像会标记为 `caution`，但只要
模型和机制仍在支持域内，V3 会使用该画像的 mean、P90、P99、batch max、最大值、
变异系数、截断率和稀有尾部差等特征完成显存推断。

## 8. 当前证据与边界

### 8.1 同集开发/回放证据

以下是 531 行、49 个来源上的同集回放，包含 425 个精确 success 和 106 个 OOM。
这是经验观察，不是独立业务盲测：

| 模型 | 来源等权中心 MAPE | 行级中心 MAPE | 中心 P90 APE | 安全放行率 | OOM 放行率 |
|---|---:|---:|---:|---:|---:|
| 旧门禁 | 11.46% | 14.97% | 33.42% | 379/394 = 96.19% | 2/106 = 1.89% |
| 当前 V3 | 8.77% | 7.77% | 16.71% | 381/394 = 96.70% | 0/106 = 0% |

这组结果支持“V3 在当前回放集合上同时改善三个主指标”，但不构成数学上的全域
优越性保证。

### 8.2 独立业务盲测进度

当前有效观测为 35/60：34 个 success、1 个 OOM。

| 指标 | 当前值 |
|---|---:|
| 数据集等权中心 MAPE | 14.96% |
| 中心 bias | +9.88% |
| 行级中心 MAPE | 13.58% |
| 中心 P90 APE | 33.11% |
| 安全配置放行率 | 21/30 = 70% |
| OOM 放行率 | 0/1 = 0% |

OOM 分母只有 1，且 25 个任务尚未形成有效观测，因此最终泛化验收仍未完成。

### 8.3 吞吐 V5 冻结验证

以下是吞吐 V5 冻结产物记录的阻塞式留出结果，属于已有实验观察：

| 协议 | 场景等权 MAPE | 场景等权成对排序准确率 | Top-1 regret |
|---|---:|---:|---:|
| H800 固定留出 | 14.98% | 90.39% | 1.75% |
| RTX 4090 完整场景留出 | 13.36% | 94.12% | 0.58% |
| RTX 4090 完整模型留出 | 28.86% | 94.12% | 0.58% |
| 完整数据集留出 | 19.49% | 85.40% | 1.24% |

工程含义：V5 避免了 V4b 的数据集身份绑定和双头不一致，但未见模型的绝对尺度
误差仍可能较大。当前产物仍保留 `analysis_only=true`、`publishable=false` 的来源
状态；2026-08-11 的显式授权只启用推荐输出，不等于开放自动训练。

### 8.4 工程边界

- 当前启用覆盖 V3 显存准入和 V5 吞吐推荐，不开放自动训练执行；
- V3 源 artifact 保持 immutable、`publishable=false`，当前启用记录在版本化适配层；
- 支持域仍是 H800、BF16、dense Qwen、纯文本、非 packing；
- Packing、MoE、VL、跨机、其他卡型和目录外模型 fail closed；
- V5 的绝对值和排序使用同一个输出；仍需按上述留出误差理解绝对预测精度；
- 后续继续以中心偏差、安全放行率和 OOM 放行率为显存验收主指标；
- 端到端还需持续验证真实吞吐 Top-1 regret 和达到最优吞吐 90% 的比例。
