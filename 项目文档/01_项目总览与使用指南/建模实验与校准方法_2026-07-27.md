# DeepSpeed SFT 训练配置推荐器：建模、实验与校准方法

**日期**：2026-07-27
**性质**：方法论与现状说明(独立文档,可单独阅读)
**一句话**：用"解析公式骨架 + 基于实验的比值校准"来预测每个训练配置的显存/吞吐,并对候选配置排序;当前**能过滤会 OOM 的配置、能识别明显好坏,但选不准最优的那一个**(排序 top-1 ≈ 0.72),瓶颈在模型表达力与数据,而非实验量。

---

## 1. 如何建模

整体范式是 **analytic backbone(解析骨架)+ experiment-calibrated correction(实验校准修正)**,刻意避免两个极端——既不是纯理论公式(外推不准),也不是纯数据拟合(泛化差、易过拟合)。

### 1.1 解析骨架(不拟合、不碰 GPU)
先用物理量把任一配置的资源与吞吐算出一个**解析基线**(`h800_theory_basis.py: memory_basis / throughput_basis`),把实测观测投影到与 CPU 侧规划器同一套物理量上。核心是**从模型几何 + 并行策略推导每 GPU 显存与算力**,而不是回归——所以没测过的配置也能算。

**(a) 显存 = 模型状态 + 激活 + 工作区。**
模型状态用固定的**每参数字节数**常量:参数 `2 B`(bf16)、梯度 `2 B`、优化器 `12 B`(Adam 的 fp32 动量+方差+主副本)、logits `4 B`。ZeRO 阶段决定这三项**是否除以分片数** `shards = gpu_count`:

| ZeRO | 参数 | 梯度 | 优化器 |
|------|------|------|--------|
| 0 | `loaded·2` | `trainable·2` | `trainable·12` |
| 1 | `loaded·2` | `trainable·2` | `trainable·12 / shards` |
| 2 | `loaded·2` | `trainable·2 / shards` | `trainable·12 / shards` |
| 3 | `loaded·2 / shards` | `trainable·2 / shards` | `trainable·12 / shards` |

(LoRA 下 `trainable ≪ loaded`,所以优化器项极小——这解释了 LoRA 的显存画像与 Full 完全不同。)

**(b) 激活**由模型几何逐项推导,而非估:每层每 token 的成本 `per_token_layer = 6·hidden + 2·kv_width + 3·intermediate`,再乘 `micro_batch · sequence · layers`。**gradient checkpointing 改变量纲**:开启时只存 `mbs·seq·layers·hidden`(检查点)+ 一层重算量;关闭时存完整的 `mbs·seq·layers·per_token_layer`。注意力项额外含 `mbs·heads·seq·4`(softmax 工作区),logits 项 `mbs·seq·vocab·4`。

**(c) 吞吐/算力**基于 H800 物理常量:HBM 带宽 `3.35e12 B/s`、节点内带宽 `900e9 B/s`、HBM 效率默认 `0.60`、集合通信效率 `0.70`。ZeRO-2/3 的 all-gather / reduce-scatter 通信载荷按 `trainable·2 B`(可配 bucket 上限)推导,得到一个通信时间下界。

**(d) 输出**:这一层只做投影,**不拟合任何系数**,产出 `theory_only` 的 bootstrap 基础,并对每条观测给出 `analytic_state_lower_bound_bytes_per_gpu` 等解析量。它保证外推不失控——校准只在其上做**有界的比值修正**。

### 1.2 实验校准修正(对数线性 ridge)
用实测值除以解析值得到**修正比值**,再用回归拟合这个比值随配置变化的规律:

- **目标量**:`log(实测吞吐)`、`log(实测显存)`(或 `log(实测/解析)` 比值)。取对数的三个理由:①资源随规模呈乘性增长,对数化后近似线性;②误差按**相对比例**(MAPE)度量而非绝对值;③保证预测恒为正(`exp` 反变换)。
- **模型**:对数线性 **ridge 回归**(`stage_decisions.py: resource_features` / `ridge_coefficients`)。
- **当前特征(11 维)**:
  `intercept, log(参数量), log(序列长), log(GBS), log(卡数), log(mbs), is_full, gc, zero2, zero3, packing`
  —— **目前没有交互项**(尝试与结论见 §4)。
  > 注:`intercept`(截距)不是物理维度,而是回归的**技术常数项**——特征值恒为 `1.0`,其系数是全局偏置(所有其他特征为 0 时的预测起点),让回归线不必强制过原点。因此 11 维中真正的配置特征是其余 10 维。前 5 个是连续量(取 log),后 5 个是 0/1 指示(`is_full`/`gc`/`packing` 开关,`zero2`/`zero3` 是 ZeRO 阶段的 one-hot,阶段 0/1 落在截距基准里)。
- **显存与吞吐分开建模,用途不同**:
  - **显存 → 可行性门控**:预测 P95 ≤ 0.95 × 显存容量才允许该配置;
  - **吞吐 → 排序**:对通过门控的候选按预测吞吐排序,选最优。
- **OOM 的处理**:OOM 观测是**右删失下界不等式**("至少需要这么多显存"),绝不当作峰值实测值填进拟合——避免把失败样本污染成数值标签。

### 1.3 ridge 求解的实现细节

拟合是一行闭式解(`ridge_coefficients`):

```python
penalty = np.eye(d) * ridge      # 岭惩罚
penalty[0, 0] = 0.0              # ★ 截距不惩罚
β = pinv(Xᵀ X + penalty) @ Xᵀ y  # 广义逆,数值稳健
```

三个关键设计:
1. **`penalty[0,0]=0`**:截距项**不做正则化**——否则会人为把基准值往 0 拉,系统性低估。这是标准做法,也是"截距是技术项、非物理量"的体现。
2. **`ridge` 惩罚项**(评估用 `1e-3`):当特征近共线或某场景样本少时,防止系数爆炸,牺牲一点偏差换方差稳定。**这也是为什么加交互特征在少候选口径下反而更差(§4)——惩罚不足以压住高维过拟合。**
3. **`pinv`(伪逆)**:即使 `XᵀX` 奇异(例如某 fold 内某特征恒定)也能求解,不会崩。

### 1.4 从多次重复到"一个配置"的聚合

回归的输入不是原始 run,而是聚合后的配置(`aggregate_configurations`):

- 按 `configuration_key`(model, train, dataset, gbs, gpu, mbs, zero, gc, packing)分组;
- **只有 success 且带吞吐值的 run 计入**;吞吐取该组的**中位数**(`median`,抗离群),并记录变异系数 `cv`;
- **完整性严格**:计划的 repeat 索引必须全部成功、job_id 集合完全匹配才标 `complete=True`;重复索引冲突/缺失一律判**不完整**而非静默平均。
- 这一步是**双刃剑**:它保证了每个配置的吞吐是稳健中位数,但也使每个"可排序场景"内的候选数很少(多为 2 个)——直接限制了排序回归能承受的模型复杂度(§4、§5.1)。

## 2. 如何设计实验

实验不是随机撒点,而是围绕一套**可交叉验证、防信息泄漏**的结构来设计。

### 2.1 场景与配置族
- **科学切分单元(场景)**:`(模型, 训练方式, 数据集, 目标GBS)`。
- **配置族(selector)**:`(train_type, zero_stage, gradient_checkpointing)` —— 共 12 个族。

### 2.2 两种角色,互不重叠(防泄漏)
每条实测都带 `calibration_partition.role`:

| 角色 | 用途 | 关键约束 |
|------|------|---------|
| `calibration` | **参与拟合** | — |
| `holdout` | **完全不参与拟合**,只用于独立验收 | 与 calibration 的切分单元**互不重叠**(`model_length_disjoint` 策略) |

这保证验收指标不被训练数据污染。

### 2.3 每个配置族的最低覆盖门槛
- 标定:≥6 可行性行 + ≥4 吞吐行
- 留出:≥4 可行性行 + ≥2 吞吐行
- 每族 ≥2 个独立切分单元
- mbs 覆盖支持域 `{1,2,4,8,16}` 的**边界**(既要有 success,又要有 OOM 或 mbs=16 成功)
- mbs 域外的点(如 mbs=32)只作边界探测,**不进标定集**

### 2.4 缺口驱动、而非泛跑
每一轮实验都由**上一轮就绪审计暴露的具体缺口**驱动:审计报告哪个 selector / 角色 / 切分单元覆盖不足,就针对性补哪一批。本阶段共 6 批 ~300 个实验:

| 轮次 | 目的 | 规模 |
|------|------|------|
| 密度 | 补吞吐候选密度 | 48 |
| holdout r1/r2 | 建立留出覆盖 + ≥2 切分单元 + mbs 边界 | 50 + 99 |
| calib r3 | 补标定角色覆盖 + 变化性 | 116 |
| packing | packed vs unpacked 对照(ABBA 四元组) | 80 |
| gap r5 | 收口剩余 selector | 16 |

## 3. 如何用实验做校准(闭环)

一条**全程 fail-closed、可复现**的流水线,每一步都可审计:

```
跑实验 → 导出观测 → 恢复侧车 → 就绪审计 → 排序/预测评估
```

1. **跑实验** `run_job.py`：原生 v2 执行指纹——GPU UUID / 拓扑 / 运行时逐 rank 存证;冻结审批(design SHA + queue/provenance/manifest 校验)后才启动。
2. **导出观测** `export_h800_observations.py` → `canonical_h800_observations.jsonl`：只有**完整指纹且合格**的观测才标 `calibration_evidence_eligible`。
3. **恢复侧车** `recover_h800_historical_evidence.py`:逐条重算 source SHA,判定每条能否作 `calibration_candidate`,**从不放松校验**。
4. **就绪审计** `audit_h800_calibration_readiness.py`(schema v6):统计每 selector 是否 `ready_for_profile_candidate`、整体是否 `calibration_publishable`。
5. **排序/预测评估** `stage_decisions.py`:**全局场景留一交叉验证**(leave-one-(model,train,dataset,gbs)-scenario-out),报告 top-1 / 两两 / MAPE。

### 3.1 "有界的比值修正"到底约束了什么(需区分两条校准面)

代码里其实有**两条并存的校准面**,机制不同,不能混为一谈:

- **A. FLOPs 时间增益校准(真·比值修正)**:拟合 `log(实测 / 解析)`(`stage_decisions.py:1071/1113`,`observed_to_analytic_ratio`),预测 = `解析FLOPs × exp(log_ratio)`。这一条是严格的"解析锚定 + 有界倍率"——即使外推,解析项仍钉住量级。
- **B. 资源回归(显存/吞吐,用于排序与 holdout 评估)**:直接拟合 `log(实测吞吐)`、`log(实测显存)`(`:1227/1232`),特征是**物理驱动量的对数**(参数量、序列长、GBS、卡数、mbs)+ 开关。这里**解析下界不是乘回去的系数**,而是"物理量本身作为对数特征"进入回归——预测 = `exp(features @ β)`,不显式乘解析基线。

**两条面的共同物理先验**(这才是"有界"的实质):

- 显存侧:实测峰值 **≥** 模型状态解析下界,比值天然 ≥ 1,回归被下界从下方托住(§1.1 的 `analytic_state_lower_bound_bytes_per_gpu` 用于门控裁剪);
- 吞吐侧:实测效率落在理想带宽的 (0,1) 区间,HBM 效率 0.60 / 集合通信 0.70 给出物理上限。

> 说明:文档 §1.2 的目标量写作"`log(实测吞吐)`、`log(实测显存)`(或 `log(实测/解析)` 比值)"——括号内即 A 路径,括号外即 B 路径。**当前 top-1 排序分数走的是 B 路径**(资源回归的留一评估),因此下文 §3.3 的折机制针对 B。

### 3.2 恢复侧车与就绪审计的把关(为什么会"未就绪")

- **恢复侧车**逐条重算 `source SHA`:观测文件内容的哈希必须与冻结记录一致,否则该条**不得**作 `calibration_candidate`。这道校验是"正确性优先"的硬闸——**绝不为凑数放松**(参见项目约束:不重生成 14MB recovery、不弱化 `--verify-historical-sources`)。
- **就绪审计 v6** 对每个 selector 套用 §2.3 的门槛(标定 ≥6/≥4、留出 ≥4/≥2、≥2 切分单元、mbs 边界完整)。任一未满足 → 该 selector `ready_for_profile_candidate=False`;整体 `calibration_publishable` 只要有一个硬缺口(如独立 holdout 验收报告未签署、native-v2 发布锚点、packing 仅 1 个模板)就判 False。**这些是流程/架构缺口,不是实验量缺口。**

### 3.3 LOOCV 折的内部机制(排序分数怎么算出来)

评估用 `group_holdout_resource_evaluation`,是一套**双层留一**:

- **外层**:每次留出一个完整场景 `(model, train, dataset, gbs)` 作测试,其余场景拟合。**按场景留一**(而非按行)是为了防止"同场景不同 mbs"泄漏进训练集,逼模型做真正的跨场景外推。
- **门槛守卫**:`if len(groups)<3 or len(configs)<特征数+2: 判 pending`——样本不足以支撑该维度回归时**主动弃权**,不硬算一个虚高分。内层还有 `if len(train_rows)<特征数: continue`,避免欠定方程。
- **打分**:在留出场景内,对每个吞吐候选预测吞吐并排序。**top-1** = 预测最优 == 实测最优的场景占比;**pairwise** = 任意两候选相对次序预测正确的占比。**这正是 §1.4 少候选问题的落点**——多数留出场景只有 2 个候选,pairwise 几乎等价 top-1,也让复杂模型无从施展。

**校准哲学**:解析骨架管外推,实验只提供有界的修正比值;每步结果标 `bootstrap / theory_only / nonpublishable`;**宁可 fail-closed 判"未就绪",不放松校验换绿灯**。

## 4. 当前效果如何

### 4.1 数据规模(本阶段成果)
- 合格 native 实测点:**0 → 460**(成功 362 + OOM 98;标定 176 / 留出 175 / 未分区 109)
- 12 个配置族中 **11 个** 达 `ready_for_profile_candidate`(从 0 起步)
- native 证据通道打通;可支撑完整有界拟合

### 4.2 预测/排序能力(LOOCV,诚实指标)

| 能力 | 指标 | 评价 |
|------|------|------|
| **显存预测** | MAPE ≈ **0.176** | 配合 P95×0.95 门控,可**过滤明显会 OOM 的配置** ✅ |
| **吞吐排序** | top-1 ≈ **0.72**(聚合口径)/ **0.58**(全量原始口径);两两 ≈ 0.75 | **能识别明显好/坏,选不准最优那一个** ⚠️ |
| **吞吐绝对值** | MAPE ≈ **0.32** | 数值不准(本就非目标) |

**一句话**:可用于"排除坏配置 + 粗筛好配置",但离"高置信自动推荐最优"(top-1 ≥ 0.9)有明显距离。

## 5. 问题在哪里

问题已定位清楚,分三层,且**都不是"多跑实验"能解决的**:

### 5.1 模型表达力不足(主瓶颈)
- 排序回归是 **11 维对数线性、无交互项**。
- 尝试加 8 个交互特征:在**原始配置口径**下 top-1 +5.6%(0.556→0.611),但落地到**生产聚合口径**后 top-1 **反而下降**(0.724→0.711)——因为生产口径下多数 fold 只有 2 个候选,19 维特征相对训练量**过拟合**。已回滚。
- 结论:**线性模型 + 少候选评估口径,特征工程已到天花板**。

### 5.2 数据侧已到头
- 两次实证:泛跑(+460 native 点)与针对性补候选(+45)对排序**均零收益**。
- 补数据不再是杠杆;数据清洗只改善**正确性**,不改善排序分数。

### 5.3 LoRA 是错误重灾区(数据质量问题)
- 排序错误中 LoRA 占 **2/3**(错误 fold LoRA:full ≈ 23:9)。
- 根因是**数据标签冲突**:同一配置既有 success 又有 OOM 记录。重跑验证:**10 个冲突配置 20/20 全部 OOM**——原来的 success 是不可复现的假象(疑似早期共享机内存宽松/mixed-dtype),应以 OOM 清洗。
- 加 LoRA 专属特征救不了(过拟合),证明是数据问题不是特征问题。

### 5.4 "可发布"存在硬天花板(非实验可解)
- 第 12 个配置族(lora/zero3/gc=False)被一个 `mbs=32` 越界数据点卡住 → 需**数据口径决策**(排除/重分类),不是补实验。
- `calibration_publishable=False` 的剩余卡点是**流程/架构性**的:独立 holdout 验收报告(签署动作)、native-v2 发布锚点(架构限制)、packing holdout 需 ≥2 切分单元但模板只有 1 个。

---

## 6. 要真正突破排序,需要什么(需团队对齐)

以下超出"跑实验 / 调特征"范畴,属架构级决策:

1. **换评估/建模口径**:当前"聚合配置 + 少候选 LOOCV"既限制模型复杂度也是评估瓶颈;改用全量原始配置口径,交互特征的增益才可能兑现。
2. **换模型族**:线性 ridge → 带单调性约束的树模型 / GAM,可在不爆炸维度下吃下交互项。
3. **先做的低成本项(零 GPU)**:清洗 LoRA 标签冲突(以 OOM 为准)后重评估;处理 mbs=32 数据口径。
