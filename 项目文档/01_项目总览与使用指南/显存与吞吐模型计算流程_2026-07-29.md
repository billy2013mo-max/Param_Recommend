# 显存与吞吐模型：从输入到输出的完整计算流程

> 日期：2026-07-29  
> 范围：当前目录内冻结的 H800 `physical-shares` 显存模型和 V4b 吞吐模型  
> 依据：实际 Python 实现、冻结 JSON 参数和 Qwen2.5/Qwen3.5 回放链路  
> 目标：解释一次预运行预测从原始训练配置到最终显存、吞吐和推荐结果的每一个主要中间步骤

## 1. 总体关系

两套模型不是并行地各算各的，正确的端到端顺序是：

```text
原始用户请求
    │
    ├── 解析模型结构、硬件和训练配置
    │
    ├── 对每个候选运行 physical-shares
    │       ├── 解析显存九分量
    │       ├── 28维残差修正
    │       ├── P95 / OOM 尾部保护
    │       └── 输出 center、P95 和是否准入
    │
    └── 只保留显存安全候选
            │
            ├── 用静态数据集画像重建每 step 工作量
            ├── 构造 V4b 的 70 维特征
            ├── absolute head 预测绝对吞吐尺度
            ├── rank head 预测候选相对快慢
            ├── 在安全候选集合中做 set-aware 融合
            └── 输出 token/s、step time 和候选排序
```

可以把它们理解为：

- `physical-shares` 回答：**这个配置是否有足够把握不会 OOM？**
- `V4b` 回答：**在确认安全的配置里，哪个配置更快？**

## 2. 原始输入是什么

一次典型候选输入大致如下：

```json
{
  "request_id": "candidate-001",
  "hardware_id": "h800",
  "model_id": "qwen3_4b",
  "dataset_id": "multiturn_2048",
  "training_mode": "lora",
  "gpu_count": 2,
  "physical_mbs": 2,
  "target_gbs": 64,
  "cutoff_len": 2048,
  "gradient_checkpointing": false,
  "zero_stage": 2,
  "packing": false,
  "dtype": "bf16",
  "kernel_path": "fa3:orig+liger_fused_ce+optim=adamw_torch_fused"
}
```

主要字段对两套模型的影响如下：

| 输入 | physical-shares | V4b |
|---|---|---|
| `model_id` / 模型结构 | 决定参数、梯度、优化器、激活等显存分量 | 决定 FLOPs、流量和模型架构特征 |
| `training_mode` | 决定 Full 或 LoRA 的 loaded/trainable 参数量 | 决定 Full/LoRA 计算量和特征 |
| `gpu_count` | 决定 ZeRO 分片、Stage 3 live 参数等 | 决定并行计算、通信、GA 和特征 |
| `physical_mbs` | 决定激活、attention、logits 显存 | 决定 padding、每 step 工作量和计算流量 |
| `cutoff_len` | 决定激活、attention、logits 显存 | 决定静态 token 画像、FLOPs 和流量 |
| `zero_stage` | 决定状态分片和通信工作区显存 | 决定通信 payload、collective 数量和特征 |
| `gradient_checkpointing` | 改变 saved activation 和 recompute workspace | 增加重算 FLOPs、流量并进入模型特征 |
| `packing` | 当前主要影响尾部 selector，中心模型没有独立 packing 特征 | 改变静态数据集装箱和每 step 工作量 |
| `dataset_id` | 不直接进入中心显存模型 | 用来读取预运行静态 token 画像 |
| `target_gbs` | 不直接进入 28 维中心特征 | 决定 gradient accumulation 和 optimizer step 工作量 |
| `dtype` / `kernel_path` | 当前中心模型不直接使用 | 进入 V4b 的 dtype/kernel 离散特征 |
| H800 硬件参数 | 提供容量和安全线 | 提供峰值 FLOPs、HBM 和卡间带宽 |

一个重要差异是：

```text
physical-shares 主要关心单个时刻的峰值显存
V4b 关心完成一个 optimizer step 要做多少工作、花多少时间
```

因此 `target_gbs` 会显著影响吞吐 step time，但在当前 physical-shares 中不直接改变中心显存特征。

## 3. physical-shares 的完整计算链

### 3.1 第一步：校验输入并读取模型结构

首先根据 `model_id` 从模型 inventory 中取得：

- 基础参数量 `P_base`；
- hidden size；
- intermediate size；
- 层数；
- attention head 数；
- KV head 数和 KV width；
- vocabulary size；
- 最大序列长度；
- LoRA rank 和 LoRA target。

对于 LoRA，当前结构计算中假设 target 为 `all`，adapter 参数量为：

```text
P_adapter
  = lora_rank
  × num_layers
  × (9 × hidden + 2 × kv_width + 3 × intermediate)
```

然后得到：

```text
Full:
  loaded_parameters    = P_base
  trainable_parameters = P_base

LoRA:
  loaded_parameters    = P_base + P_adapter
  trainable_parameters = P_adapter
```

这里的区别很重要：

- Full 需要为全部基础参数保存梯度和优化器状态；
- LoRA 的基础模型仍需加载，但只有 adapter 是可训练参数。

### 3.2 第二步：读取 H800 容量

当前链路从硬件配置中读取 PyTorch 报告容量：

```text
device_capacity ≈ 139.83 GiB
safe_limit = 0.95 × device_capacity ≈ 132.84 GiB
```

最终不是用中心值与容量比较，而是用 operational P95 与安全线比较。

### 3.3 第三步：计算九类解析显存

记：

```text
N = GPU 数
B = physical MBS
L = cutoff length
P_loaded = 加载参数量
P_train  = 可训练参数量
```

当前常量口径为：

```text
参数：2 bytes / element
梯度：2 bytes / element
优化器：12 bytes / trainable parameter
通信：2 bytes / element
logits：4 bytes / element
```

#### 3.3.1 参数显存

```text
ZeRO 0/1/2:
  M_parameters = 2 × P_loaded

ZeRO 3:
  M_parameters = 2 × P_loaded / N
```

#### 3.3.2 梯度显存

```text
ZeRO 0/1:
  M_gradients = 2 × P_train

ZeRO 2/3:
  M_gradients = 2 × P_train / N
```

#### 3.3.3 优化器状态显存

```text
ZeRO 0:
  M_optimizer = 12 × P_train

ZeRO 1/2/3:
  M_optimizer = 12 × P_train / N
```

#### 3.3.4 Saved activations

先定义每 token、每层的解析激活宽度：

```text
per_token_layer
  = 6 × hidden
  + 2 × kv_width
  + 3 × intermediate
```

不开 gradient checkpointing：

```text
M_saved
  = B × L × num_layers
  × per_token_layer × 2
```

开启 gradient checkpointing：

```text
M_saved
  = B × L × num_layers
  × hidden × 2
```

#### 3.3.5 Recompute workspace

不开 GC：

```text
M_recompute = 0
```

开启 GC：

```text
M_recompute
  = B × L × per_token_layer × 2
```

#### 3.3.6 Attention workspace

```text
M_attention
  = B × L × (2 × hidden + 2 × kv_width) × 2
  + B × attention_heads × L × 4
```

#### 3.3.7 Logits workspace

当前采用保守的 full-logits 口径：

```text
M_logits = B × L × vocab_size × 4
```

#### 3.3.8 ZeRO collective workspace

模型使用 DeepSpeed 的保守 bucket 上限估算通信临时区：

- ZeRO 1：主要使用 reduce bucket；
- ZeRO 2：取 reduce bucket 与 all-gather bucket 的较大值；
- ZeRO 3：使用 reduce bucket，并单独计算 live parameters。

#### 3.3.9 ZeRO Stage 3 live parameters

ZeRO 3 虽然把常驻参数分片，但当前层或模块执行时仍需要临时 materialize 参数。

模型根据：

- 最大 live elements；
- 最大 reuse elements；
- 最大 module 参数量；
- 少量 persistent 参数；

估算其他 rank 临时加载到当前 rank 的参数量。

单卡或非 ZeRO 3 时该项为 0。

### 3.4 第四步：九分量求和

```text
M_analytic
  = M_parameters
  + M_gradients
  + M_optimizer
  + M_saved
  + M_recompute
  + M_attention
  + M_logits
  + M_zero_workspace
  + M_stage3_live
```

这个值不是最终预测，而是物理参考值。

它回答的是：

> 按当前解析机制，显存量级大约应该是多少？

### 3.5 第五步：构造 28 维 residual 特征

physical-shares 的 28 维特征分成两部分。

#### 19 个机制、规模和交互特征

```text
is_lora
gradient_checkpointing
zero2
zero3
lora_x_gc
lora_x_zero2
lora_x_zero3
gc_x_zero2
gc_x_zero3
lora_x_zero3_x_non_gc
log2_gpu_count
log2_mbs
log2_cutoff_over_512
log2_parameters_over_1p7b
lora_x_log2_parameters
gc_x_log2_cutoff
zero2_x_log2_gpu_count
zero3_x_log2_gpu_count
log2_mbs_x_log2_cutoff
```

#### 9 个显存分量占比

对每一个解析显存分量计算：

```text
share_k = M_component_k / M_analytic
```

对应：

```text
share_parameters
share_gradients
share_optimizer
share_saved_activations
share_recompute_workspace
share_attention_workspace
share_logits_workspace
share_zero_collective_workspace
share_stage3_live_parameters
```

为什么要使用 share？

例如同样都是 40 GiB 的解析显存：

- 一个配置可能主要由 saved activations 构成；
- 另一个配置可能主要由参数和 optimizer 构成。

两者受到 allocator、临时 workspace 和解析误差的影响并不相同。九个 share 能告诉回归器“这个总量是由什么组成的”。

### 3.6 第六步：使用冻结统计量标准化

对于 28 维原始特征 `x`：

```text
z_k = (x_k - mean_k) / scale_k
```

其中 `mean_k` 和 `scale_k` 都来自冻结训练产物：

```text
offline_experiments/artifacts/h800_challenger_modeling.json
  → memory
  → frozen_model
  → reserved_center
```

推理时不会重新计算训练集均值，也不会重新拟合。

### 3.7 第七步：预测解析值的 log 倍率残差

冻结 Ridge 计算：

```text
delta
  = intercept
  + Σ z_k × beta_k
```

训练目标是：

```text
y
  = log(observed_reserved / M_analytic)
```

因此中心预测为：

```text
M_center = M_analytic × exp(delta)
```

解释：

- `delta = 0`：相信解析总量；
- `delta > 0`：真实 reserved 通常高于解析值；
- `delta < 0`：解析值在这一机制组合下偏保守。

当前冻结中心模型参数：

```text
feature_set = physical_shares
feature_dimension = 28
alpha = 1.0
historical_scenario_weight = 0.25
fit_success_rows = 624
fit_scenarios = 53
```

### 3.8 第八步：选择成功样本的 P95 尾部

中心值不能直接用于 OOM 安全准入。模型还要为成功样本选一个 log-residual 上分位数。

当前 exact selector 是：

```text
(
  training_mode,
  zero_stage,
  gradient_checkpointing,
  packing
)
```

例如：

```text
("lora", 2, false, false)
```

查找层级为：

```text
exact selector
    ↓ 样本不足或有限样本 q95 不可识别
training_mode × gradient_checkpointing
    ↓ 仍不可用
pooled 全局桶
```

成功残差来自 inner leave-scenario-out：

1. 每次留出一个完整场景；
2. 用其他场景重新拟合中心模型；
3. 对留出场景计算：

```text
e_success = log(observed_reserved / predicted_center)
```

4. 在对应桶中取有限样本 conformal 95% 上分位数。

分位点下标为：

```text
rank = ceil((n + 1) × 0.95)
```

如果该 rank 超过当前样本数，则该桶不视为可用，并继续向更粗层级回退。

### 3.9 第九步：叠加 exact-selector OOM guard

OOM 的真实峰值不可见，不能伪造一个精确标签。

训练尾部时，只使用 OOM 提供的右删失下界：

```text
OOM_floor
  = max(
      OOM error 推导的 demand lower bound,
      95% safe limit + 1 byte
    )
```

然后计算：

```text
e_oom = log(OOM_floor / predicted_center)
```

每个 exact selector 保存所有 OOM 下界中的最大值：

```text
oom_guard = max(e_oom)
```

OOM guard 不做粗粒度回退，只使用 exact selector；没有对应 OOM 桶时取 0。

### 3.10 第十步：得到 operational P95

最终保护倍率为：

```text
log_guard = max(
  0,
  success_log_q95,
  exact_selector_oom_guard
)
```

最终：

```text
M_p95 = M_center × exp(log_guard)
```

这里取 `max(..., 0)` 表示 operational P95 不允许低于中心预测。

### 3.11 第十一步：输出和准入判断

physical-shares 原始输出包含：

```json
{
  "available": true,
  "reserved_center_bytes": 27870123456,
  "success_tail_source": "selector",
  "success_log_residual_upper": 0.2424,
  "oom_exact_selector_log_guard": 0.0,
  "operational_p95_reserved_bytes": 35514873211,
  "issues": []
}
```

业务层再执行：

```text
admitted = operational_p95_reserved_bytes <= safe_limit_bytes
```

当前 H800：

```text
safe_limit ≈ 132.84 GiB
```

若连 pooled 成功 q95 都不可用，则：

```text
available = false
issues = ["finite_sample_success_q95_unavailable"]
```

这种情况下不能把中心值当作安全上界放行。

## 4. V4b 的完整计算链

### 4.1 第零步：只接收显存过滤后的候选

V4b 的候选集合应先通过：

```text
physical-shares P95 <= 95% H800 capacity
```

然后，对同一个固定用户场景中的安全候选一起调用 V4b。

当前场景通常固定：

- model；
- dataset；
- Full/LoRA；
- target GBS；
- cutoff；
- packing；
- dtype。

候选之间通常变化：

- GPU 数；
- MBS；
- ZeRO stage；
- GC；
- kernel path。

### 4.2 第一步：规范化请求

输入校验包括：

- `training_mode` 只能是 Full 或 LoRA；
- `dataset_id` 必须有静态画像；
- GPU、MBS、GBS、cutoff 必须是正整数；
- cutoff 不能超过模型最大长度；
- `zero_stage` 归一化到 0、1、2、3；
- 未显式给 kernel 时使用 H800 默认 kernel；
- unpacked 模式要求：

```text
target_gbs % (gpu_count × physical_mbs) == 0
```

### 4.3 第二步：计算 gradient accumulation

unpacked 时：

```text
GA = target_gbs / (gpu_count × physical_mbs)
physical_sequences_per_optimizer_step = target_gbs
```

packing 时：

- 若用户显式提供 GA，使用显式值；
- 否则根据静态画像中的 `mean_samples_per_pack` 估算 GA；
- physical sequence 数为：

```text
gpu_count × physical_mbs × GA
```

### 4.4 第三步：从静态数据集画像估计每个 physical sequence 的工作量

V4b 的正式预运行回放不使用实验结束后的 token 计数器，而是读取：

```text
offline_experiments/artifacts/dataset_profiles/
  <dataset_id>.qwen3_nothink.jsonl
```

每条静态样本至少提供：

- total tokens；
- label tokens；
- turns。

先对长度做：

```text
used_length = min(total_tokens, cutoff_len)
```

#### Unpacked 数据

为了估计动态 padding，画像代码使用多个固定随机种子进行确定性 shuffle。

对每个 micro batch：

```text
computed_tokens
  = batch 中最大长度 × batch 样本数

attention_pairs
  = 最大长度² × batch 样本数
```

多次 shuffle 后取均值，得到每个 physical sequence 的预期：

```text
effective_tokens
computed_tokens
computed_attention_token_pairs
logical_samples = 1
```

#### Packed 数据

使用 deterministic best-fit-decreasing 近似把样本装入 cutoff 容量：

```text
effective_tokens = 每个 pack 实际装入的 token
computed_tokens  = cutoff
attention_pairs  = pack 内每个原始样本 length² 的和
logical_samples  = 每个 pack 包含的样本数
```

当前 packing 不属于主要已验证域，因此这是明确的预运行计算契约，不代表已经充分验证。

### 4.5 第四步：得到每个 optimizer step 的静态工作量

用每 physical sequence 的均值乘以本 step 的 physical sequence 数：

```text
work_per_step[key]
  = work_per_physical_sequence[key]
  × physical_sequences_per_optimizer_step
```

得到：

```text
effective_tokens
computed_tokens
computed_attention_token_pairs
logical_samples
```

其中：

- `effective_tokens` 是最终吞吐的分子；
- `computed_tokens` 反映 padding 后真正执行的 token 工作量；
- `attention_pairs` 反映 attention 的近似二次复杂度；
- `logical_samples` 用于样本吞吐和长度统计。

### 4.6 第五步：计算模型结构

V4b 与 physical-shares 使用相同的模型几何解析，包括：

- base / loaded / trainable 参数；
- LoRA adapter 参数；
- layers；
- hidden；
- intermediate；
- attention heads；
- KV width；
- vocab；
- LoRA rank。

### 4.7 第六步：根据静态工作量计算物理代理量

这些量不是 V4b 的最终物理公式，而是 70 维回归特征的一部分。

#### FLOPs

Full 的线性 FLOPs：

```text
linear_flops = 6 × linear_base × computed_tokens
```

LoRA：

```text
linear_flops
  = 4 × linear_base × computed_tokens
  + 6 × adapter_parameters × computed_tokens
```

Attention：

```text
attention_flops
  = 6 × num_layers × hidden × attention_pairs
```

GC 重算：

```text
recompute_linear
recompute_attention
```

最终：

```text
total_flops
  = linear
  + attention
  + recompute_linear
  + recompute_attention
```

#### HBM 流量

估算：

- 权重读取流量；
- 激活读写流量；
- attention 流量；
- GC 重算流量；
- optimizer 流量。

形成：

```text
kernel_traffic_bytes
optimizer_traffic_bytes
```

#### ZeRO 通信

根据：

- GPU 数；
- ZeRO stage；
- loaded/trainable parameters；
- gradient accumulation；
- bucket 大小；

估算：

```text
communication_payload_bytes
collective_count
```

例如 ZeRO 3 会考虑参数多次 materialization，GC 打开时 materialization 次数更高。

#### 理想硬件时间

```text
ideal_compute_seconds
  = total_flops / (gpu_count × H800 peak FLOPs)

ideal_kernel_hbm_seconds
  = kernel_traffic / H800 HBM bandwidth

ideal_optimizer_hbm_seconds
  = optimizer_traffic / H800 HBM bandwidth

ideal_collective_seconds
  = communication_payload / H800 link bandwidth
```

当前 H800 解析常量中：

```text
HBM bandwidth = 3.35e12 bytes/s
intra-node link bandwidth = 900e9 bytes/s
```

### 4.8 第七步：构造 V4b 的 70 维特征

70 维 full-factor 特征分为：

#### 训练机制和离散配置

```text

zero1 / zero2 / zero3
dtype_bf16
kernel_fa2 / kernel_fa3
kernel_liger
kernel_fused_ce
kernel_fused_optimizer
kernel_compile
dataset_short
dataset_multiturn
dataset_longtail
dataset_longcontext
```

#### 并行、batch 和 cutoff

```text
log2_gpu_count
log2_mbs
log2_gradient_accumulation
log2_target_gbs
log2_cutoff_over_512
```

#### 模型结构

```text
log2_base_parameters
log2_trainable_parameters
log2_loaded_parameters
log2_num_layers
log2_hidden_size
log2_intermediate_size
log2_attention_heads
log2_kv_width
log2_vocab_size
log2_lora_rank
```

#### 静态数据工作量

```text
log1p_effective_tokens_per_step
log1p_computed_tokens_per_step
log1p_attention_pairs_per_step
log1p_logical_samples_per_step
effective/computed tokens per sample
attention pairs per computed token
effective_to_computed_token_ratio
```

#### 物理代理量

```text
log1p_total_flops
attention_flop_share
recompute_flop_share
log1p_kernel_traffic_bytes
log1p_optimizer_traffic_bytes
log1p_communication_payload_bytes
log1p_collective_count
log1p_ideal_compute_seconds
log1p_ideal_kernel_hbm_seconds
log1p_ideal_optimizer_hbm_seconds
log1p_ideal_collective_seconds
log1p_flops_per_kernel_byte
ideal_collective_time_share
H800 peak/HBM/link descriptors
```

#### 机制交互

```text
lora_x_gc
lora_x_zero2
lora_x_zero3
gc_x_zero2
gc_x_zero3
zero2/zero3 × log2_gpu_count
zero2/zero3 × log2_parameters
gc × log2_cutoff
gc × log2_parameters
log2_mbs × log2_cutoff
log2_mbs × log2_parameters
log2_gpu_count × log2_parameters
```

### 4.9 第八步：组装 candidate

每个候选变成：

```text
candidate = {
  scenario_id,
  features[70],
  effective_log_work = log(effective_tokens_per_step),
  log_analytic_anchor
}
```

V4b 当前 absolute head 使用：

```text
target_mode = direct_log_step
```

所以虽然链路仍会计算 `log_analytic_anchor`，当前 absolute head 推理时不会把它加到预测 step time 中。

### 4.10 第九步：absolute head 预测 log step time

absolute head 有自己冻结的：

- 70 维 means；
- 70 维 scales；
- intercept；
- 70 维 coefficients。

标准化：

```text
z_abs = (x - mean_abs) / scale_abs
```

预测：

```text
log_step_abs
  = intercept_abs + z_absᵀ beta
```

再由静态有效 token 数换算绝对吞吐：

```text
a_i
  = log_throughput_abs_i
  = log(effective_tokens_per_step_i)
    - log_step_abs_i
```

因此 absolute head 的本质是：

```text
先预测 optimizer step 时间
再用 effective tokens / step time 换算 token/s
```

当前冻结参数：

```text
feature_set = full_factor
target_mode = direct_log_step
feature_dimension = 70
alpha = 1.0
pair_weight = 0.25
historical_scenario_weight = 0.25
Huber delta = 0.35 log-seconds
```

虽然叫 absolute head，其训练损失中仍包含 0.25 权重的场景内 pairwise step-difference 行，用来辅助保持局部顺序。

### 4.11 第十步：rank head 预测排序分数

rank head 同样接收 70 维特征，但有自己冻结的标准化统计量和系数：

```text
z_rank = (x - mean_rank) / scale_rank
r_i = z_rankᵀ gamma
```

它没有截距，因为训练数据是场景内候选差：

```text
(z_i - z_j)ᵀ gamma
  ≈ log(T_i) - log(T_j)
```

训练时会对一个场景内所有候选两两配对，并按场景等权，避免候选较多的场景占据过大权重。

当前参数：

```text
feature_set = full_factor
feature_dimension = 70
alpha = 0.01
historical_scenario_weight = 0.25
Huber delta = 0.35 log-throughput
```

`r_i` 本身不是 token/s，也不应该直接 `exp(r_i)` 当成最终吞吐；它只表示候选的相对位置。

### 4.12 第十一步：在安全候选集合内做 set-aware 融合

对同一场景中所有安全候选计算：

```text
a_bar = mean(a_i)
r_bar = mean(r_i)
```

H800 当前融合系数：

```text
lambda = 0.25
```

最终：

```text
log(T_hat_i)
  = a_bar
  + 0.25 × (a_i - a_bar)
  + 0.75 × (r_i - r_bar)
```

解释：

- 整组候选的绝对吞吐中心由 absolute head 的 `a_bar` 锚定；
- 候选相对中心的偏移，25% 使用 absolute head；
- 75% 使用更擅长排序的 rank head。

若只有一个安全候选：

```text
a_i = a_bar
r_i = r_bar
```

所以：

```text
log(T_hat_i) = a_i
```

即自动退化为 absolute head。

#### 为什么显存过滤后要重算 V4b

候选删除后，`a_bar` 和 `r_bar` 会变化，因此最终输出的绝对 token/s 会变化。

对于仍保留的任意两个候选，其预测差值为：

```text
log(T_hat_i) - log(T_hat_j)
  = 0.25 × (a_i - a_j)
  + 0.75 × (r_i - r_j)
```

所以在模型参数和候选单体特征不变时，剩余候选之间的两两顺序通常不因其他候选删除而变化；但：

- 最终绝对 token/s 会变化；
- 单候选时会退化成 absolute head；
- 当前模型的正式 contract 明确要求以实际 feasible set 重新计算。

因此实现上仍必须先做显存过滤，再把剩余候选整体传给 V4b。

### 4.13 第十二步：输出吞吐和排序

```text
predicted_tps_i = exp(log(T_hat_i))

predicted_step_seconds_i
  = effective_tokens_per_step_i / predicted_tps_i
```

最终可输出：

```json
{
  "request_id": "candidate-001",
  "predicted_effective_tokens_per_second": 20879.6,
  "predicted_step_seconds": 3.4777,
  "rank_within_group": 1
}
```

## 7. 可直接照着实现的伪代码

```python
safe_candidates = []

for request in raw_candidates:
    normalized = normalize_request(request)
    geometry = resolve_model_geometry(normalized)

    # physical-shares
    components = analytic_memory_components(
        normalized,
        geometry,
    )
    analytic = sum(components.values())

    memory_x = mechanism_features(normalized, geometry)
    memory_x += component_shares(components, analytic)
    memory_z = (
        memory_x - memory_model.means
    ) / memory_model.scales

    delta = (
        memory_model.intercept
        + dot(memory_z, memory_model.beta)
    )
    center = analytic * exp(delta)

    success_q95 = select_conformal_tail(
        normalized,
        memory_tail,
    )
    oom_guard = select_exact_oom_guard(
        normalized,
        memory_tail,
    )
    p95 = center * exp(max(0, success_q95, oom_guard))

    if p95 <= 0.95 * h800_capacity:
        safe_candidates.append({
            "normalized": normalized,
            "geometry": geometry,
            "memory_center": center,
            "memory_p95": p95,
        })


v4b_candidates = []

for candidate in safe_candidates:
    work = static_dataset_work_per_step(
        candidate["normalized"],
        dataset_profile,
    )
    physical_proxies = build_flops_traffic_communication(
        candidate["normalized"],
        candidate["geometry"],
        work,
        h800_hardware,
    )
    x70 = build_v4b_features(
        candidate["normalized"],
        candidate["geometry"],
        work,
        physical_proxies,
    )

    z_abs = (x70 - abs_head.means) / abs_head.scales
    log_step = abs_head.intercept + dot(z_abs, abs_head.beta)
    a = log(work.effective_tokens) - log_step

    z_rank = (x70 - rank_head.means) / rank_head.scales
    r = dot(z_rank, rank_head.gamma)

    v4b_candidates.append({
        **candidate,
        "work": work,
        "absolute_log_tps": a,
        "rank_score": r,
    })


for group in group_by_user_scenario(v4b_candidates):
    a_bar = mean(row.absolute_log_tps for row in group)
    r_bar = mean(row.rank_score for row in group)

    for row in group:
        log_tps = (
            a_bar
            + 0.25 * (row.absolute_log_tps - a_bar)
            + 0.75 * (row.rank_score - r_bar)
        )
        row.predicted_tps = exp(log_tps)
        row.predicted_step_seconds = (
            row.work.effective_tokens / row.predicted_tps
        )

recommendations = {
    group_id: max(
        group,
        key=lambda row: row.predicted_tps,
    )
    for group_id, group in group_by_user_scenario(
        v4b_candidates
    ).items()
}
```

## 8. 当前实现需要特别注意的边界

### 8.1 physical-shares

1. 当前主要适用于 H800 稠密文本模型。
2. Qwen3-VL 上已经出现严重低估，不能直接用于 VL。
3. `packing` 目前没有进入 28 维中心特征，只进入尾部 selector；packing 也不属于主要验证域。
4. `dataset_id` 和真实长度分布不进入显存中心，只有 cutoff 作为长度尺度。
5. P95 可能偏保守，安全候选可能全部被过滤掉。
6. 若成功 q95 无法从 selector、mode×GC 或 pooled 中取得，必须返回 unavailable。

### 8.2 V4b

1. 必须传入同一场景的完整安全候选集合。
2. 不能把 rank score 直接当 token/s。
3. 必须使用预运行静态数据集画像，不能使用运行后计数器。
4. `dataset_id` 必须存在对应画像文件。
5. 当前冻结 V4b 是 H800 模型，不应直接跨卡型使用。
6. 当前 artifact 中 V4b 仍被记录为 two-head challenger，并非统一 `ThroughputPredictor` 的默认模型。
7. 当前统一 `ThroughputPredictor` 默认使用 V5；H800 V4b 的正式回放通过内部 helper 组装输入并调用冻结 V4b。

### physical-shares

```text
训练配置
  → 九类解析显存
  → 解析总量
  → 19个机制特征 + 9个分量占比
  → 标准化 Ridge 预测倍率残差

  → operational P95
```

### V4b

```text
显存安全候选
  → 静态数据集 token 画像
  → 每 optimizer step 工作量
  → FLOPs/HBM/通信代理量
  → 70维特征
  → absolute head 得到绝对 log TPS
  → rank head 得到相对排序分数
  → 25% absolute 偏移 + 75% rank 偏移
  → 最终 token/s 和候选排序
```
