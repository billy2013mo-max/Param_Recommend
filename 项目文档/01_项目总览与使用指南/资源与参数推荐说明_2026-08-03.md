# SFT 资源与参数推荐说明：逻辑、现状与计划

> 日期：2026-08-03　适用：`Param_Recommend`
> 当前发布状态：**`shadow_only`** —— 可离线回放与影子验证，不允许自动发起训练。

---

## 1. 我们在解决什么

用户提交一个 SFT 任务，需要回答：**几张什么卡、ZeRO 几、开不开 GC、MBS 多大、cutoff 多少、要不要 packing。**

现状是靠人拍或试跑：配置不合理导致吞吐极低，或者直接 OOM 白跑一轮。

目标：**在训练效果约束不变的前提下**，自动给出「最小可行资源下预计训练时间最短」的方案。

这里有一条决定项目边界的前提：**训练语义不能变**。模型、数据、epoch、LR、LoRA rank、GBS 全部由用户固定，我们只动 MBS / GA / ZeRO / GC / 卡数这些**不影响收敛结果**的旋钮。

所以我们优化的是「同一次训练怎么跑得更快」，不是「换个配方效果更好」。这条守住了，推荐才是安全的。

---

## 2. 整体流程：静态定型 → 联合搜索

```
用户固定：模型 / 训练类型 / 数据集 / epoch / LR / LoRA rank / GBS
   │
   │  ── 阶段一：静态分析（不碰 GPU）──
   │  tokenize 数据集 → 长度分布 P50/P90/P95/P99/max
   │  cutoff_len = max 向上取整到 512 的倍数
   │  模拟 neat-packing on/off → 决定是否开 packing
   │  → 输出唯一 DataPlan，此后 cutoff 与 packing 不再进入搜索
   │
   │  ── 阶段二：联合搜索 ──
   │  搜索空间 = 卡型/卡数 × ZeRO(0/1/2/3) × GC(on/off) × MBS(1/2/4/8/16)
   │  约束：非 packing 时 MBS ≤ GBS / DP；GA 由 GBS 派生，不独立搜索
   ▼
显存模型逐候选算 P95 → 过滤掉会 OOM 的
   ▼
吞吐模型在「剩下的安全候选集」上排序
   ▼
选最小可行卡数内吞吐最高的方案
```

Packing 静态决策规则：保守节省 ≥15% 且 pack 利用率 ≥90% → 开；最大节省 ≤5% → 关；5~15% 之间默认关。

**为什么 cutoff 和 packing 必须先静态定死？** 它们改变的是「工作量本身」（token 总数、有效 token 率、样本语义），不是执行方式。混进联合搜索会让候选之间失去可比性——你没法说「packing 的 A 比不 packing 的 B 快」，因为两者在做不同的事。

## 3. 显存模型 physical-shares：判断能不能跑

核心是两层：**物理解析骨架 × 数据驱动的倍率修正**。

**第一层：解析基线（纯物理，零拟合）**

按 ZeRO stage 分片模型状态（常量：param 2B、grad 2B、optimizer 12B/参数）：

| stage | parameters | gradients | optimizer |
|---|---|---|---|
| 0 | 全量 | 全量 | 全量 |
| 1 | 全量 | 全量 | ÷N |
| 2 | 全量 | ÷N | ÷N |
| 3 | ÷N | ÷N | ÷N |

激活部分，令 `per_token_layer = 6·hidden + 2·kv_width + 3·intermediate`：

- **GC 开**：只存层边界 `mbs·seq·layers·hidden·2`，加一份单层重算工作区
- **GC 关**：每层全存 `mbs·seq·layers·per_token_layer·2`

这两行就是 GC 的全部物理含义：把 `layers × per_token_layer` 换成 `layers × hidden`，省几十倍，代价是多一份单层工作区。

再加 attention 工作区、logits 工作区（保守取全 logits）、ZeRO 通信桶、ZeRO-3 live 参数。九项相加得 `M_analytic`。

**第二层：28 维残差回归**

学的不是显存，而是**解析值差多少倍**：

```
拟合目标   y = log(M_observed / M_analytic)
中心预测   M_center = M_analytic × exp(β₀ + zᵗβ)
```

28 维 = 19 个机制/规模/交互项 + **9 个解析分量各自的占比**。

后 9 维是模型名字的来源，也是它的核心洞见：同样 100 GiB 解析值，「激活主导」和「优化器状态主导」的真实偏差方向完全不同（激活多时 allocator 碎片更多）。占比特征让回归器对不同**结构成因**给不同修正——纯配置特征做不到这件事。

**安全上界**

```
M_p95 = M_center × exp( max(0, q95_success, oom_guard) )
准入条件：M_p95 ≤ 0.95 × 容量　（H800 ≈ 132.84 GiB）
```

两个细节值得注意：

- `q95_success` 用 **leave-scenario-out 的 out-of-fold 残差**取 conformal 分位。用 in-sample 残差会系统性低估尾部。
- `oom_guard` 利用 OOM 的**右删失信息**——OOM 不告诉你真实峰值，但告诉你「至少超过某个界」。降级层级刻意不对称：成功尾部可以从精确 selector 降到全局池，**OOM guard 只用精确 selector、绝不降级**，避免一个配置的 OOM 污染无关配置。

## 4. 吞吐模型 v4b：在安全候选里排序

**为什么要两个 head？** 绝对值准 ≠ 排序对。对推荐来说排序更重要：只要选对最快的那个，绝对值偏 20% 不影响决策。

先算 roofline anchor：

```
anchor = max(compute, kernel_hbm) + optimizer_hbm + collective + count×latency
```

`max(compute, hbm)` 表示计算与访存可重叠、取瓶颈那个；optimizer 和通信串行累加（保守假设不重叠）。

**absolute head**：`log(step) = log(anchor) + β₀ + xᵗβ`，只学「实际比 roofline 慢多少倍」。α=1，训练时设计矩阵同时含绝对行和同场景 pairwise 差分行（权重 0.25），所以本身已带弱排序意识。

**rank head**：`r_i = xᵗβ_rank`，**无截距**，只用同场景候选对的差分训练（`z_i − z_j → log T_i − log T_j`）。α=0.01，比 absolute 弱 100 倍——它不需要拟合绝对水平，只需解释组内差异，所以可以更激进。

**set-aware 融合**（λ=0.25）：

```
log(T̂ᵢ) = mean(a) + 0.25·(aᵢ − mean(a)) + 0.75·(rᵢ − mean(r))
```

绝对尺度由 absolute head 的组内均值锚定，组内差异 75% 交给 rank head。单候选时自动退化为 absolute head。

---

## 5. 两个必须记住的坑

**坑一：显存是逐样本的，吞吐是集合相关的。**

`mean(a)` 和 `mean(r)` 是对**当前候选集合**求的。所以顺序只能是「先显存过滤 → 再在剩余候选上重算融合」。

不能先算完 v4b 再删掉 OOM 候选——那样锚点里带着已被删除候选的影响，中心化也是错的。代码里 `candidate_set_contract` 字段就是在声明这个契约。

**坑二：两个模型的分层含义相反。**

- **显存**：物理骨架承担全部量级外推，回归只输出一个接近 1 的倍率。所以**骨架缺项会直接崩** —— VL 的 66.8% MAPE 是 `M_analytic` 本身算错了，回归器救不回来。
- **吞吐**：anchor 只是可选的残差起点，主体是学出来的。换架构时表现为回归系数外推失效，不是骨架崩。

## 6. 当前进度：吞吐达标，卡在显存

工程主线已封装为 `H800PhysicalV4BPredictor`（schema `.../v3`），选择策略固定 `minimum_admitted_gpu_count_then_v4b`：先最小化卡数，再在同卡数内优化吞吐。跨卡排名会输出但仅作诊断，`scale_out_enabled=false`。

**8/2 fresh prospective holdout（24 job，全 success）**

| 项目 | 结果 | 判定 |
|---|---:|---|
| false-safe OOM | 0 | 通过 |
| upper 总覆盖 | 23/24 = 95.83% | 勉强过线 |
| 场景等权 P05 upper coverage | **85.83%** | **显存 gate 失败** |
| center MAPE / P90 APE | 8.82% / 17.05% | 未达替换门 |
| v4b Hit@90% | 8/8 = 100% | **产品目标通过** |
| v4b worst regret | 8.16% | **≤10%，通过** |

唯一 upper miss：Qwen3-8B LoRA / 2GPU / ZeRO-2 / GC off / MBS=2 / cutoff 4096，预测 upper 89.08 GiB，实测 reserved 117.80 GiB。它最终没 OOM（离安全线还有 15 GiB），但 **28.72 GiB 的低估足以否决 formal acceptance——不能用「最后跑成功了」掩盖校准失败**。

根因定位得很清楚：allocated 头其实很准（MAPE 4.54%），异常的是实测 `reserved/allocated = 2.059`，而 24 条的中位数只有 1.109。数据画像给出结构解释——旧 multiturn 数据的 `E[batch 内最大长度]` 约 1493 tokens，新 education profile 约 2875 tokens。**当前 memory basis 只用 cutoff，没把动态 padding 压力当特征**，所以区分不了这两个分布。

**8/3 profile-aware v1 → final unseen holdout（10 job）**

按上述诊断做了 profile-aware 修正，28 条定向校准，校准内 LOPO MAPE 5.98%、upper coverage 100%。然后用两个**全新未见画像**做最终验收：

| 项目 | 结果 |
|---|---:|
| false-safe OOM / upper coverage | 0 / 10-10 = 100% |
| center MAPE | **66.00%（门槛 6%）** |
| P90 APE | **181.46%（门槛 12%）** |
| Qwen3-14B Full 切片 | 1.63% / 3.02% ✅ |
| Qwen3-8B LoRA 切片 | **108.91% / 264.83%** |
| 安全候选 admission recall | 9/10 = 90%，误拒 1 个 |

被误拒的那个：预测 center/upper = **272.02 / 430.82 GiB**，实测 **58.00 GiB**——而且它是那组里实测最快的配置。

**失效根因精确到项**：v1 reservation 头里 `risk×pressure²`、`risk×pressure³`、`risk×pressure³×log2(MBS)` 三项贡献了最终 reservation log 的 **89.6%**。校准数据的 padding pressure 最大 0.7020，新画像是 0.9999——三次项在校准域内拟合得很好，但**没有饱和、没有输出边界**，一外推就爆炸。这不是调大 ridge alpha 能解决的，是模型族的无约束外推。

**8/3 有界 v2（CPU-only 修复，今天冻结）**

结构收紧到一个 direct reserved 头、7 个变量：5 个执行机制桶 one-hot（桶键只由 `training_mode/gpu_count/zero_stage/GC/packing/MBS` 组成，**不含模型 ID 和数据集 ID**）+ 2 个严格落在 `[0,1]` 的画像量。**没有平方项、没有三次项、不再让两个回归校正相乘。** 全 `[0,1]` stress grid 上校正倍率范围 0.271~2.306，落在预先声明的 0.20~3.00 结构门内。未见的机制桶直接 `unseen_selector_bucket` fail closed。

对已消费的 10 条做只读诊断回放：

| 指标 | v1 | v2 |
|---|---:|---:|
| center MAPE | 66.00% | **8.91%** |
| P90 APE | 181.46% | **20.47%** |
| false reject | 1 | **0** |

那个爆炸的 case：v2 给 53.48 GiB，实测 58.00 GiB。

**但必须说清楚**：v2 的结构是**看到这 10 条结果之后**设计的，属于 `post-holdout repair candidate`。这批数据不能再当 release holdout。**「已知故障被修复」不等于「新画像泛化通过」。**

**一句话现状**：阶段 F 的显存定向修复循环中。v2 已冻结、已知故障已修复、正式泛化验收待新证据。吞吐 v4b 的低 regret 目标一直保持通过。

## 7. 其他几条线

**Qwen3.5 + TileLang（7/29 跑完）**：25 job，20 success / 4 OOM / 5 failed。5 个 failed 根因是 `CUDA illegal memory access`，逐个重跑后全部转 success。Qwen3.5 目前只能作相对排序诊断——吞吐绝对尺度有明显漂移。

**扩卡策略（8/1 审计，一次有价值的修正）**：重算发现有 **14 个**相邻翻倍配对，旧报告只呈现了 4 个——差异不是数据缺失，是旧代码只在配对两端恰好落入同一 CV 折时才计入。干净配对（2→4）实测比值：

| 数据分布 | 配对数 | 中位 | ≥1.8 |
|---|---:|---:|---:|
| short_512 | 3 | 1.824 | 2 |
| multiturn_4096 | 2 | 1.998 | 1 |
| longcontext_32768 | 3 | 1.572 | 0 |

**结论：1.8 阈值是可达的**，此前「天花板约 1.6」的印象来自只看 longcontext 切片。**数据长度分布才是扩卡效率的主导因素。** 但每个端点都只有单次运行、conformal 下界不可识别，所以只能用于实验设计定向，不能开 `scale_out`。

顺带一个对候选生成器有直接影响的机制发现：**14B LoRA + ZeRO-2 时，加卡几乎不降低每卡显存**——被分片的只有约 110M adapter 的梯度与 Adam 状态（合计 1.23 GiB，2 卡每卡仅省约 0.6 GiB），而 27.51 GiB base weights 在每个 rank 上完整复制。所以候选生成器在 LoRA + ZeRO-2 路径上**不能假设扩卡自动放宽 MBS 上限**，只有 ZeRO-3 才分片 base weights。

**VL**：独立支持轨道 V1-VL，不并入首期 Dense V1。8/1 有一次自我推翻：此前「视觉塔权重解释 1.9× 显存缺口」的猜想被算术证明否掉了—— `actual_parameters` 对 VL **已包含视觉塔**（8,767,123,696 − 576,388,336 = 8,190,735,360，与训练日志 Full 的 trainable 完全相等）。dense 骨架早就把那 1.07 GiB 算进去了，17.3 GiB 的缺口几乎全部来自视觉激活、workspace 和 gather 行为。**在显存 basis 里新增视觉权重项会重复计算**，已加 `double_counting_guard`。

**Packing**：目前只生成 shadow candidate，未进入正式显存和吞吐排序。现有 10 个配对点同时参与过阈值制定，不算独立泛化证据。

**一个未解的治理问题——硬件身份**：容器上报 NVIDIA H200（driver 580.82.07），历史 `hardware.json` 声明 H800。显存、SM 数（132）、compute capability（9.0）几乎完全一致，只有 SKU 名不同，负责人已口头确认是 H800。但 1623 条历史观测里 526 条 run-bound 的 8 个 UUID 与当前 4 张卡**零重叠**。两种解释（驱动报错 / 真换过硬件）无法从数据判定。处置是**不改 `hardware.json`、不放宽 predictor 校验**（两者都会破坏防篡改根），而走一次显式授权的硬件身份断言，留下「谁在何时基于什么断言放行」的可追溯记录。

## 8. 为什么还没上线

| 门槛 | 要求 | 当前 |
|---|---:|---|
| prospective P95 coverage | ≥95% | 场景等权 85.83% ❌ |
| false-safe OOM | 0 | 0 ✅ |
| top-1 regret | ≤10% | worst 8.21% ✅ |
| 每个可推荐卡数的安全候选数 | ≥2 | 很多场景只有 1 个 ⚠️ |
| 扩卡收益 | 预测与实测下界均 ≥1.8× | 下界不可识别 ❌ |
| 绝对 tokens/s | 需独立尺度验收 | `absolute_scale_trusted=false` ❌ |
| runtime fingerprint | 完整绑定 | 硬件身份断言未产出 ⚠️ |

**吞吐的产品目标（选对配置）已经达标，整条链路卡在显存的安全覆盖率上。**

## 9. 下一步：21 次最小严格验收

不再调已揭盲的回放，先离线冻结一批从未进入 v2 设计与拟合的新画像：

1. **3 个互相独立的未使用文本画像**：rare-tail short、broad non-truncated longtail、concentrated/truncated long —— 分别检验最大长度项、fragmentation 项、截断抵消项
2. 每个画像跑当前 5 个精确支持桶 = **15 次**
3. **3 个 Qwen3.5-4B LoRA 同机制 cross-scale 点** —— 检验「物理锚点管模型量级、校正头只管执行机制与画像」这个迁移假设
4. 每画像 1 个 tail-forced 的 8B LoRA 安全点 = **3 次**，验证随机 13-step 测量可能遗漏的长度尾部

新 acceptance contract 必须在看 GPU 结果**之前**冻结。主门是 false-safe=0、场景等权 upper coverage、admission recall；center 误差降为次门。原来的 6% MAPE / 12% P90 是 v1 的高精度替换门，**不能在看完结果后静默放宽**——若要按产品目标调整，必须在新 design 里显式版本化并说明理由。

## 10. 这个项目真正的方法论

模型结构本身不是最值得讲的，这套不骗自己的纪律才是：

**能推导的必须解析算，实验只校准硬件与实现造成的效率、workspace、碎片和尾部风险。** 好处是量级外推由物理保证，回归只需学一个接近 1 的倍率。

**模型名和数据集名不能作为系数键。** 否则就是查表，不是建模。所以 v2 的桶键只由执行机制字段组成。

**冻结-验收纪律**：预测必须在看结果前冻结；holdout 消费一次就不能复用；看到结果后改出来的模型只能叫 repair candidate。8/3 那次正是靠这条纪律才暴露了 66% 的失效——如果允许回灌，v1 会带着一个隐藏的外推炸弹上线。

**外推必须有界。** v1 的教训不是「正则不够」，而是三次交互项在校准域外没有饱和。v2 的应对是 `[0,1]` 画像量 + 预先声明的倍率门 + 未见桶 fail-closed。

**失败要归因到机制，不加黑盒倍率。** `reserved/allocated = 2.06` 异常 → 定位到 batch padding 压力 → 补画像特征。而不是给这个配置打一个补丁系数。

**自我推翻要留痕。** 视觉塔猜想被算术推翻、扩卡「天花板 1.6」被重算修正——两处都在文档里明确标注了原判断与修正过程，而不是悄悄改掉。
