# 通用 SFT 参数配置模型实验与建模计划

日期：2026-07-31  
状态：CPU 契约、fresh holdout、profile-aware 定向校准和 final unseen 验收均已完成；v1 显存 challenger 因 8B LoRA 外推失效被拒绝，阶段 F 已冻结 post-holdout 有界 v2 修复候选并完成诊断回放，但仍等待全新 prospective holdout；v4b 低 regret 目标保持通过，`scale_out_enabled=false`，不自动启动训练  
适用项目：`Param_Recommend`

## 1. 目标与结论先行

本计划的目标是把当前的静态 Packing、H800 `physical-shares` 显存模型和
`v4b` 吞吐排序模型，收敛成一个能够迁移到**新模型和新数据长度分布**的通用
SFT 参数配置模型。

目标不是为每个模型或数据集拟合一个倍率，而是建立以下统一链路：

```text
模型结构 + 训练配置 + 数据长度分布 + 硬件/runtime
                         ↓
                 Unified WorkloadProfile
                         ↓
          ┌──────────────┼──────────────┐
          │              │              │
   physical-shares   v4b 同卡数      cross-card
      显存头          吞吐排序头       ratio head
          │              │              │
          └──────────────┴──────────────┘
                         ↓
              候选搜索、风险门控与推荐
```

核心原则：

1. 能由模型结构、ZeRO 语义、数据长度和计算图推导的量，必须解析计算。
2. 实验只校准硬件/软件实现造成的效率、workspace、碎片、重叠和尾部风险。
3. Packing 不是一个全局显存/吞吐倍率，而是改变统一工作量画像的一种执行机制。
4. 模型名称和数据集名称不能直接作为可复用系数键。
5. 历史回放只能用于建模和诊断；发布必须依赖冻结后的独立 prospective holdout。
6. 任何超出已验证支持域的请求都必须降级或 fail-closed，不能静默外推。

## 2. 当前基线与已知问题

当前工程已经具备：

- H800 `physical-shares` 显存预测与安全上界；
- H800 `v4b` 相对吞吐排序；
- 静态 token 长度分析与 neat-packing 模拟；
- DeepSpeed/训练运行证据、execution fingerprint 和审批闸门；
- 历史 H800 结果恢复、场景级交叉验证和候选实验矩阵；
- Qwen2.5/Qwen3/Qwen3.5 的部分泛化回放。

当前不能直接宣称通用模型，原因包括：

- Packing `on` 目前只能生成 shadow candidate，尚未进入统一 H800 Predictor 的正式显存和吞吐排序；
- Packing 现有 10 个配对点同时参与过阈值制定，不是独立泛化证据；
- 旧 `h800_theory_calibration.json` 的 P95/false-safe/regret 确实未达到门槛，但它是
  `theory_only / bootstrap / nonpublishable`，不是当前服务 Predictor 使用的 challenger；
- `h800_evidence_gap.json` 中的 11 个 gap 也属于这条旧 theory-only 证据链，不能直接当成
  当前 challenger 的 11 个精度缺口；当前服务真正的发布阻塞是 frozen 后缺少 fresh
  prospective acceptance（以及相应的 runtime/legacy 治理项）；
- 当前 challenger 在已查看的 calibration/holdout 上数值上已达到现行门槛：显存 scenario-equal
  P95 coverage 约 96.58%（selected nested LOOCV aggregate 99.11%、同一 native holdout 96.67%）、
  false-safe OOM 为 0，v4b selected calibration top-1 regret 约 0.17%、`joint_two_head`
  holdout top-1 regret 约 1.57%；但该 holdout 不是冻结后新鲜 prospective acceptance，仍不能发布；
- 当前显存和吞吐分别有 retrospective 结果，尚未用一组冻结后的混合风险候选完成端到端联合验收；
- 当前跨卡策略仍是 `minimum_admitted_gpu_count_then_v4b`，`scale_out_enabled=false`，没有经过
  独立验收的 1.8× 相邻翻倍 ratio head；因此不能把“能放下的最小卡数”自动改成扩卡推荐；
- 很多场景每个 GPU 数只有一个安全候选，吞吐排序没有足够的比较对象；
- Qwen3.5 的吞吐绝对尺度存在明显漂移，只能作为相对排序诊断；
- 缺少可信的逐 operator/module manifest 时，ZeRO-3 live-parameter 上界只能保守估计；
- 历史证据仍有 legacy/runtime fingerprint/独立 native-v2 anchor 等发布阻塞项；
- 新模型和新数据分布的验证还没有按结构和长度统计特征建立独立 holdout。
- VL 目前只能作为独立支持轨道：Qwen3-VL 的现有 18 个独立端点为 14 个 success、4 个
  OOM，全部是 H800、2 卡、`multiturn_4096`、纯文本输入、cutoff 4096、packing off；
  因此它验证了“当前 Dense 显存骨架不能覆盖 VL”，没有验证真实图片输入。
- 当前 Qwen3-VL Full runtime manifest 显示总参数约 8.767B、可训练参数约 8.191B，
  视觉塔约 576M 且冻结。这个比例是该模型/配方的 runtime 事实，不能由 `train_type=full`
  推导，也不能泛化到所有 VL 配方。

因此，本计划首先冻结并升级已有 schema，另建单独审批的 campaign；不恢复旧队列，
不覆盖现有 artifact，也不 fork 出平行 WorkloadProfile/ModelManifest。

## 3. 首期支持域和非目标

### 3.1 首期支持域（V1）

首期先保证以下范围内的可解释泛化：

- GPU：H800，单机 1/2/4 卡；8 卡作为后续扩展；
- 精度：BF16；
- 模型：Dense Transformer，优先 Qwen2/Qwen3/Qwen3.5，随后增加一个非 Qwen Dense 家族；
- 训练：普通 SFT，Full 和 LoRA；
- ZeRO：单卡 stage-0， 多卡 ZeRO-2/ZeRO-3，必要时补 ZeRO-1；
- MBS：1、2、4、8、16；
- cutoff：512、2048、4096、8192、32768；16384 只有在 Predictor 和静态 Packing policy
  的支持域完成显式对齐后才加入 V1；
- Packing：neat-packing on/off，物理 MBS=1；
- runtime：固定且有 fingerprint 的 FA3/Liger/CCE/DeepSpeed 路径；
- 数据：short、multiturn、longtail、longcontext 等文本长度分布。

### 3.2 明确暂不纳入 V1

- VL/多模态模型；
- MoE；
- DPO、ORPO、KTO、RFT 等非普通 SFT；
- 多机训练；
- CPU optimizer/parameter offload；
- FP16/FP32 等非 BF16 主路径；
- 任意 GPU 之间直接复用 H800 系数；
- 真实训练时在线拟合或自动修改生产系数。

这些不是永久不支持，而是必须拥有独立的结构模型、runtime selector 和验收集。

### 3.2.1 VL 专项支持轨道（V1-VL，不并入首期 Dense V1）

VL 不应直接套用 Dense 的显存和吞吐系数，也不应因为已有一个 VL 模型 ID 就生成安全
推荐。V1-VL 先作为独立、可回滚的支持轨道；在该轨道通过 fresh prospective 验收前，
VL 请求最多返回 `conservative_fallback`/shadow candidate，且
`automatic_execution_allowed=false`。

当前代码和证据的事实口径如下：

- `inventory_models.py::_geometry_config()` 只提取语言塔；`model_inventory.json` 已有
  `model_type`、`family` 和 `architectures`，但没有导出视觉塔结构字段。当前 9 个 inventory
  条目并非全是 `Qwen3ForCausalLM`，不能把“没有 vision fields”写成“无法识别 VL”。
- `h800_physical_v4b_predictor.py` 的 `_is_vision_language()` 负责识别，
  `_support_assessment()` 才负责把未校准 VL 标为 `unsupported`；当前实现是三级 lattice，
  `generic_structural`/`conservative_fallback` 需要作为产品策略补充，而不是把 unsupported
  变成自动放行。
- `static_packing_predictor.py` 已对非文本请求返回
  `multimodal_packing_not_supported`；VL packing 在有独立 processor/collator 和 ABBA 证据
  前保持显式 `off`。

V1-VL 工作拆分：

| 轨道 | CPU-only 可完成 | 必须 GPU 佐证 |
|---|---|---|
| 结构 | 采集 raw `vision_config`、规范化视觉层数/patch/merge/temporal 字段；统计唯一视觉参数；建立 component-level freeze/LoRA manifest | 参数驻留、ZeRO-3 gather/live 行为和解冻组件的真实显存影响 |
| 画像 | 统一 image count、分辨率/像素上下界、`image_grid_thw`、视觉 token、文本 token、截断和不确定性字段；复用并提升现有 VL profiler | 真实 processor/collator、视觉 encoder、动态分辨率和多图路径确实执行 |
| 显存 | **不要**新增视觉权重常驻项（整 checkpoint 参数量已含视觉塔，见 §16.9，会重复计算）；需要新增的是视觉激活、merger/projector 激活、多模态 workspace 与 ZeRO gather 行为的解析 basis；旧 18 端点只做诊断回放 | 新图片输入下的显存系数、MBS 增长、OOM 右删失和 P95 安全上界 |
| 吞吐 | 增加视觉 FLOPs/token、图像数、视觉/文本工作量和任务指标定义；现有 v4b 只作初始排序头 | 真实图片输入下的绝对尺度、排序和跨卡 ratio |
| 支持域 | 输出 `required_experiment_family`、fallback reason、`visual_path_observed` | prospective false-safe OOM=0、P95 coverage、端到端推荐验收 |

已有 text-only holdout 中，VL Full 的 v5 吞吐 MAPE 约 3.00%，但只有 4 次成功、2 个
配置、1 个候选对；VL LoRA 的 pairwise 为 100%、Top-1 regret 为 0，但绝对 MAPE 约
72.7%。这些数字可以作为“先复用排序头”的依据，不能作为真实图片 VL 的发布证据。

视觉塔权重不能被写成 1.9× 显存缺口的主要解释：Qwen3-VL MBS1 的测量缺口约 17.3 GiB，
576M BF16 参数约 1.07 GiB；视觉激活、临时 workspace、参数聚合和 allocator 行为仍需
实测拆分。旧报告中的“视觉塔猜想”应保留为待验证假设，而不是定量结论。

**2026-08-01 更新（§16.9 已给出算术证明）**：该猜想现已被**推翻**，不再是待验证假设。
`model_inventory.json` 的 `actual_parameters` 是整 checkpoint 计数，对 VL
**已经包含视觉塔**（`8,767,123,696 − 576,388,336 = 8,190,735,360`，与训练日志中 Full 的
trainable 完全相等）。因此 dense 骨架早已把那 1.07 GiB 计入，缺口几乎完全来自视觉激活、
workspace 与 gather 行为。**在显存 basis 中新增视觉权重项会重复计算**；见
`vision_tower_structure.py` 的 `double_counting_guard`。

注意：当前 H800 Predictor 的实际 `SUPPORTED_CUTOFF_LENS` 为
`{512, 2048, 4096, 8192, 32768}`，不包含 16384；静态 Packing policy 的释放域
则使用最大 16384，且当前释放域比 Predictor 窄（只覆盖有限的 LoRA/model 组合）。两者
在发布前必须统一，不能仅在计划中声明支持 16384，或把静态 policy 的少量证据当成通用
Packing 支持。

### 3.3 跨卡资源推荐策略

V1 不再只返回“最小安全卡数”。在用户允许扩卡且候选处于支持域时，采用相邻翻倍的
保守扩卡策略：

```text
先找到当前最小安全卡数 N
在 N 和 2N 上分别找到最优安全候选
若 lower_throughput(2N) / upper_throughput(N) >= 1.8
    则推荐扩到 2N，并继续检查 2N -> 4N
否则停止扩卡，保留 N 作为推荐
```

这里的 1.8 是吞吐**比值**，即相对前一档提升至少 80%，不是 1.8% 或 70% gain。
V1 采用强扩展定义：同一业务请求固定 `target GBS`、cutoff、数据画像和训练语义，
只允许通过 MBS/GA/ZeRO 等合法配置改变卡数；如果业务希望随卡数增加 GBS，必须另建
weak-scaling 模型，不能与本规则混用。

#### 3.3.1 现有扩卡证据基线（2026-08-01 审计）

`scripts/audit_scaling_pair_evidence.py`（只读诊断，产物
`artifacts/scaling_pair_evidence_audit.json`）直接从 canonical observations 重算了
相邻翻倍配对。结论修正了此前"只有 4 个配对、全部 longcontext LoRA"的印象：

- 30 个 `scale-*` 运行覆盖 12 个场景，可支持 **14 个**相邻翻倍配对；
  旧 `h800_theory_calibration.json` 只呈现了 **4 个**。差异不是数据缺失，而是
  `_scaling_pairs()` 只在配对两端点恰好落入同一 leave-one-scenario-out 测试折时才计入，
  且每个卡数只保留一个候选；
- 按数据分布：`short_512` 6 个、`longcontext_32768` 5 个、`multiturn_4096` 3 个；
  按训练类型：LoRA 10 个、Full 4 个。**Full 与短/中长度分布的配对此前完全没有进入统计**；
- 其中 8 个是干净扩卡（两端 ZeRO stage 相同），全部为 2→4；另外 6 个在 1→2 时
  同时从 `zero=none` 切到 `zero2`，混入了引入分片通信的代价，只能作为诊断。

干净配对（2→4）的实测比值：

| 数据分布 | 配对数 | 最小 | 中位 | 最大 | ≥1.8 |
|---|---:|---:|---:|---:|---:|
| `short_512` | 3 | 1.448 | 1.824 | 1.933 | 2 |
| `multiturn_4096` | 2 | 1.792 | 1.998 | 2.204 | 1 |
| `longcontext_32768` | 3 | 1.567 | 1.572 | 1.573 | 0 |
| 合计 | 8 | 1.448 | 1.682 | 2.204 | **3** |

由此得到三条结论，直接影响阶段 H 的规模：

1. **1.8 阈值是可达的，保持不变。** `qwen3_8b/full/multiturn_4096` 达到 2.204，
   `qwen3_14b/lora/short_512` 达到 1.933，`qwen3_8b/lora/short_512` 达到 1.824。
   此前"实测天花板约 1.6"的印象来自只看 longcontext 切片。
2. **数据长度分布是扩卡效率的主导因素。** `longcontext_32768` 三个配对紧密聚集在
   1.567～1.573 且无一达标，`multiturn_4096` 中位 1.998。因此 ratio head 必须以
   WorkloadProfile 的长度/attention-pair 特征为输入，1.8 不能按卡数一刀切地
   预判通过或失败。
3. **当前证据仍不足以发布。** 全部 14 个配对的每个端点都只有单次运行
   （`every_usable_pair_rests_on_single_run_endpoints`），conformal 下界不可识别
   （`conservative_ratio_lower_bound_not_identifiable`），且没有一个是冻结后的新鲜
   观测。因此这批数字只能用于实验设计定向，不能用于开启 `scale_out`，也不能
   充当阶段 H 的验收集。

审计还发现两个方向异常（在 `N` 卡 success 而 `2N` 卡 OOM）。经
`scripts/diagnose_scaling_oom_direction.py` 逐条归因，**两个都有物理解释，没有真正的标签
冲突**（`label_conflict_candidate=0`），因此不需要 software/infra 三分类：

| 场景 | 转换 | 归因 | 处置 |
|---|---|---|---|
| `qwen3_14b/lora/multiturn_4096` | 1→2 | `configuration_confounded`：2 卡同时把 mbs 从 2 提到 4，激活随 mbs 线性增长，超过分片带来的节省 | 对其自身配置仍是有效边界证据 |
| `qwen3_14b/full/multiturn_4096` | 2→4 | `sharding_ineffective`：4 卡从 ZeRO-3 退到 ZeRO-2 且关闭 GC，被分片的量不足以抵消每卡成本 | 有效边界证据，但不能读作"加卡反而更差" |

关键机制（实测数字支撑）：14B LoRA 在 ZeRO-2 下，被分片的只有约 110M adapter 的
梯度与 Adam 状态（合计约 1.23 GiB，2 卡每卡仅省约 0.6 GiB），而 27.51 GiB 的 base
weights 在每个 rank 上仍然完整复制。因此对 LoRA + ZeRO-2，**加卡几乎不降低每卡显存**，
而提高 mbs 会线性增加激活。1 卡 mbs=2 实测 reserved 113.90 GiB（余量 25.93 GiB），
2 卡 mbs=4 与 4 卡 mbs=4 则分别只剩 2.04 / 2.15 GiB 余量后 OOM。

这条对显存模型有直接含义：**"加卡放松显存"只在被分片的量占主导时成立**。候选生成器
在 LoRA + ZeRO-2 路径上不能假设扩卡自动放宽 MBS 上限；ZeRO-3 才会分片 base weights。
扩卡必须同时满足：

1. N 和 2N 的候选都通过显存 P95/95% 容量线；
2. 两档都有至少两个可比较的安全候选，不能用单一候选定义该卡数的最优；
3. 跨卡吞吐比值使用已标定的 cross-card ratio/scale head，不能直接使用当前未信任的
   absolute throughput proxy；
4. 预测保守比值达到 1.8，且冻结后的独立实测比值的单侧置信下界也达到 1.8；
5. 预测区间重叠、候选不完整、运行机制越界或任一端点不安全时，停止扩卡并返回不确定原因。

从 N 到 2N 的每一步都要先在各自卡数完成显存门控和同卡数排序，再比较两档的
`best_safe_candidate`；如果 N 或 2N 没有至少两个安全候选，结果只能是
`insufficient_candidate_evidence`，不能用“唯一可运行候选”强行作扩卡依据。

推荐结果新增：

```text
minimum_admitted_gpu_count
recommended_gpu_count
scaling_steps[]: {from_gpu, to_gpu, baseline_candidate, expanded_candidate,
                  predicted_ratio, conservative_ratio_lower,
                  measured_ratio, passes}
scaling_stop_reason
selection_policy = thresholded_doubling_then_v4b
```

实现上把“卡数选择”和“卡内配置选择”拆成两层：

```text
admitted[N] = memory_gate(all_candidates_at_N)
N = first card count with admitted[N] >= 2
best[N] = v4b_rank(admitted[N])
for 2N in [2N, 4N, ...] while endpoint exists:
    if admitted[2N] < 2: stop(insufficient_candidate_evidence)
    ratio = cross_card_lower_bound(best[N], best[2N])
    if ratio < 1.8 or ratio is uncertain: stop(threshold_not_cleared)
    recommend 2N; N = 2N
```

这段逻辑只允许在候选已经过显存 gate 后运行；它不是“先按绝对吞吐挑一个可能 OOM 的
winner，再看是否扩卡”。

当前 `h800_physical_v4b_predictor.py` 的产品策略仍是
`minimum_admitted_gpu_count_then_v4b`，并明确 `scale_out_enabled=false`；本计划要求先
完成 cross-card ratio 验收，再单独开启该开关。`experiment.json` 当前使用
`minimum_throughput_gain_per_doubling=0.7`，与 1.8 比值规则不一致，必须改成显式的
`minimum_throughput_ratio_per_doubling=1.8`（或等价的 `gain=0.8`），禁止同时保留两个含义相近的字段。

### 3.4 业务覆盖与 Offload 决策

当前真实业务验证目录中有 5 个数据集，但最终输出只有 3 条推荐：2 个普通文本
SFT shadow recommendation，以及 1 个 Qwen2.5-VL 低置信度、支持域外的静态启发式
结果。偏好对任务和双图多标签任务不属于 V1 的普通 Dense 文本 SFT 支持域。
计划和产品报告必须显式展示这个覆盖率，不能把“未生成推荐”写成预测器故障。

部分 optimizer offload 是另一条真实业务路径。当前业务已经使用过
`offload_optimizer.ratio=0.4`，但 H800 memory/throughput model 没有表示 CPU Adam、
PCIe/CPU 传输、线程数或 overlap 的字段。本计划的 V1 决策是**不纳入 offload**：对含
`offload_optimizer`/`offload_param` 的请求返回 `unsupported_execution_mechanism`，不把
offload 配置静默当成 no-offload，也不生成安全推荐。若业务必须支持，再建立 V1.1 独立
offload track，单独标定 memory、CPU/PCIe overhead、吞吐和线程数，通过独立 holdout 后
再加入统一候选空间。在该 track 完成前，offload 不得消费 no-offload 的 calibrated profile。

## 4. 统一模型架构

### 4.1 ModelStructureManifest

冻结并统一现有 inventory/runtime manifest 为稳定版本的模型结构清单。至少包含：

- 唯一 tensor identity、shape、dtype、bytes；
- 参数所属 module/group；
- embedding、decoder block、attention、MLP、norm、LM head；
- hidden size、intermediate size、layer 数、attention heads、KV heads、head dim；
- vocab size、position embedding、最大上下文；
- tied weights；
- Full/LoRA 下 trainable/frozen 标记；
- LoRA rank、target modules、modules_to_save、额外 bias/embedding；
- modality、raw `vision_config` 和规范化视觉塔字段：`vision_depth`、视觉 hidden/intermediate、
  `patch_size`、`spatial_merge_size`、`temporal_patch_size`、`out_hidden_size`；不能假设所有
  模型都使用 `num_hidden_layers` 或 patch size 14；
- `vision_parameter_elements`、`projector_parameter_elements`、`merger_parameter_elements`，
  以 runtime 唯一 tensor identity 去重，避免 tied weights 或 merger 重复计数；
- component-level 的 `freeze_vision_tower`、`freeze_multi_modal_projector`、
  `freeze_language_model`，以及实际 `requires_grad` 聚合、LoRA target 是否命中视觉组件；
- `visual_path_observed`、processor/template identity 和 image/video 输入能力；
- 视觉模型若未通过对应 V1-VL 验收，必须显式标记 unsupported/fallback，而不是部分套用
  Dense 公式。

模型支持等级：

| 等级 | 条件 | 处理 |
|---|---|---|
| `exact` | 结构和 runtime inventory 完整，处于已验收覆盖域 | 使用校准 profile |
| `generic_structural` | 主体 Transformer 结构可识别，但缺少部分实现细节 | 使用保守上包络，仅影子/低置信度 |
| `conservative_fallback` | 只有总参数量和少量维度 | 小 MBS、GC、更多显存余量；不得宣称 calibrated |
| `unsupported` | 未通过对应支持轨道的 MoE/VL/未知算子或机制 | 不进入自动排序和自动执行 |

### 4.2 Unified WorkloadProfile

静态 Packing 模拟器和非 Packing 数据分析都必须输出同一个工作量契约。

建议字段：

```text
model_manifest_id
dataset_profile_id
cutoff_len
packing_enabled
logical_samples
physical_sequences
computed_tokens
effective_tokens
padding_tokens
attention_token_pairs
pack_utilization
mean_samples_per_pack
physical_mbs
gradient_accumulation_steps
micro_steps_per_optimizer_step
expected_gbs
expected_gbs_relative_error
length_p50/p90/p95/p99/max
runtime_mechanism_id
```

关键约定：

- 非 Packing 的 attention 计算量按动态 padding 后的真实 batch 形状计算；
- Packing 的 attention pairs 按每个 pack 内子序列的真实长度计算，不能统一替换成 `cutoff²`；
- `logical samples`、`physical sequences`、`computed tokens`、`effective tokens` 必须分开；
- Packing 后物理 MBS 固定为 1 时，不能将其误当作普通非 Packing MBS=1；
- GBS 是用户训练语义不变量，Packing 只能在相对误差和动态累积策略满足门槛时放行。

### 4.2.1 VL WorkloadProfile 扩展

VL 画像不是在文本字段后面简单追加一个总 token 数，而是要保留视觉、文本和任务
语义的可解释分解。统一 schema 至少增加：

```text
modality                         # image / video / mixed
task_family                      # causal_generation / multilabel_classification / preference
images_per_sample
videos_per_sample
image_resolution_p50/p90/p95/max
image_pixels_min/max
visual_tokens_per_image_p50/p90/p95/max
visual_tokens_total_p50/p90/p95/max
text_tokens
label_tokens
repeated_prompt_tokens
image_token_ratio
visual_text_token_ratio
image_processor_id/version
image_grid_thw_summary
temporal_frames_summary
processor_min_pixels/max_pixels
sampled_media_count
media_profile_confidence
```

现有 `real_business_validation_20260730/scripts/profile_business_vl_dataset.py` 可作为
Qwen2.5-VL profiler 的输入，但它使用 Qwen2.5-VL 的 `patch_size=14`、`merge_size=2`，
不能直接作为 Qwen3-VL 的通用公式。必须保留各代模型的 raw config 和 processor 版本，
并标记视觉统计是全量还是抽样估计。若支持视频，还要记录 temporal patch/frame 维度。

VL 任务要分别报告视觉编码工作量、重复 prompt 工作量、语言生成/label 工作量；
`effective_tokens` 不能把它们静默合并，否则会误判 qype19 这类“短 label、重视觉编码”任务。

### 4.3 RuntimeMechanismFingerprint

校准 selector 只允许引用真正改变执行机制的内容：

- GPU family、GPU topology；
- PyTorch、CUDA、NCCL、DeepSpeed、LLaMA-Factory；
- FlashAttention、Liger、CCE、Triton；
- dtype、optimizer、GC variant、torch compile；
- ZeRO bucket/prefetch/persistence/max-reuse；
- collective 类型、bucket 语义、overlap；
- Packing 实现版本和 processor/template；
- 相关环境变量。

模型、数据集、GBS 和单个模型名不能直接成为跨场景复用的 runtime key。

## 5. 数学模型设计

### 5.1 显存模型

统一形式：

```text
peak_memory
  = persistent_model_state
  + saved_activations(workload)
  + recompute_workspace(workload, GC)
  + logits_or_CE_workspace
  + zero_collective_workspace
  + framework_NCCL_workspace
  + allocator_fragmentation
```

其中：

- 模型状态按 Full/LoRA、dtype、ZeRO stage、卡数解析；
- 激活按 hidden/MLP/attention shape、computed tokens、attention pairs 和 GC 图解析；
- ZeRO-3 的逐 module 物化按可信 operator manifest 计算；缺失时使用明确的保守上界；
- OOM 是右删失不等式，只能约束需求大于可用容量，不能伪造 peak 标签；
- 实验只标定 activation liveness、workspace、allocator residual 和 P95 安全尾部。

#### 5.1.1 VL 显存分支

VL 分支增加以下解析项，并保留 component breakdown：

```text
vision_weight_state
projector_merger_state
vision_optimizer_state_if_trainable
visual_encoder_activation(images, visual_tokens, resolution, MBS)
multimodal_merge_activation(text_tokens, visual_tokens, image_count, MBS)
vision_kernel_workspace
multimodal_workspace
```

视觉塔冻结时不应进入 optimizer/gradient state，但其参数仍可能以 ZeRO 分片、all-gather
或 live-module 形式占用显存；“冻结 = 每卡没有参数显存”是不允许的简化。视觉塔解冻、
projector 解冻和语言侧 LoRA 必须使用 runtime manifest 的实际参数分组，不能由
`train_type` 推导。静态新增这些项属于 CPU 建模；具体系数、MBS 关系和 P95 仍需 GPU 校准。

physical-shares 的 residual selector 优先使用：

```text
GPU/runtime + dtype/kernel + train_type + ZeRO + GC + packing path
```

不得将 model_id/dataset_id 作为独立倍率键。

### 5.2 吞吐模型

统一形式：

```text
step_time
  = critical_compute_time(FLOPs, computed_tokens, attention_pairs)
  + communication_time(ZeRO, GPU_count, GA)
  + optimizer_time
  + input_pipeline_time
  + packing_overhead
```

v4b 继续以相对排序为主；绝对 tokens/s 和完成时间只有在另行通过尺度验收后才可发布。

吞吐模型必须显式使用：

- computed/effective token ratio；
- attention-pair 工作量；
- padding ratio、pack utilization；
- physical MBS 和 micro-step 数；
- ZeRO collective payload/count；
- GC 重算 FLOPs；
- Packing 与 cutoff/MBS/GC/ZeRO 的交互。

实验可校准的范围限制为：

- compute/memory efficiency；
- communication bandwidth/latency/overlap；
- input pipeline 和 Packing 整理开销；
- 有界 pairwise ranking residual。

#### 5.2.1 VL 吞吐分支

VL 吞吐至少分别建模：

- visual encoder FLOPs/时间；
- multimodal merger/projector FLOPs；
- language-side computed tokens 和 attention pairs；
- 图像数、视觉 token 数、分辨率/视频帧数；
- CPU media decode/resize、host-to-device 和 input pipeline 时间；
- causal generation、multilabel classification、preference optimization 的任务差异。

现有 Qwen3-VL text-only 结果只能验证“没有图片时”的条件排序。真实图片输入、不同
图片数量/分辨率和不同任务类型必须至少做小规模 paired calibration；不能因为 text-only
VL holdout 的 v2～v5 pairwise 结果为 100% 就跳过 VL 吞吐验证。绝对 tokens/s 仍需单独
尺度验收，qype19 等任务还应同时报告 samples/s 或 task-defined throughput。

### 5.3 跨卡相对吞吐模型

跨卡扩展不能直接使用当前 `absolute_scale_trusted=false` 的单点吞吐 proxy。
需要增加一个以同一场景的相邻卡数为单位的 ratio head：

```text
R(N, 2N) = throughput(2N, best_safe_candidate(2N))
           / throughput(N, best_safe_candidate(N))

recommend_scale_out(N -> 2N)
  iff lower_bound[R(N, 2N)] >= 1.8
  and measured_holdout_lower_bound[R(N, 2N)] >= 1.8
  and both endpoints pass memory admission
```

ratio head 的输入必须共享同一个模型、数据画像、GBS、cutoff、Packing 状态和
runtime mechanism，只允许改变 GPU 数以及随之变化的 ZeRO/MBS/GA 候选。它可以使用：

- 解析的计算、HBM 和 collective 工作量；
- N 与 2N 的通信 payload、ring factor、overlap 和 micro-step 数；
- 同卡数内 v4b 候选的排序结果；
- 配对实验得到的 log-throughput difference residual。

它不能用两个互不绑定的绝对吞吐预测值相除，也不能把预测 winner 但显存未放行的
候选用于扩卡比值。若同一卡数有多个安全候选，应先分别完成同卡数排序，再取每档
最优安全候选；若排序不确定，则扩卡结果也必须标记为 uncertain。实测比值以同一
场景下重复运行的有效吞吐（V1 默认 `effective_tokens/s`，同时保留
`computed_tokens/s`）估计，并记录中位数/均值、重复间方差和单侧置信下界；不能只
比较一次 run 的点估计。

跨卡需求的工作边界如下：

| 内容 | 性质 |
|---|---|
| 相邻翻倍候选配对、固定 GBS 的语义、显存 gate→卡内排序→ratio gate 的流程、1.8 阈值和输出字段 | 纯建模/工程实现 |
| ratio head 的通信/重叠残差、不同卡数的实际吞吐比值、1.8 阈值的通过/失败边界、预测下界覆盖率和 fresh claim 精度 | 必须 GPU 实验佐证 |
| 新 topology、Packing、offload、weak-scaling GBS | 各自独立实验，不能借用 no-offload/strong-scaling 的 ratio |

## 6. 实验分层与计划

实验必须按“先建模、再校准、后独立验收”执行。旧实验队列、旧 approval 和旧
candidate 不构成本计划的执行授权。

### 阶段 A：设计冻结与 CPU-only 实现

目标：不占 GPU，完成所有可以纯建模解决的缺口。

工作项（以抽取/合并已有实现为主，不新建平行 schema）：

1. 盘点并冻结已有 `sft_static_workload_profiles/v1`、runtime model manifest、
   support assessment 和候选生成逻辑，必要时抽取为公共模块；
2. 冻结 `ModelStructureManifest/v1`、`WorkloadProfile/v1`、`RuntimeMechanism/v1`；
3. 将静态 Packing Predictor 输出接到候选生成器；
4. 实现 Packing on/off 的共同候选空间；
5. 完成 attention-pair、token、GA、GBS 和 padding 的不变量测试；
6. 完善显存状态、激活、ZeRO、GC、通信和计算 basis；
7. 增加候选合法性检查、静态下界剪枝和边界 MBS 搜索；
8. 增加跨卡相邻翻倍候选配对、ratio head 和 `thresholded_doubling_then_v4b` 输出契约；
9. 定义支持域、fallback、OOD 和 confidence 输出；
10. 为新 schema、实验 campaign 和结果 artifact 生成独立 SHA 绑定。

阶段门槛：

- CPU-only 单元测试和 basis digest 全部通过；
- 任一模型结构无法解析时能正确降级；
- Packing on 不再直接被统一 Predictor 当成未知字段吞掉，而是形成显式 shadow candidate；
- 尚未有 GPU 校准的结果必须标成 `theory_only`/`shadow_only`。

#### 阶段 A-VL：CPU-only 结构与画像增量

这部分不启动 GPU，但不能把 CPU 回放当成发布验收：

1. 在现有 inventory/runtime manifest 上抽取视觉塔、projector/merger 和唯一参数统计，
   保留 raw config；Qwen2.5-VL、Qwen3-VL 使用各自的 patch/merge/temporal 语义；
2. 从 runtime `requires_grad` 聚合三个冻结 flag，并校验 LoRA target 是否实际命中视觉组件；
3. 将现有 VL profiler 提升为版本化 `WorkloadProfile`，记录图像/视频、分辨率、视觉 token、
   processor 版本、抽样置信度和任务类型；
4. **已完成（§16.9）**：视觉塔结构解析与 checkpoint 逐张量校验。注意结论修正 ——
   整 checkpoint 参数量已含视觉塔，**不得在显存 basis 中新增视觉权重常驻项**（会重复计算）；
   需要新增的是视觉激活、merger/projector 激活、多模态 workspace 与 ZeRO gather 的结构项，
   且系数必须标为未校准。这些项没有 GPU 证据无法定值，属阶段 I-VL-GPU；
5. 统一 VL support lattice：证据不足时输出 `conservative_fallback` 和
   `required_experiment_family`，但保持 `automatic_execution_allowed=false`；
6. 复用静态 packing 的显式 `multimodal_packing_not_supported`，VL packing 保持 off；
7. 用现有 18 个 VL 端点做 CPU 回放，报告 14/4 success/OOM、2/4 false-safe 和 6 条
   admission safety failure；该回放只用于诊断，不能作为 fresh acceptance。

### 阶段 B：预处理与运行时一致性 canary

目标：证明输入给数学模型的结构化工作量与真实训练路径一致。

检查项：

- tokenizer/template 处理后的长度与画像一致；
- 静态 greedy packing 与实际 processor 的 pack 数和利用率一致；
- packed batch 的 loss mask 正确；
- 跨样本 attention 隔离正确；
- 实际 computed tokens 和 attention pairs 与事件日志一致；
- 每个 rank 的 tensor/module inventory 一致；
- native-v2 execution fingerprint 完整；
- ZeRO-3 persistence/max-live module manifest 有可信来源。

VL 还必须增加：

- 真实 image processor/collator 与静态 `image_grid_thw`、视觉 token、placeholder 顺序
  和截断行为一致；不能只按图片 header 和固定公式估算；
- Qwen2.5-VL 与 Qwen3-VL 的 processor/template/config 版本绑定；
- 对图片数、动态分辨率、视频 temporal frames、多图顺序和 loss mask 做 CPU 校验；
- 运行时记录能证明视觉路径是否执行，纯文本 VL 运行不得标记为 visual-path evidence。

软件错误、数据错误和基础设施错误必须修复后重跑，不能作为 OOM 或不可行标签。

### 阶段 C：先结账已有跨卡排序实验

目标：在新 campaign 之前先关闭已经执行但未完成的 4 卡排序验收。

`qwen3_14b_4gpu_rank_validation_20260730` 中：

- `rank1_z3_gc_mbs16_ga2` 在 step 35 后 `exit_code=1`，没有完整结果，不能作为排序观测；
- `rank2_z2_gc_mbs8_ga4` 与 `rank3_z3_gc_mbs8_ga4` 均成功，但吞吐差距约 0.39%，低于
  预设的 3% tie threshold；
- `EXPECTED_RANKING.md` 要求小于 3% 时做反序复测。

因此先完成：

1. rank1 的成功重跑，并核对失败是否为 software/infrastructure failure；
2. 因为 rank2/rank3 小于 3% tie threshold，按 `EXPECTED_RANKING.md` 做必要的反序重复，
   尽量通过成对提交/复用运行上下文把新增重跑控制在 1～2 次；
3. 保留 GPU 空闲、温度、功率和 runtime fingerprint，生成正式的 4 卡 ranking closeout report。

该 closeout 不能用来拟合新系数，只用于关闭未结账证据和验证当前 cross-card 候选流程。

### 阶段 D：冻结 challenger 的小规模 prospective holdout

目标：优先验证实际服务链路上的 frozen challenger，而不是先把旧的理论校准数字
当成当前产品精度，也不是先重跑大规模显存边界。

冻结以下内容后采集约 20～30 个新运行：

- 只使用当前服务域：H800、BF16、Dense Qwen、Full/LoRA、无 offload、`packing=false`；
- 覆盖 1/2/4 卡；每个待推荐卡数至少两个显存安全候选；
- 至少包含一组显存边界点、一个 4 卡排序场景和若干同卡数吞吐候选；
- 加入 2～4 个同一场景的相邻卡数配对（1→2 或 2→4）作为扩卡收益的**新鲜观测**；
  若 ratio head 尚未冻结，这些观测只做诊断，不据此调参或自动开 `scale_out`；
- 模型、数据长度分布、GBS 和 runtime mechanism 至少有冻结后未见场景。

本阶段必须单独输出 `fresh_prospective_acceptance`，不能把先前看过的 native holdout
标作新验收。如果 memory、joint gate 和 regret 门槛通过，当前 challenger 可进入
validated-canary 候选，原先 40～80 次通用显存重标定不自动启动；如果失败，只根据
失败的 selector（模型结构、长度分布、卡数、runtime 或机制）定位补充实验，不能盲目
扩大矩阵。

### 阶段 E：Packing 机制校准

目标：标定 Packing 对显存、吞吐和训练语义的影响；该阶段与当前 frozen challenger
的无 Packing 发布验收分开。`static_packing_policy_v1.json` 已明确
`independent_holdout_points=0`、`is_abba=false` 且每个 treatment 只有一次运行；这 10 个
点只能作为 resubstitution 诊断，不能宣称泛化。

每个 family 固定模型、数据、GBS、cutoff、GPU、ZeRO、GC、dtype、optimizer，仅比较
Packing off/on。采用随机化 ABBA 顺序，至少三次重复。

建议初始 family：

| Family | 模型/训练 | 数据/长度 | 关键变量 |
|---|---|---|---|
| P1 | Qwen3-14B Full | multiturn，4096 | 2 GPU、ZeRO-3、GC、MBS=2 |
| P2 | Qwen3-14B Full | longtail，8192 | 2/4 GPU、MBS=1/2 |
| P3 | Qwen3-8B LoRA | short，512/2048 | 原 MBS=1/2/4 |
| P4 | Qwen3-8B LoRA | multiturn，2048/4096 | ZeRO-2/3 |
| P5 | Qwen3-14B LoRA | longtail，8192 | GC on/off |
| P6 | Qwen3-14B Full | short，512/2048 | 高原 MBS 的负收益边界 |
| P7 | 未参与校准的新 Qwen 规模 | 4096/8192 | 检查模型迁移 |
| P8 | 未见长度分布 | 与 P1 同模型 | 检查数据分布迁移 |

初始规模约为 8 个 family × 2 个 treatment × 3 次重复，即 48 个训练运行；若静态
模型已经明确某个方向不可能改变结论，可按预注册停止规则缩减。每次记录：

- reserved/allocated peak、OOM request 和 allocator 证据；
- logical samples/s、effective/computed tokens/s；
- attention pairs/s、step time、micro-step time；
- pack utilization、samples per pack；
- 实际 GBS 与目标 GBS 误差；
- loss mask、跨样本 attention 和训练 loss 语义检查。

Packing 自动开启门槛：

- 预期 GBS 相对误差 ≤5%；
- 无新增 false-safe OOM；
- 原 MBS=1 时保守收益 ≥10%；
- 原 MBS>1 时保守收益 ≥20%；
- 所有计划重复完整且没有语义错误。

未达到门槛的正向静态结果保持 `hold_off`，不能进入最终推荐；Packing 跨卡收益也要
等到阶段 G 的 ratio 规则单独验收，不能从单卡 ABBA 结果推导。

### 阶段 F：按 holdout 结果触发的显存边界校准

目标：只修复 prospective holdout 或 Packing ABBA 明确暴露的显存残差、workspace 或
尾部问题，而不是把旧 `theory_only` 的 0.9063 coverage 当成当前服务模型的失败。

触发条件至少满足一项：prospective false-safe OOM 非零、P95 coverage 未达标、残差在
某一机制/卡数集中，或 Packing workspace 没有可辨识证据。围绕预测安全线上下选点，
不重铺完整笛卡尔积。

建议变量：模型 Qwen3-8B/14B；Full/LoRA；ZeRO-2/3；GC on/off；MBS 1/2/4/8；
cutoff 2048/4096/8192；Packing on/off；GPU 1/2/4。每个 boundary family 优先获得
明显安全 success、接近 95% 容量线的边界点，必要时再做 success/OOM 夹逼。

不为了制造 OOM 强行运行 MBS=32/64；如果支持域内已有完整 MBS=16 success，该 family
可停止扩展。初始建议 12～16 个 boundary family、每个 2～3 个点、关键点 1～2 次
重复，预计 40～80 次；但只有 holdout 失败或残差不可辨识时才批准这部分。

### 阶段 G：同卡数吞吐与跨卡扩展校准

目标：在显存门控后的真实候选集合中验证 v4b 排序，并建立“相邻翻倍至少提升 80%才扩卡”
的 cross-card ratio head。**同卡数排序与跨卡扩展共享端点运行，但验收指标分开。**

#### G1. 同卡数候选排序

- 每个场景、每个可推荐 GPU 数至少提供 2 个、最好 3 个显存已放行候选；覆盖 MBS、
  ZeRO-2/3、GC、Packing（若已通过阶段 E）以及不同通信/计算瓶颈；
- 每个候选至少重复 2 次，接近候选或 tie threshold 内重复 3 次；
- 初始覆盖 8～12 个场景，优先 Qwen3-8B/14B Full/LoRA 与 short/multiturn/longtail/
  longcontext，固定 H800 BF16、无 offload；
- 指标为 scenario-equal pairwise accuracy、top-1 regret、Hit@90% 和 memory-gated
  safety failure。只有每个卡数至少有两个真实安全候选时，才计入正式排序验收。

#### G2. 相邻翻倍扩卡实验

每个 scaling family 固定同一模型结构、WorkloadProfile、target GBS、cutoff、Packing
状态和 runtime fingerprint，比较 1→2、2→4；4→8 留到 H800 八卡支持域单独验证。
第一轮先做 `packing=false`、无 offload 的服务域，Packing 或 offload 的扩卡结论不得从
无对应证据的 ratio 迁移。

实验设计要求：

0. 先读 §3.3.1 的审计基线，再定采样点。现有 8 个干净 2→4 配对已经覆盖
   `short_512`/`multiturn_4096`/`longcontext_32768` 三种分布，其中 3 个达标；因此本阶段
   不需要从零建立"1.8 是否可达"的证据，重点转为三件事：补 1→2 的**干净**配对
   （现有 6 个 1→2 全部混淆了 `none→zero2` 切换）、把单次端点补成可估下界的重复，
   以及冻结后采新鲜观测。已达标与未达标的 family 都必须保留；
1. 每个端点卡数先经过显存 gate，再在该卡数内完成 v4b 排序；用各自的
   `best_safe_candidate(N)` 和 `best_safe_candidate(2N)` 组成配对，不能拿显存未放行的
   理论 winner 充当端点；
2. 选择既有扩卡收益 ≥1.8 的 family，也有明确低于 1.8 的 family，避免只采集“会通过”的
   样本；至少 8～12 个 scaling family，覆盖模型规模、训练类型、长度分布、cutoff、
   ZeRO/GC 和计算/通信瓶颈。长度分布必须同时包含短、中、长三档：审计显示它是扩卡
   效率的主导因素（longcontext 中位 1.572 vs multiturn 中位 1.998），只采一档会得出
   与阈值无关的结论；
3. 1→2 的配对必须区分"加卡"与"引入 ZeRO 分片"两种效应。若该场景单卡必须
   `zero=none`、两卡必须 `zero2`，则该配对只能标为 `mechanism_confounded` 并单独报告，
   不得混入 ratio head 的干净残差；
4. 每个相邻转换的每档至少 2 个安全候选，端点重复至少 2 次；预测比值接近 1.8 或
   候选排序在 tie threshold 内时增加到 3 次，并采用随机化/反序执行；
5. 独占 GPU、记录温度/功率/空闲状态、runtime fingerprint 和 host interference，确保
   比值不是由批次顺序或共享机器噪声造成；
6. 每次记录 `effective_tokens/s`（V1 主指标）、`computed_tokens/s`、logical samples/s、
   step/micro-step time、attention pairs、allocated/reserved peak、通信 payload、
   overlap、MBS/GA/ZeRO、实际 GBS 和完整 attempt 状态；
7. 用重复运行的 paired log-throughput difference 估计 ratio，并给出点估计、方差和单侧
   95%/conformal lower bound。扩卡发布要求预测 lower bound ≥1.8，且独立新鲜测量的
   lower bound 也 ≥1.8；任何“不确定/区间跨阈值”均停止扩卡。

同卡数与扩卡端点尽量复用同一批运行。由于 §3.3.1 已从既有运行免费获得 8 个干净
2→4 配对，本阶段的增量重点是 1→2 干净配对、端点重复和冻结后新鲜观测，初始总量
下调为约 48～96 次（取决于场景数、候选数、中间 2 卡端点是否复用和停止规则），
不含阶段 C 的 4 卡 closeout 与阶段 D 的新鲜 holdout。

### 阶段 H：Offload 决策或独立 V1.1 track

本计划的 V1 决策是对 `offload_optimizer`/`offload_param` 返回
`unsupported_execution_mechanism`，并禁止静默当作 no-offload。若业务必须纳入，则另立
V1.1 campaign，至少覆盖 CPU Adam、offload ratio、PCIe/CPU topology、线程数、prefetch/
overlap、Full/LoRA、1/2/4 卡及边界 MBS；显存、吞吐和跨卡 ratio 都要重新做 paired
calibration 与 prospective holdout，不能只增加一个 offload 倍率。该 track 单独审批，
初始估计 24～48 次，未验收前不进入 V1 候选空间。

### 阶段 I-Dense：模型和数据分布 prospective holdout

目标：验证冻结模型面对真正未见模型和未见长度分布的迁移能力。冻结 basis 公式、residual
特征、系数、Packing 门槛、cross-card ratio head、1.8 阈值、support domain、confidence
规则和候选生成策略后，按完整场景切分采集 holdout。

建议覆盖：一个未参与标定的新 Qwen 规模、一个未见长度分布、一个显存边界 family、一个
Packing on/off 配对、一个至少含两个同卡数安全候选的吞吐排序场景，以及一个 1→2 或 2→4
扩卡配对。若准备支持非 Qwen，再加入一个非 Qwen Dense 模型。holdout 不得只随机切分样本
行或单次 run；每个新扩卡 claim 都必须有对应新鲜端点观测。

### 阶段 I-VL：真实图片输入的独立校准与 prospective 验收

该阶段不把已有 Qwen3-VL 纯文本端点当作视觉证据，也不把 qwen2.5-VL 的业务画像当作
GPU 安全证据。执行顺序为“最小 canary → 结构校准 → fresh holdout”，任一软件/媒体/
processor 错误先修复再继续。

#### I-VL-1. GPU canary 与实验矩阵

先用少量运行确认视觉路径、显存计数器和 loss 语义正确，再展开矩阵。首轮至少覆盖：

- 模型：Qwen2.5-VL-7B、Qwen3-VL-8B；两代模型不得共享未经校准的视觉系数；
- 训练：LoRA、Full；视觉塔冻结、projector 冻结/解冻和语言侧 LoRA 作为独立机制；
- 卡数：1/2/4 卡；先做 1→2、2→4，4→8 另立 H800 八卡轨道；
- 输入：1 图、2 图、多图；低/中/高分辨率；动态 `min_pixels/max_pixels`；若支持视频，
  增加帧数/temporal patch；
- MBS：1/2/4/8，并在预测安全线附近做 success/OOM 夹逼；
- runtime：BF16、固定 processor/template、ZeRO-2/3、GC on/off、packing off；
- 任务：生成式 VL-SFT 与多标签/分类任务分开，不将 qype19 合并到普通 causal SFT。

每个关键配置至少重复 2 次，边界点和候选差距接近 tie threshold 时重复 3 次。初始
GPU 规模按 24～48 次起步，依据 canary/残差和停止规则缩减或扩展；这部分只覆盖真实
图片输入，不与旧 text-only 端点重复计数。

#### I-VL-2. VL 显存验收

冻结 VL memory basis、视觉特征和候选生成后，使用完整 VL 场景切分 fresh holdout：

- prospective false-safe OOM = 0；
- scenario-equal P95 coverage ≥95%；
- 误拒率、no-candidate rate 和残差按模型代际、冻结机制、图像数/分辨率、卡数拆分；
- OOM 作为右删失，不能用成功样本伪造视觉激活标签；
- 旧 18 个端点仅用于校准/诊断，不能再当最终验收集。

若视觉塔/图像激活缺项仍造成系统性低估，保持 VL `unsupported` 或
`conservative_fallback`，不得仅提高固定倍率后发布。

#### I-VL-3. VL 吞吐与排序验收

现有 v4b 可以作为初始排序头，但必须在真实图片输入下重新验证：

- visual/text/computed tokens、attention pairs、samples/s 和 effective tokens/s 分开报告；
- Full VL 当前 text-only MAPE 约 3.00% 的结果只作为小样本诊断，不能覆盖 LoRA 或图片输入；
- LoRA text-only 的 pairwise 100% 与绝对 MAPE 约 72.7% 说明排序和绝对尺度必须分开治理；
- 每个卡数至少有两个显存安全候选，先同卡数排序，再进行 1.8× ratio gate；
- 真实图片输入的吞吐、CPU media pipeline 和视觉 encoder 时间必须进入独立 holdout。

qype19 的标签规范化、按参考商品图分组切分（461 张参考图、最大复用 140 次）和稀有
标签覆盖检查属于独立前置工作；vlhjn4 的 54,142 条偏好对属于 DPO/ORPO 轨道，不得
因为文本中包含视频 OCR/ASR 就并入 VL-SFT。

### 阶段 J：端到端联合验收

冻结后运行真实完整链路：

```text
数据画像
  → Packing on/off DataPlan
  → 合法候选生成
  → physical-shares P95 门控
  → 每个卡数的 v4b 排序
  → N→2N ratio lower-bound gate
  → 最终推荐卡数和配置
```

最终验收的是“推荐结果是否正确”：既要检查显存没有 false-safe OOM，也要检查同卡数
top-1 regret、扩卡 claim 的 1.8× 安全性和不确定时的 fail-closed，不能只分别报告
显存 MAPE 和吞吐 MAPE。

## 7. 数据切分与拟合方法

### 7.1 场景切分

外层场景至少按以下维度分组：

```text
模型结构/模型规模
+ train_type
+ 数据长度分布画像
+ target GBS
+ cutoff
```

同一场景的所有 runtime cohort、ZeRO、GC、MBS、GPU 数和重复记录必须一起留出。

runtime cohort 只能作为训练折内 nuisance/fixed effect，不能让同一场景从另一
runtime cohort 泄漏回来。

### 7.2 拟合方式

显存：

- 中心使用解析物理 basis + 受约束 log residual；
- success 作为精确事件；
- OOM 作为右删失不等式；
- P95 使用折外残差/保守 conformal 或 KM 尾部；
- 运行安全上界与统计 P95 分开报告。

吞吐：

- 解析 FLOPs、HBM traffic 和 collective payload；
- 绝对头只做诊断，默认不发布绝对尺度；
- 主排序使用 scenario-equal pairwise residual；
- Packing residual 只允许有界、可解释的交互项。
- 另拟合 cross-card ratio head：对同一场景的 paired
  `log(T_2N) - log(T_N)` 建模，而不是对两个未绑定的绝对预测值做除法；
- ratio head 的训练/校准/holdout 必须以完整场景为单位，至少覆盖“通过 1.8”和“不通过
  1.8”两类 family，并对候选选择不确定、显存未放行和运行失败的端点做显式剔除；
- 发布时使用折外的一侧 95% 或 conformal lower bound。点估计高于 1.8 但下界跨阈值时，
  输出 `uncertain`，不能自动扩卡。

### 7.3 允许的校准键

```text
GPU/runtime fingerprint
+ dtype/kernel path
+ train_type
+ ZeRO stage
+ GC
+ packing path
```

跨卡 ratio 还必须记录 `from_gpu_count`、`to_gpu_count`、拓扑/collective 语义和
`target_gbs`；它们是输入特征和配对约束，不是可按 model_id/dataset_id 记忆的倍率。
V1 的 threshold 是 `throughput_ratio >= 1.8`；现有 `minimum_throughput_gain_per_doubling=0.7`
只能作为待迁移的旧配置，不能与新 ratio 字段并存。

模型名、数据集名不能成为自由倍率键。数据分布必须通过 WorkloadProfile 进入
工作量特征，而不是通过 dataset ID 记忆。

## 8. 发布验收门槛

未达到以下门槛时，产物必须保持 `theory_only`、`shadow_only` 或
`hold_off`：

| 指标 | 发布要求 |
|---|---:|
| prospective successful P95 coverage | ≥95% |
| prospective false-safe OOM | 0 |
| memory-gated safety failure | 0 |
| 推荐方案相对实测安全最优的 top-1 regret | ≤10% |
| 每个可推荐卡数的安全候选数 | ≥2 |
| Packing GBS 相对误差 | ≤5% |
| Packing 保守收益（原 MBS=1） | ≥10% |
| Packing 保守收益（原 MBS>1） | ≥20% |
| VL prospective visual-path evidence | `visual_path_observed=true`，processor/collator 绑定完整 |
| VL prospective P95 coverage | ≥95%，按完整 VL 场景 scenario-equal 统计 |
| VL prospective false-safe OOM | 0 |
| VL task-family coverage | causal VL-SFT、classification/multilabel、preference 不混合验收 |
| 声称扩卡收益 | 预测 lower bound 和新鲜实测 lower bound 均 ≥1.8× |
| 扩卡 false-positive | 0；每个自动扩卡 claim 都必须由独立场景验收支持 |
| 扩卡不确定处理 | 比值下界缺失、跨阈值或端点不安全时必须停止并 `uncertain`/`fail_closed` |
| runtime mechanism fingerprint | 完整绑定 |
| 绝对 tokens/s | 未通过独立尺度验收则不得发布 |

对于超出覆盖域的新模型或新数据，应输出：

- `support_status`；
- `calibration_scope`；
- `confidence`；
- `fallback_reason`；
- `required_experiment_family`。

不能仅通过把 confidence 字符串改成 `low` 来继续消费 calibrated profile。

## 9. 停止规则与失败处理

### 9.1 停止规则

- 如果 CPU basis 不能解释单调性，先修模型，不启动 GPU；
- 如果某个 boundary family 已获得明确安全 success 且模型区间收敛，停止继续加点；
- 不为制造 OOM 强行试更大 MBS；
- 如果 Packing 在某一结构/数据域静态指标不满足，直接 `off`，不做无意义 A/B；
- 如果候选差异小于测量噪声，增加重复而不是继续增加模型自由度；
- 如果残差随某个机制系统性偏移，判定为理论缺项，补机制或特征，不直接加黑盒倍率。
- VL 画像只有图片 header 或抽样公式、没有真实 processor/collator 对账时，不能把
  `visual_path_observed` 置为 true，也不能生成自动安全候选；
- 视觉权重加入后若仍无法解释 MBS 依赖，优先补视觉激活/workspace/ZeRO 语义，不能把
  1.9× 缺口直接压成一个 VL 固定倍率；
- VL 的旧纯文本端点只能作为校准/诊断，不能替代真实图片输入的 prospective holdout；
- qype19 的多标签任务和 vlhjn4 的 DPO/ORPO 任务不能因为数据含图片/视频文本而进入
  causal VL-SFT 的同一验收集；
- 扩卡从当前最小安全卡数 N 开始，只检查相邻的 N→2N；若 ratio lower bound <1.8、
  实测下界 <1.8、任一端点不安全或候选不足，立即停止并保留 N，不跳过失败的一档去
  推荐 4N；后续更大卡数只能作为预先登记的诊断实验；
- 若吞吐点估计 ≥1.8 但置信区间跨过 1.8，结果为 `uncertain`，不得因为“平均值看起来够”
  自动扩卡；
- 跨卡端点必须先过显存门控，再参与 ratio；显存 rejected、software failure、incomplete
  fingerprint 的记录不能进入扩卡比值；
- 将旧的 `minimum_throughput_gain_per_doubling=0.7` 迁移为唯一明确的
  `minimum_throughput_ratio_per_doubling=1.8`（或明确等价的 `gain=0.8`），迁移前禁止
  混用 gain 和 ratio 两套语义。

### 9.2 失败分类

- 真实 CUDA OOM：参与边界右删失和安全验收；
- software failure：修复 runtime 后重跑，不作为不可行；
- infrastructure failure：不进入模型，不推进条件后继；
- 数据/模板错误：重新生成画像和请求，原记录作废；
- fingerprint/hash 不一致：整次 attempt 标记 incomplete，不能用于校准。

## 10. 预计实验规模与资源安排

以下是初始审批包络，不是必须全部执行的固定队列：

| 实验组 | 初始规模 | 目的 |
|---|---:|---|
| CPU-only basis/contract | 0 GPU | 统一接口和理论不变量 |
| VL CPU 结构/画像/processor contract | 0 GPU | 视觉塔结构、冻结分组、图像画像和 collator 对账 |
| 既有扩卡证据重算审计 | 0 GPU（已完成） | 从既有 30 个 `scale-*` 运行免费得到 14 个配对、8 个干净 2→4 |
| 预处理/runtime canary | 少量 | 证明工作量和执行路径一致 |
| 已有 4 卡排序 closeout | 约1～2次重跑起（按成对提交展开） | 补 rank1，并完成 rank2/rank3 反序复测 |
| frozen challenger 新鲜 holdout | 约20～30次 | 先验收实际服务模型；包含少量扩卡诊断配对 |
| Packing ABBA | 约48次 | Packing 显存/吞吐/语义校准 |
| 显存边界 | 条件性约40～80次 | 仅在 holdout/ABBA 暴露残差后做 P95、OOM guard、workspace |
| 同卡数 + 跨卡 ratio | 约48～96次 | v4b 候选排序和 1.8× 相邻翻倍 gate（共享端点运行；已因审计下调） |
| VL 真实图片 canary + prospective | 初始约24～48次 | 两代 VL、图片/分辨率/冻结机制和 MBS 边界的独立证据 |
| Offload V1.1（可选） | 条件性约24～48次 | 仅在决定纳入业务 offload 后单独校准 |
| 模型/数据 prospective holdout | 约20～30次起 | 新模型、新分布及新扩卡 claim 的独立验收 |

上表是**审批上限包络**，不是预期执行量。两条路径的量级差别很大，决策时应同时看：

| 路径 | 触发条件 | 大致 GPU 量 |
|---|---|---:|
| 乐观路径 | 阶段 D 新鲜 holdout 通过 → 显存边界 40～80 次不启动；VL 与 Offload 暂不纳入 | 约 120～180 次 |
| 完整路径 | holdout 失败需定向补测，且 VL、Offload 两个 track 都纳入 | 约 240～400 次 |

实际执行量由每轮残差和停止规则动态缩减；不能把上述上限简单相加，尤其显存 40～80
次只有在新鲜 holdout 失败时才审批，同卡数和跨卡实验应尽量共享端点运行。所有 GPU 任务必须使用新的 campaign、
新的 approval design 和新的 schema；本表不授权直接调用旧 scheduler。

## 12. 推荐执行顺序

最终顺序固定为：

```text
A. 冻结 scope、schema、split、1.8× ratio 定义和验收门槛
  ↓
B. 抽取已有 WorkloadProfile/Manifest/support/candidate 实现并完成 CPU-only 测试
  ↓
C. 预处理和 runtime 一致性 canary
  ↓
D. 补结账已有 4 卡排序（rank1 重跑 + rank2/rank3 反序复测）
  ↓
E. 在 frozen physical-shares + v4b 上先做 20～30 次 fresh prospective holdout
  ↓
F. 若 E 失败，按残差做定向显存/吞吐补实验；若 E 通过，不自动启动 40～80 次显存铺开
  ↓
G. Packing ABBA（独立于无 Packing challenger 的发布验收）
  ↓
H. 同卡数排序 + 1→2/2→4 cross-card ratio 校准，冻结 scale-out policy
  ↓
I. Offload V1 拒绝或启动独立 V1.1 track
  ↓
I-Dense. 新模型/新数据及新扩卡 claim 的 prospective holdout
  ↓
I-VL-CPU. VL 结构/画像/processor contract 与 support gate
  ↓
I-VL-GPU. VL 真实图片 canary、显存/吞吐校准和独立 prospective holdout
  ↓
J. 端到端联合验收：显存 gate → v4b → ratio gate → 卡数/配置推荐
  ↓
K. shadow → canary → production，分阶段发布
```

在 D/E 的 GPU 阶段前，数据/runtime owner 先填完六个 profile requirements；先运行一次不带
`--write-queue` 的 materializer 取得确定性的 `queue_binding_sha256`，再让新 approval 同时绑定
design、精确 GPU 池、该 queue hash 和 runtime fingerprint；随后重新运行 campaign gate，最后才允许
`--write-queue`。任何一个 hash 不匹配都不会写 JSONL。

其中 E 的结果决定 F 是否发生，不能先按旧 theory-only 数字批准大批量边界实验；跨卡
ratio 校准和端到端联合验收完成前 `scale_out_enabled` 必须保持关闭。VL 的
I-VL-CPU/I-VL-GPU 轨道必须先完成视觉路径和真实图片验收；即便 E 或 I-VL-GPU 通过，
Packing、offload、未见模型/数据仍不能借用无对应证据的系数。

任何阶段的结果都不能反向修改已冻结 holdout 或通过查看 holdout 重新选系数。

## 13. 最终成功标准

这项工作完成的标志不是“所有模型都能给出一个数字”，而是：

1. 新模型能够从结构 manifest 得到可解释的显存和吞吐预测；
2. 新数据长度分布能够通过 WorkloadProfile 进入模型，不依赖 dataset ID 倍率；
3. Packing on/off 能作为同一候选空间中的执行机制参与选择；
4. 显存预测不会把真实 OOM 判成安全；
5. 吞吐排序在安全候选集合中相对实测最优损失不超过门槛；
6. 从最小安全卡数开始，只有在相邻翻倍的预测和新鲜实测吞吐 lower bound 都达到 1.8×
   时才扩卡；不确定、候选不足或端点不安全时保留当前卡数并 fail-closed；
7. VL 只有在真实 processor/collator、视觉路径、冻结分组和图像/分辨率画像均绑定，且
   fresh prospective false-safe OOM=0、P95 coverage≥95% 后，才能进入独立 VL 支持域；
8. qype19 多标签、vlhjn4 DPO/ORPO 和 offload 不得借用 causal Dense/VL-SFT 系数；
9. 业务覆盖率和支持域外请求能明确拒绝或生成独立补实验需求；
10. 超出覆盖域时能保守降级并生成补实验需求；
11. 所有可发布系数都有独立 holdout、runtime fingerprint 和可回滚版本。

在上述条件全部满足前，统一模型只能用于离线回放和影子推荐，不能自动发起训练。

### 13.1 产品落地标准（与模型指标同等重要）

上面 11 条全部是模型属性。它们全部达标仍可能出现"指标全绿但没人换配置"的结局，
因此必须同时登记两个产品指标：

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| 推荐采纳率 | 用户实际采用推荐配置的比例，按"对手是默认值"和"对手是用户已调好的配置"分别统计 | 现有实测显示两者收益差一个量级：单卡相对朴素默认 MBS=1 提升 15.29%，而 14B 两卡相对用户自调配置只提升 1.06%（稳定段 2.19%），4 卡两候选间仅差 0.39% |
| 净收益 | ①相对用户原配置的吞吐提升中位数；②**避免的 OOM 次数** | 后者是本项目最大的实际价值来源：一次 OOM 的成本是排队、加载、启动全部作废再加一轮人工调参，而不只是训练时间 |

配套要求：

- 产品侧必须能区分"推荐等于用户原配置"（无收益但确认安全）与"推荐改变了配置"两种结果，
  否则采纳率无法解释；
- 当推荐提升低于产品切换门槛（例如 3%～5%）时，输出应显式说明"当前配置已接近最优"，
  而不是给出一个看起来更好但实际在噪声内的候选。§9.1 已规定候选差异小于测量噪声时
  增加重复而非增加模型自由度，产品输出层需要对应的表达；
- 避免 OOM 的计数只统计"预测拒绝且事后确认真会 OOM"的案例，不能把所有被拒候选都算成
  避免了一次 OOM。

### 16.2 主要结论

结论已写入 §3.3.1，并据此调整了阶段 G2 的设计要求和 §10 的规模估计：

- 既有 30 个 `scale-*` 运行可支持 **14 个**相邻翻倍配对，而旧 calibration 只呈现 **4 个**；
  差异来自 LOOCV 折内配对约束和每卡数只留一个候选，不是数据缺失；
- 其中 **8 个是干净 2→4 配对**，覆盖三种长度分布，**3 个达到 1.8**（最高 2.204）。

- 长度分布是扩卡效率的主导因素：longcontext 三个配对聚集在 1.567～1.573 且无一达标，
  multiturn 中位 1.998；ratio head 必须以 WorkloadProfile 特征为输入；
- 全部 6 个 1→2 配对都同时从 `zero=none` 切到 `zero2`，混淆了扩卡与分片通信两种效应，
  只能作诊断；补干净 1→2 配对成为阶段 G2 的首要增量目标；
- 所有端点均为单次运行，conformal 下界不可识别；这批数字**不能**用于开启 `scale_out`，
  也不能充当阶段 G 的验收集。

### 16.6 Packing 接入候选生成器（阶段 A 第 3、4 项）

新增 `scripts/packing_aware_candidates.py`（schema
`sft_packing_aware_candidate_space/v1`，15 个测试通过、ruff clean，产物
`artifacts/packing_aware_candidate_space_v1.json`）。它让 packing on/off 从"被统一
Predictor 当成未知字段吞掉"变成候选空间里的显式分支。

职责边界：**不自行推导 packing 决策、不覆盖 policy 的 `off`**
（`derives_packing_decision_itself=false`、`overrides_policy_off=false`）。决策仍由冻结
`static_packing_policy_v1.json`（SHA 绑定）给出，本模块只查询并服从。

- **按 baseline shape 逐个查询**：packing 收益取决于它替代的非 packing MBS —— 同一数据集
  对 mbs=1 值得开、对 mbs=8 可能不值得 —— 所以决策是 per (gpu_count, mbs)，不是 per scenario；
- **两个分支的资格是刻意不对称的**：非 packing 候选为 `rankable`；packing 候选为
  `shadow_only` 并携带原因 `packing_memory_and_throughput_heads_not_calibrated`
  （冻结 H800 头没有任何 `packing=true` 训练行）；
- packing 候选固定物理 MBS=1，并记录 `replaces_no_packing_mbs`，供后续 ABBA 配对使用。

实测两个场景（CPU-only，未启动 GPU）：

| 场景 | 查询 shape | 决策 | rankable | shadow | packing-on shapes |
|---|---:|---|---:|---:|---|
| `8b/lora/short_512` cut512 | 15 | 全 `off` | 50 | **0** | 无 |
| `8b/lora/multiturn_4096` cut4096 | 12 | `off`+`on` | 40 | **6** | 1/2 卡 × mbs 1/2/4 |

cutoff 512 全部 `off` 是正确的：硬门槛要求 `cutoff/mbs ≥ 1024`，reason code
`cutoff_tokens_per_no_packing_mbs`。cutoff 4096 才出现 `all_static_gates_passed`。

**开发中发现一处结构约束（值得记录）**：冻结 predictor 把 `packing` 放进
`scenario_material`，并拒绝混合不同用户场景的 `comparison_group`。因此两个分支必须使用
**不同的 predictor group id** —— "统一候选空间"体现在报告层（一个场景进、一份报告出、
两个分支来自同一批 baseline shape），而不是强行塞进同一个 group id，后者会被 predictor
直接报错。测试已固化这一契约。

端到端验证：`rankable` 分支 40 个候选全部在支持域内（`rejected_by_support_domain=0`）
并选出推荐；`shadow` 分支 6 个候选被冻结 predictor **全部**以
`outside_supported_domain` 拒绝、`ranked=0`、`selected=None`。这正是期望行为 ——
packing 可见但不可放行。

两代结构差异必须分开处理，否则误差达 20%（这是 checkpoint 校验抓出来的）：

- **Qwen3-VL**：patch 16、两层 MLP（fc1/fc2）、LayerNorm（weight+bias）、
  learned position embedding、每个 deepstack tap 一个额外 merger。
  **deepstack mergers 占整塔 20.9%（120.4 M）**，漏掉它会低估 21%；
- **Qwen2.5-VL**：patch 14、**gated MLP**（gate/up/down 三个投影）、RMSNorm（仅 weight）、
  window attention、`tokens_per_second` 视频节奏。

按 §4.1「视觉模型若未支持必须显式标记 unsupported，而不是部分套用公式」，未验证的生成
一律 fail-closed：Qwen2-VL 使用旧版 config 布局（`embed_dim`/`mlp_ratio`），被显式拒绝而
**不是**套用 Qwen2.5-VL 公式。

**诚实性护栏（本模块最重要的部分）**：报告显式声明
`explains_observed_vl_memory_gap=false`，并把常驻视觉权重与实测缺口放在同一单位下对比 ——
Qwen3-VL-8B 在 mbs=1 的实测缺口约 21.19 GiB（36.41 实测 vs 15.22 dense 预测），而 576.4 M
BF16 参数仅 1.074 GiB，**只能解释 5.1%**。测试固化了「该比例必须 <10%」。

因此本模块只交付一件事：让 VL 从「被 dense 公式静默低估」变成「结构可解析且可显式降级」。
`not_modelled` 明确列出仍缺的四项：视觉激活、多模态 workspace、ZeRO-3 对视觉参数的 gather
行为、图像 token 序列膨胀与动态分辨率分布 —— 这些必须由阶段 I-VL-GPU 的真实图片证据标定，
不能由本模块的结构项冒充。

同时补充 `visual_tokens_per_image()`：按 patch/merge 几何计算单图视觉 token 数（768×768 在
patch16 下为 576 token），供后续 VL WorkloadProfile 使用。这是 VL 与文本的关键差异 ——
计算量由分辨率和图像数决定，而非样本文本长度。

### 16.8 阶段 B canary 设计与 approval 请求（可在当前卡池执行的唯一 GPU 工作）

理由是每个一致性检查都把「静态预测」与「同一次运行的实测执行」相比 —— 两边同时来自同一台

| 分类 | 数量 | 处置 |
|---|---:|---|
| `hardware_independent` | **10** | 可在当前卡池执行，结论有效 |

视觉塔，所以该 flag 不能由 `train_type` 推导）、GBS 契约复现、execution fingerprint 完整性、
以及 VL 的 `visual_path_observed`。

`hardware_bound` 只有两项：显存峰值与 step 时间 —— 正是吞吐/显存头建模的量，必须留在
本卡池内做诊断。


VL 已经正确落 `conservative_fallback` 并被拒绝，不会误判放行。§16.5 的 `candidate_generator`
与之组合后，A-VL 的降级链路完整。

**但本轮发现一个必须记录的事实，它推翻了历史报告中的「视觉塔猜想」：**

`model_inventory.json` 的 `actual_parameters` 是**整 checkpoint 计数**，对 VL 模型
**已经包含视觉塔**。算术证据是精确的：

```text
inventory actual_parameters            = 8,767,123,696
本轮实测视觉塔（safetensors 逐张量）   =   576,388,336
差                                     = 8,190,735,360
训练日志中 Full 的 trainable            = 8,190,735,360   ← 完全相等
```

（Full 冻结了视觉塔，所以其 trainable 恰好等于语言塔。）

因此 dense 骨架推导常驻权重时**已经把视觉塔算进去了**。实测验证：把 `actual_parameters`
从 8.767B 改成语言塔的 8.191B，predictor 的 center 从 15.217 GiB 降到 14.549 GiB，
差 0.668 GiB —— 说明那 1.07 GiB 视觉权重本来就在里面。

**推论（与 §3.2.1 原表述冲突，以本节为准）**：

1. mbs=1 处 21.19 GiB 的缺口**几乎完全不是**常驻视觉权重造成的 —— 那 1.07 GiB 已被计入；
2. 若按原计划「在显存 basis 中增加视觉权重项」，会**重复计算**同一批字节，而且缺口仍有
   ~21 GiB 未解释；
3. 缺口必须归因于**视觉激活、多模态 workspace、ZeRO-3 对视觉参数的 gather 行为、
   图像 token 序列膨胀** —— 这些全部只能由阶段 I-VL-GPU 的真实图片证据标定，
   没有任何 CPU-only 工作能替代。

为防止后续实现踩这个坑，`vision_tower_structure.py` 增加了
`double_counting_guard`：`checkpoint_total_includes_vision_tower=true`、
`safe_to_add_as_new_memory_term=false`，并说明这些组件计数的正确用途是
**归因与 freeze/LoRA 范围推理，而不是在整 checkpoint 参数量之上再加一项常驻显存**。
两个测试固化了该算术恒等式和「视觉权重占缺口 <10%」。

这也意味着 A-VL 的 CPU-only 部分实际上已经做完了：结构可解析、可校验、可显式降级、
且不会被误用。**VL 变准的唯一路径是 GPU 实证，不能再靠建模推进。**

- token 记账：effective ≤ computed、computed ≤ cutoff、padding 是比率、**MBS 增大不可能
  改善 padding 利用率**（否则模型会认为大 batch 更省算力）；
- attention pair：为正、**不得用 `cutoff²` 顶替**、packed 按子序列求和而非整 pack 平方、
  随 cutoff 单调不减；
- packing：logical samples/物理序列 >1、fill ratio 仅 packing 时报告、**不得虚增
  每样本 effective token**；
- GBS/GA：`gpu×mbs×GA == target_gbs` 恒等、GA ≥ 1、不可整除时拒绝而非取整、
  packed 不携带非 packing GA；
- 确定性：同请求两次构造结果逐字节相同。

**开发中被测试抓到一个我写错的不变量**：我原本断言"packing 必然改善 padding 利用率"。
实测 `mbs=1` 时非 packing 的利用率是 **1.000000**（动态 padding 只补到样本自身长度），
而 packing 补到 cutoff 是 **0.993487** —— 略低。所以 packing 的 padding 收益**只存在于
mbs>1 的基线**。这恰好解释了冻结 policy 为何把 mbs=1 与 mbs>1 的收益门槛分开设，而不是
用一个全局数字。已改为对 mbs≥2 断言，并补一条 mbs 无关的真实收益不变量
（每逻辑样本占用更少物理序列）。

## 23. 有界显存 challenger v2 冻结（2026-08-03）

本节执行 §22.4 的 CPU-only 定向修复。没有启动 GPU、没有创建或修改实验队列、没有覆盖 v1 或
当前生产 artifact。v2 是在阅读 v1 final holdout 失败后设计的，因此它是
`post-holdout repair candidate`，不是新的 unseen 通过结论。

### 23.1 v1 外推失真的精确来源

失真集中在 Qwen3-8B LoRA、2 GPU、ZeRO-2、GC off 分支的 reservation 头。v1 对最终长文本
MBS=2 case 给出的：

- allocated profile correction log 为 `0.0258`，物理 allocated anchor 本身没有爆炸；
- reservation ratio log 为 `1.5745`，即 reservation 单层倍率约 `exp(1.5745)=4.83`；
- 其中 `risk × pressure²`、`risk × pressure³`、
  `risk × pressure³ × log2(MBS)` 三项贡献约 `0.3287 + 0.5181 + 0.5644 = 1.4112`，
  占最终 reservation log 的约 89.6%。

校准风险切片的 batch padding pressure 最大约为 `0.7020`，最终长文本画像约为 `0.9999`。
三次交互项在 calibration LOPO 内可以拟合 education profile 的 allocator reservation 峰值，但在
接近 cutoff 的新画像上没有饱和或输出边界，最终把实测 58.00 GiB 的配置推成
272.02 / 430.82 GiB center / upper。这是模型族的无约束外推，不是简单增加 ridge alpha 即可解决。

### 23.2 v2 数学结构与支持域

v2 admission 只保留一个 direct reserved 头：

```text
reserved_center
  = physical_allocated_anchor
  × exp(direct_bounded_log_correction)
```

冻结的 direct 头共有 7 个变量：

1. 5 个执行机制桶 one-hot；桶键由 `training_mode / gpu_count / zero_stage / GC / packing / MBS`
   精确组成，但不包含模型 ID 或数据集 ID；
2. `I(LoRA) × maximum_clipped_tokens / cutoff_len`；
3. `I(LoRA) × E[random_batch_max]/cutoff_len × (1-truncation_fraction)`。

两个画像量都严格位于 `[0,1]`，没有平方、三次项，也不再把 allocated 和 reservation 两个回归
校正相乘。完整 `[0,1]` stress grid 上，冻结模型的校正倍率范围为 0.271～2.306，落在预先声明的
0.20～3.00 结构门内。

另保留一个 6 变量 allocated 诊断头；它不参与 admission center 计算。operational upper 为：

```text
max(
  direct_center × exp(selector LOPO residual guard),
  physical_anchor × exp(selector calibration anchor envelope),
  physical_anchor × exp(legacy exact-selector OOM guard)
)
```

这不是统计上已识别的 P95，而是显式保守的经验上界。未见的执行机制桶直接返回
`unseen_selector_bucket`，不能自动推荐。因此当前 v2 只覆盖校准中的 5 个 packing-off 桶；
4 GPU、packing-on、LoRA GC-on 等配置仍然 fail closed。

版本化产物为：

- `artifacts/h800_bounded_memory_challenger_v2.json`；
- `artifacts/h800_bounded_memory_challenger_v2.md`；
- 拟合入口 `scripts/fit_h800_bounded_memory_challenger_v2.py`；
- 推理实现 `scripts/h800_bounded_memory_model.py`；
- shadow 组合 Predictor `scripts/h800_bounded_v4b_predictor.py`。

holdout 的 10 条观测进入数值拟合的数量为 0。v2 校准结果：

| direct reserved nested 选型 LOPO MAPE / P90 APE | 8.83% / 24.44% |

### 23.4 下一批最小严格验收

1. 3 个互相独立且未使用的文本画像：rare-tail short、broad non-truncated longtail、
   concentrated/truncated long；三者分别检验最大长度项、fragmentation 项和截断抵消项；
2. 每个画像运行当前 5 个精确支持桶，共 15 次；
3. 增加 3 个 Qwen3.5-4B LoRA 同机制 cross-scale 点，检验“物理锚点处理模型量级、校正头只处理
   执行机制/画像”的迁移假设；
4. 对每个画像额外运行 1 个固定 tail-forced 的 8B LoRA、2 GPU、ZeRO-2、GC off、MBS=2
   安全点，共 3 次，验证随机 13-step 测量可能遗漏的长度尾部；总计 21 次。
