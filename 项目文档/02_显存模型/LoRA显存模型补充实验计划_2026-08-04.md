# LoRA 显存模型补充实验计划

日期：`2026-08-04`

状态：`第一阶段已完成；已触发第二阶段 20 个新场景、60 个作业`

执行说明：`2026-08-04` 先完成旧四-profile 的 20 个复跑作业；随后已完成 15 个全新 source-disjoint 场景的 77 个第一阶段作业。结果为 68 success、9 个确认 CUDA OOM、0 个基础设施失败。M0～M3 重拟合选择 M1，但 critical recall 为 78.05%、reserved center MAPE 为 20.68%，95% expansion 阈值仍取经验最大值，因此按本计划第 5 节进入第二阶段。完整结果见 [LoRA 显存模型 15 源重拟合结果](LoRA显存模型15源重拟合结果_2026-08-05.md)。

目标：补齐 `LoRA + ZeRO-2 + GC-off + 2 GPU + non-packing` 在低 `profile_max/cutoff_len` 区域的证据，重新拟合 effective-sequence 显存模型，并在模型冻结后使用全新 prospective holdout 做正式验收。

## 1. 当前问题

两条已消费 holdout 中的不安全 LoRA case 都落在同一机制区域：

| 模型 | cutoff | 对齐后的 profile max | max/cutoff | physical upper | observed reserved |
|---|---:|---:|---:|---:|---:|
| Qwen3.5 4B LoRA | 32768 | 12488 | 0.3811 | 99.75 GiB | 137.74 GiB |
| Qwen3 8B LoRA | 32768 | 12520 | 0.3821 | 76.78 GiB | 137.56 GiB |

以 8B case 为例：

```text
physical anchor       ≈ 76.74 GiB
observed allocated    ≈ 79.0 GiB
observed reserved     = 137.56 GiB
safe limit            = 132.84 GiB

allocated / anchor    ≈ 1.03
reserved / allocated  ≈ 1.74
reserved / anchor     ≈ 1.79
```

因此主要问题不是 profile max 或 live tensor 物理量，而是低-ratio critical LoRA 的 CUDA allocator expansion 超出了现有校准范围。

现有 critical 桶：

- 观测行：24；
- 独立场景：4；
- 经验最大 `reserved/allocated`：约 1.668；
- holdout 所需 expansion：约 1.74；
- 95% finite-sample conformal 最低可计算场景数：19；
- 要使 95% conformal 不再被迫取经验最大值：39 个场景。

## 2. 要验证的假设

| 编号 | 假设 | 证伪条件 |
|---|---|---|
| H1 | effective sequence 是 non-packing allocated 的正确物理长度 | 新低-ratio 数据上 allocated/anchor 随 ratio 系统漂移且无法由小幅校准修复 |
| H2 | LoRA 误差主要来自 reserved/allocated expansion | 新数据中 allocated 同样出现大幅、无规律低估 |
| H3 | 低 ratio 对 expansion 的影响依赖训练机制 | Full 与 critical LoRA 在相同 ratio 下表现一致 |
| H4 | `gpu_count` 是真实机制变量 | 同模型、同数据、同 MBS 的 2/4 GPU expansion 无稳定差异 |
| H5 | `log(max/cutoff)` 只应作为残差或交互特征 | 全局 ratio 系数比 effective anchor 更稳定且不会重新误拒 Full |

## 3. 场景与作业的计数规则

### 3.1 独立场景

一个独立场景至少绑定：

```text
model revision
dataset source revision
tokenizer revision
chat template / preprocessing revision
profile SHA-256
runtime cohort
allocator configuration
```

同一模型和数据只改变 MBS、重复运行或改变随机种子，仍只算一个独立场景。重复运行可估计方差，但不能增加 conformal 的独立样本数。

### 3.2 单场景三个 LoRA 压力点

| 压力点 | 目标 | 要求 |
|---|---|---|
| 低压成功点 | 获得稳定 allocated/reserved 基线 | 明确低于安全线 |
| 边界成功点 | 估计高压 expansion | 尽量接近安全线但必须成功 |
| 更高压力点 | 提供 OOM lower bound 或更高 expansion | 可成功或 OOM |

如果第二个点已经 OOM，必须降低 MBS 补一个边界成功点。每个独立场景至少需要两个成功点，才能进入 expansion 校准。

## 4. 第一阶段：最低可重拟合版本

### 4.1 新增场景分布

新增 15 个 source-disjoint 场景，使 critical 桶从 4 个增加到 19 个：

| `profile_max/cutoff_len` | 新场景数 | 建议模型分布 | 目的 |
|---|---:|---|---|
| `<= 0.40` | 4 | 4B、8B、14B 均覆盖 | 复现当前最危险区域 |
| `(0.40, 0.70]` | 4 | 小、中、大模型混合 | 识别强收缩区间斜率 |
| `(0.70, 0.90]` | 4 | 小、中、大模型混合 | 连接新旧训练分布 |
| `> 0.95` | 3 | 作为接近 cutoff 的对照 | 检查 expansion 是否只在低 ratio 异常 |
| **合计** | **15** |  |  |

优先使用新的业务来源或重新构造但 source-disjoint 的数据集，不得把同一原始数据随机切成多个“独立场景”。

## 5. 第二阶段：提高 95% 尾部可用性

第一阶段完成后 critical 桶共有 19 个独立场景，95% conformal 虽然可计算，但阈值仍是经验最大值。

如果第一阶段出现以下任一情况，则继续第二阶段：

- reserved safety 满足但 admission recall 被最大值阈值压到 90% 以下；
- expansion 上界对单个场景极端敏感；
- critical ratio 交互系数在 outer folds 中符号或量级不稳定；
- 部分 ratio 档仍少于 4 个独立场景。

第二阶段新增：

| 实验组 | 新增独立场景 | 每场景作业 | 作业数 |
|---|---:|---:|---:|
| Critical LoRA expansion 扩充 | 20 | 3 | 60 |

完成后：

```text
已有场景       4
第一阶段新增  15
第二阶段新增  20
总计          39
```

此时 95% finite-sample conformal 取第二大场景分数，不再被迫取经验最大值。

完整校准阶段作业数：

```text
第一阶段 77 + 第二阶段 60 = 137 个 GPU 作业
```

## 6. 固定实验配置

除明确的消融维度外，以下配置必须冻结：

| 字段 | 固定要求 |
|---|---|
| GPU | H800；记录实际卡型号、容量和 UUID |
| 模式 | critical 组固定 LoRA / ZeRO-2 / GC-off / non-packing |
| 卡数 | 主组 2 GPU；配对组增加 4 GPU |
| cutoff | 由目标 ratio 档和 profile max 共同确定，不能事后修改 |
| padding | 动态 padding；`pad_to_multiple_of=8` |
| profile | 最终 tokenizer + template + preprocessing 后生成 |
| allocator | 固定 `PYTORCH_CUDA_ALLOC_CONF` 与进程启动方式 |
| 软件 | 固定 PyTorch、CUDA、DeepSpeed、Transformers revision |
| 并发 | 独占目标 GPU，禁止混入其他占用进程 |
| warmup | 固定 warmup 和测量窗口，确保达到显存稳定峰值 |

profile max 进入物理层时使用：

```text
effective_sequence = packing
  ? cutoff_len
  : round_up(min(cutoff_len, profile_max), 8)
```

## 7. 每条作业必须采集的字段

### 7.1 输入与身份

- experiment ID、scenario ID、repeat ID；
- model ID、revision、参数规模、结构 manifest；
- dataset source、revision、样本数；
- tokenizer/template/preprocessing/profile SHA-256；
- cutoff、raw profile max、aligned effective sequence、ratio；
- training mode、LoRA rank/target modules；
- ZeRO stage、GC、packing、MBS、GA、GPU count；
- runtime cohort、CUDA/PyTorch/DeepSpeed/allocator 指纹。

### 7.2 结果与遥测

- outcome：success/OOM/infra failure；
- per-rank peak allocated；
- per-rank peak reserved；
- 多卡最大值，不能只记录多卡平均；
- OOM 的 reported allocated/reserved/free 和安全下界；
- 峰值所在 step、测量窗口和稳定性标记；
- tokens/batch、实际 padding 长度和 runtime batch-shape counter；
- wall time、tokens/s，用于排除异常运行但不参与本轮显存目标拟合。

infra failure 不得当作 OOM，也不得进入显存回归。

## 8. 拟合消融

数据冻结后一次性拟合以下四个版本：

| 版本 | 物理锚点 | allocated residual | reservation expansion |
|---|---|---|---|
| M0 | cutoff | 旧冻结口径 | 旧冻结口径，仅作对照 |
| M1 | effective sequence | 不含 ratio | 机制桶 guard |
| M2 | effective sequence | 增加 `log(max/cutoff)` | 机制桶 guard |
| M3 | effective sequence | 增加 `log(max/cutoff)` | 增加 `critical_lora * log(max/cutoff)` 交互 |

约束：

- 所有 center 和 tail 均在每个 outer fold 内重拟合；
- 外层按 source-disjoint scenario 留一；
- 内层 tail 同样按 scenario OOF；
- 同场景多行折叠为最坏 calibration score；
- 比较 row-weight 与 scenario-balanced center，默认优先 scenario-balanced；
- consumed 8/2、8/3 holdout 只做诊断，不得用于选择 M1/M2/M3；
- ratio 系数若在 folds 中不稳定，则回退 M1，不因单批 holdout 表现保留。

最终安全上界仍为：

```text
max(
  direct_reserved_upper,
  allocated_upper * expansion_upper,
  oom_lower_guard,
)
```

ratio 特征不能替代 fail-closed 和 OOM guard。

## 10. Prospective holdout

模型、特征、桶键、coverage 和风险策略全部冻结后，再生成全新 holdout。

### 10.1 实用版本

| 类型 | 独立场景数 |
|---|---:|
| Critical LoRA，ratio `<= 0.5` | 12 |
| LoRA 对照，ratio `> 0.7` | 6 |
| Full，ratio `<= 0.5` | 6 |
| 4-GPU 配对机制 | 3 |
| 其他 source-disjoint 控制 | 3 |
| **合计** | **30** |

每个场景至少执行一个冻结模型预先选定的边界配置，不得看结果后替换候选。

### 10.2 强统计版本

若希望在零失败条件下给出约 95% 置信度、支持失败率不高于 5% 的陈述，应扩展到约 59 个独立 holdout 场景。

### 10.3 发布门槛

| 指标 | 门槛 |
|---|---:|
| false-safe OOM | 0 |
| unsafe success admitted | 0 |
| scenario-weighted reserved upper coverage | `>= 95%` |
| admission recall | `>= 95%` |
| center MAPE | `<= 20%` |
| profile/runtime contract mismatch | 0；不匹配必须 unavailable |

holdout 失败后只能形成新的 repair candidate，不能在同一批 holdout 上修正并重新宣称验收通过。
