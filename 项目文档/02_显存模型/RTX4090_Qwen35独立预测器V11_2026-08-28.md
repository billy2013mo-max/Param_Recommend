**产物**：`offline_experiments/artifacts/rtx4090_qwen35_v11_predictor.json`
**代码**：`offline_experiments/scripts/{fit,predictor}_rtx4090_qwen35_v11.py`

## 1. 要干的事

V1 上线后用 20 组 out-of-sample 作业做了独立验证。两件事：

1. **抓到一个真缺陷**：`FA2 + mbs>1` 是框架硬错误（`fla` 要求 batch=1），V1 会对
   这类配置返回 `admitted=True`，等于推荐一个秒崩的配置。已加前置门。
2. **抓到两条系统性数值偏差**：多卡 + GC 显存被低估（−16% 平均），因为 V1 里
   `gc×log_gpu` 项没有多卡 GC 数据无法识别；GC 对多卡吞吐是**乱流**（有的快 7 倍、
   有的慢 4 倍），单一线性项拟合不了。

V1.1 合并 OOS 数据重拟合，显存偏差基本消除；吞吐的绝对误差没改善（MAPE 46%），
但**排序质量实测很好**（配对正确率 94.1%，推荐第一名 11 组中 10 组命中，
平均 regret 3.9%）——见 §5。**MAPE 大不等于排序坏，这两件事必须分开看。**

## 2. 相对 V1 的变化

**变化 1：训练分布 532 → 552 行**，新增 20 组 out-of-sample
（`oos_v1_results.jsonl`，14 有效 + 6 框架失败剔除）。

**变化 2：显存特征加 `gc × log_gpu`**

V1 所有 `gc=True`（48 条）都是单卡，`log2(1)=0`，所以 `gc×log_gpu` 恒为零、
无法识别。多卡 GC 行为的泄露被 ridge 吸收到别处，造成多卡 GC 显存低估。
OOS 拆穿后在重拟合里加上，系数 **+949 MiB/（GC×log2卡数）**。

**变化 3：吞吐特征加 `gc × log_gpu`**

OOS 测试中多卡 GC 的吞吐表现是非单调的（见 §5），但 `gc×log_gpu` 至少
捕获了一部分方向。系数 **−0.027**，影响很小——因为真实影响是 regime 跳变，
不是连续斜率。

**变化 4：预测器前置门增加第三条**

`attn == "fa2" and mbs > 1` → 不可行。这是 V1 真缺陷的修复。详见
[V1 文档 §2.3](#23-fa2-无-packing-的吞吐塌陷)，但那条讲的是吞吐塌陷，
这条讲的是**显存 + 能不能跑**。

**变化 5：预测器加载 v1.1 的 JSON 和特征函数**

（历史教训：复制脚本时 `DEFAULT_ARTIFACT` 和 `from fit_rtx4090_qwen35_v1 import`
两处漏改，导致第一轮对照 v1/v1.1 全相同。已修。）

## 3. FA2 + mbs>1 是硬约束（V1 遗留的真缺陷）

V1 的 `eff_mbs` 特征假设「FA2 无 packing 时有效微批 = mbs」。OOS 的 C 组
4 条 + D 组 2 条实测证明了这是错的，而且错得比「预测不准」更严重——**配置根本跑不起来**：

```
ValueError: The batch size is expected to be 1 rather than 2 when using
`cu_seqlens`. Please flatten variable-length inputs before processing.
  fla/ops/gated_delta_rule/chunk.py:548 ← llamafactory/model/patcher.py:208
```

原因：FA2 触发 patcher 把 `position_ids` 转成 `cu_seqlens`，`fla` 就要求 batch=1。
跟开不开 packing 无关。**这解释了为什么 V1 训练池里 FA2 的 292 行全部是 mbs=1**
——当初做实验的人撞过这堵墙并固定了 mbs=1，但约束从没写进模型。

**推荐含义**（已写进前置门文案）：

- 想要 **MBS>1** → 只能走 **sdpa**（放弃 packing 的吞吐增益，sdpa 走显式 MBS）
- 想要 **packing** → 只能 **fa2 + mbs=1**（packing 是 FA2 上最大的吞吐来源）

**二者不可兼得**。

## 4. 显存改善：OOS 相对 MAE 17.6% → 5.8%

在 V1 用的同一批 14 组 OOS 数据上对照（预测器各自加载自己的冻结 JSON）：

| 指标 | V1 | V1.1 |
|---|---:|---:|
| 显存相对 MAE | 17.6% | **5.8%** |
| 显存平均偏差 | −16.0% | **−2.2%** |
| 显存最大低估 | −60.1% | **−24.3%** |
| 错放 OOM | 0 | **0** |
| 误拒可跑配置 | 1 | 2 |

`gc×log_gpu = +949` 补上了多卡 GC 的显存低估。**准入零错放**保持（这是唯一
不可接受的错误方向）。

**具体例子**：`0.8B/multiturn/4卡/z2/fa2无packing/GC`，V1 预测 1863 MiB、
实测 4666（−60%）；V1.1 预测 3928 MiB（−16%）。这条是 V1 最差的一条。

## 5. 吞吐：绝对值不准，但排序可用

### 5.1 先说结论

V1.1 的吞吐 MAPE 在 OOS 上基本没动（46.2% vs 47.9%）。但**MAPE 大不等于
排序坏**——推荐系统真正关心的是「在候选里挑出的那个够不够快」，不是「预测的
数字准不准」。这两件事实测差很远：

| 指标 | 值 | 说明 |
|---|---:|---|
| MAPE（绝对误差） | 22.7% | 数字偏 |
| **Spearman 秩相关** | **0.978** | 单调性几乎完美 |
| **两两配对方向正确率** | **94.1%** | 62102 对里 94% 判对谁更快 |
| 组内加权配对正确率 | 92.2% | 按 (模型, 数据集) 分组 |
| **第一名命中** | **10/11 组** | 推荐的最优配置就是真最优 |
| **平均 regret** | **3.9%** | 推荐的配置平均只比最优慢 3.9% |

**所以吞吐模型可以用来排序**，不能用来当预算数字。

（复算：`scripts/evaluate_rtx4090_qwen35_v11_ranking.py`）

### 5.2 分组明细

分组口径是 (模型, 数据集)——真实场景里模型和数据由用户给定，他挑的是其余
参数（卡数 / zero / attn / packing / cutoff / mbs / gc）。跨模型比 tok/s
没有业务意义。

| 模型 | 数据集 | n | Spearman | 配对正确率 | regret |
|---|---|---:|---:|---:|---:|
| 0.8B | blind_f1 | 32 | +0.995 | 98.4% | 命中 |
| 0.8B | blind_f2 | 26 | +0.997 | 98.8% | 命中 |
| 0.8B | multiturn_4096 | 54 | +0.964 | 92.9% | 命中 |
| 0.8B | short_512 | 72 | +0.970 | 91.9% | 命中 |
| 4B | blind_f1 | 27 | +0.991 | 97.7% | 命中 |
| 4B | blind_f2 | 21 | +0.973 | 95.7% | 命中 |
| 4B | multiturn_4096 | 19 | +0.851 | 86.5% | 命中 |
| **4B** | **short_512** | 59 | +0.961 | 90.3% | **42.6%** |
| 9B | blind_f1 | 9 | −0.083 | 52.8% | 命中 |
| 9B | blind_f2 | 4 | +0.800 | 83.3% | 命中 |
| 9B | short_512 | 29 | +0.915 | 86.7% | 命中 |

**唯一真出问题的一组是 `4B/short_512`**：推荐 6383 tok/s，实际最优 11123，
慢 42.6%。原因是那条 `4B/neat/c4096/gc=on` 是全组唯一开 GC 的行，落在
「多卡 + GC 只有 8 条」的稀疏区，被错排到第一。真最优是 `c2048/gc=off`。

`9B/blind_f1` 的 Spearman 是 −0.083，看着吓人但不影响推荐：9 行里 8 行
实测挤在 339～426 之间（差异在噪声级），只有第一名 796 拉开差距，而**那个
第一名预测器排对了**，所以 regret = 0。这一格测的是噪声内部的顺序。

### 5.3 GC 的影响是 regime 跳变，不是可加项

多卡 GC 的吞吐影响在数据里是**非单调的**，任何单一线性项都拟合不了：

| 配置 | gc 关/开吞吐比 | 方向 |
|---|---:|---|
| 0.8B/g2/fa2/off/c2048 | 7.56 | GC 让它慢 7.6 倍 |
| 4B/g2/fa2/off/c2048 | 4.44 | GC 慢 4.4 倍 |
| 4B/g4/fa2/off/c4096 | 0.22 | GC 让它快 4.5 倍 |
| 4B/sdpa/g1/mbs4 | 0.39 | GC 快 2.6 倍 |
| 9B/g4/fa2/off/c4096 | 0.27 | GC 快 3.7 倍 |

同一个模型、同一组配置参数，方向相反。而多卡 GC 只有 8 条数据 + 若干单卡
对照，无法把「什么条件触发跳变」建成连续项。这也是 `gc×log_gpu` 在吞吐模型里
系数只有 −0.027（几乎无效）的原因——它在显存模型里有效（+949 MiB），因为
显存的 GC 效应是连续的。

**但这不妨碍排序**，实测：

| 子集 | n | 配对正确率 | MAPE |
|---|---:|---:|---:|
| 多卡 + GC | 8 | **92.9%** | 36.7% |
| 其余 | 345 | 94.1% | 22.4% |

MAPE 差距明显，配对正确率却接近——该子集是「绝对值偏、方向对」。

**使用建议**：多卡 + GC 的 tok/s 数字不要当预算依据，但用来比较大小没问题。

（对比：VL 模型 V1.1 的 `gc×log_gpu` 在吞吐上有效，是因为 VL 数据里 GC 的
吞吐行为是连续的。Qwen3.5 非连续，机制不同。）

## 6. 一个测量伪影（不当作模型缺陷）

OOS 的 G 组（cutoff=6144 外推）单条吞吐实测 5322，而 c2048 和 c8192 邻居
分别是 7011 和 21973——**c6144 掉在单调趋势之下**。检查工作目录确认它是
正常完成的运行时（124320 tokens / 23.36s，内存也正常），但 c6144 不是 2 的
幂，`packing` 在某些非对齐 cutoff 上会有一致的序列拼接低效，导致非单调的
吞吐下探。这是**测量伪影**，不是上限规律，V1.1 没有把它当结构项拟合。

排除这一条后，吞吐 MAPE 34%（V1 与 V1.1 相当）。

## 7. 数据修复记录（V1.1 新增）

发现 Qwen3.5 的 tok/s 解析问题根因，比已知更严重：

**根因**：HuggingFace 把大浮点数按科学计数法打印（如 `1.193e+04`），而矩阵
脚本用的正则 `[0-9.]+` 在 `e` 处停下，丢掉指数——**真值 ≥ 10⁴ 的行一律被
除以 10⁴**。

**后果**：本轮 OOS 20 组里 3 条中招（真值 11928 / 16732 / 11123，记录值全
是 ~1.1x）。VL 侧 24 条 + Qwen3.5 sedpa 4 条，都是同一个 bug。

**更深一层**：在当前环境下 `train_tokens_per_second` 这个字段在 metrics 里
**已经完全不存在**（`all_results.json` 里是 `None`），正则会匹配到日志里别的数字，
结果不可信。

**权威算法**（已写进 `scripts/recompute_tps_from_results.py`）：

```
tok/s = num_input_tokens_seen / train_runtime
```

两个字段都在每个作业的 `all_results.json`（或 `trainer_state.json`
log_history 末条）里，是 Trainer 自己记的，不经过任何字符串解析。

**已修正**：VL 数据 24 条（2026-08-25）、Qwen3.5 sdpa 4 条（2026-08-28）、
Qwen3.5 OOS 3 条（本轮）。每个修复脚本都备份了原文件。

## 8. 已知边界（V1 全部继承 + V1.1 新增）

沿用 V1 的 6 条边界（模型集死三个、regime 不可外推、gc 全单卡、multiturn
长尾、外推 40GiB 数值发散、只覆盖 LoRA）。

**V1.1 新增**：
1. **多卡 + GC 的 tok/s 绝对值不可靠**（MAPE 36.7%，regime 跳变导致）。
   但**排序仍可用**（配对正确率 92.9%）——见 §5.3
2. **多卡 GC 的显存仍会低估到 −24%**（比 V1 的 −60% 好，但仍偏保守）
3. **cutoff 非 2 的幂时吞吐可能非单调下探**（测量伪影）
4. **V1 的 `eff_mbs` 假设失效**：`FA2 + mbs>1` 改为前置拒绝
5. **`4B/short_512` 这一组的排序有已知失误**：推荐配置比最优慢 42.6%，
   根因是该组唯一的 GC 行落在数据稀疏区（见 §5.2）
