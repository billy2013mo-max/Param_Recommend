# 历史显存数据迁移与 M1 重拟合结果

日期：`2026-08-05`

状态：`五步迁移已完成；325 条历史精确观测已纳入；M1 仍为影子候选；生产模型未修改`

> 后续修正：本报告将原历史留出 167 条也作为已消费校准证据，适用于分析“全部历史证据参与拟合”的效果，不应再用于宣称固定历史留出验证。保留原历史留出、不让其进入任何拟合的新结果，请以[历史留出集固定验证结果](历史留出集固定验证结果_2026-08-05.md)为准；本报告生成的全历史影子候选也已被严格留出版本取代。

## 1. 结论

历史数据确实还在目录中，对应原始数据、逐样本 token 画像和实验观测都能找到。完成重新绑定和审计后：

- 接纳了 `325` 条 attempt、rank 事件和终态绑定完整的历史 H800 显存观测；
- 其中 `232` 条成功、`93` 条 OOM；
- 原来的 `158` 条校准观测和 `167` 条旧验证观测都已转成“已消费的历史校准证据”；
- 排除了 `594` 条更早的 legacy 观测，因为它们没有精确 attempt 绑定、结构化终态和校准分区；
- 5 个历史派生数据集与当前 19 个业务源的内容重叠为 `0`；
- 5 个历史派生数据集内部存在较多样本复用，因此只能保守地合并成 `1` 个独立历史源，而不能虚报成 5 个；
- 合并后共有 `430` 条原始观测、`319` 个折叠后配置、`20` 个独立源；
- 候选范围内仍然选择 M1，但提升较小，安全配置放行率没有提高；
- 第二阶段 20 个全新业务源、60 个作业仍然必须执行。

## 4. 历史数据为什么只能计为一个独立源

5 个派生数据集内部存在明显的样本复用：

| 数据集组合 | 重复内容数量 |
|---|---:|
| `multiturn_2048` 与 `multiturn_4096` | 906 |
| `longtail_8192` 与 `multiturn_4096` | 250 |
| `longtail_8192` 与 `multiturn_2048` | 224 |
| `longtail_8192` 与 `short_512` | 125 |
| `longcontext_32768` 与 `longtail_8192` | 20 |
| `longcontext_32768` 与 `short_512` | 1 |

这些重叠关系把 5 个数据集连成了一个整体。如果把它们算作 5 个独立源，会高估独立证据量并在留源验证中产生数据泄漏。

当前处理方式是：

```text
保留全部历史配置和观测
        ↓
统一归入一个历史公共数据源族
        ↓
拟合、交叉验证和安全尾部计算时总权重只算 1 个源
```

历史数据和当前 19 个业务源之间的内容重叠为 `0`，因此历史源与当前业务源之间仍是独立的。

## 5. 哪些历史观测被接纳

| 历史观测类型 | 数量 | 处理方式 |
|---|---:|---|
| 原历史校准集 | 158 | 纳入新拟合 |
| 原历史验证集 | 167 | 标记为已消费验证集后，重新归为训练/校准证据 |
| **严格历史观测合计** | **325** | **全部纳入** |
| 更早 legacy 观测 | 594 | 排除 |

325 条接纳观测全部满足：

- H800 硬件绑定完整；
- 精确 execution attempt 已冻结；
- rank 事件与 attempt 绑定完整；
- 成功或 OOM 终态有结构化证据；
- 显存峰值来自真实测量，不是补值；
- 原始数据和画像可以恢复。

594 条 legacy 记录虽然结果文件存在，但每条都同时缺少：

- 授权校准角色；
- 校准拆分策略；
- 独立数据源标识；
- 精确 attempt 事件绑定；
- 可用于校准的执行证据；
- 结构化终态分类。

因此这 594 条没有被悄悄删除，而是完整登记为排除记录。以后如果能重新恢复精确 attempt 证据，可以再次迁移。

## 6. 重复实验与成功/OOM 冲突的处理

合并前共有 `430` 条观测：

| 数据 | 原始观测 |
|---|---:|
| 当前 19 源 | 105 |
| 历史迁移数据 | 325 |
| **合计** | **430** |

折叠后：

| 项目 | 数量 |
|---|---:|
| 唯一配置/结果组 | 319 |
| 成功 | 247 |
| OOM | 72 |
| 被折叠的重复行 | 111 |
| 独立源 | 20 |

历史数据中发现 2 个相同配置同时出现过成功和 OOM。这里没有用成功中位数覆盖 OOM，而是分别保留为：

```text
同配置成功证据
同配置 OOM 边界证据
```

这样可以保留边界配置的运行波动，不会因为折叠而掩盖显存风险。

## 7. 合并历史数据后的 M1 指标

### 7.1 实际候选范围

候选仍只支持：

```text
H800 + LoRA + ZeRO-2 + 关闭梯度检查点 + 2 GPU + 不使用 Packing
```

在该范围内，合并历史数据后的留一数据源交叉验证结果为：

| 指标 | 结果 |
|---|---:|
| 独立数据源 | 20 |
| 配置数 | 61 |
| 成功 / OOM | 51 / 10 |
| 已分配显存数据源等权误差 | 5.16% |
| 预留显存数据源等权误差 | 19.54% |
| 预留显存上界覆盖率 | 100% |
| 安全配置放行率 | 73.33% |
| 被错误放行的 OOM | 0 |
| 被错误放行的超安全线成功作业 | 0 |

M1 仍优于加入长度比例项的 M2、M3；M2、M3 的比例系数仍然不稳定。因此仍选择“不额外加入最大长度/截断长度比例项”的 M1。

### 7.2 在原来 19 个业务源上的前后对比

为了公平比较，下面只看相同的当前 19 个业务源。迁移后的模型在每个验证折中可以额外使用历史源训练。

| 指标 | 原 M1 | 加入历史数据后的 M1 | 变化 |
|---|---:|---:|---:|
| 全配置已分配显存误差 | 4.98% | 4.73% | 改善 0.25 个百分点 |
| 全配置预留显存误差 | 15.42% | 15.96% | 变差 0.54 个百分点 |
| 全配置上界覆盖率 | 98.95% | 100% | 改善 1.05 个百分点 |
| 全配置安全放行率 | 71.23% | 71.23% | 不变 |
| Critical LoRA 已分配显存误差 | 5.29% | 5.18% | 改善 0.11 个百分点 |
| Critical LoRA 预留显存误差 | 20.68% | 20.42% | 改善 0.26 个百分点 |
| Critical LoRA 上界覆盖率 | 100% | 100% | 不变 |
| Critical LoRA 安全放行率 | 78.05% | 78.05% | 不变 |
| Critical LoRA 错误放行 OOM | 0 | 0 | 不变 |

所以历史数据不是没有作用，但作用比较小而且有正有负：

- 已分配显存误差小幅改善；
- Critical LoRA 的预留显存误差小幅改善；
- 全配置预留显存误差略微变差；
- 最关键的安全配置放行率没有提升。

主要原因是 325 条历史观测虽然配置很多，但内容相互关联，统计上只能增加 1 个独立源，无法替代新的独立业务场景。

## 8. 为什么没有扩大模型支持范围

如果把历史 Full、其他 ZeRO、其他卡数等所有机制也纳入候选范围，留源验证中出现：

- 6 个被错误放行的 OOM；
- 4 个被错误放行的超安全线成功作业。

这些问题发生在当前 Critical LoRA 候选范围之外。因此本次只把历史数据作为训练增强和范围外诊断，不把 M1 的支持范围扩大到所有历史机制。

## 9. 第二阶段仍然需要执行

加入历史数据后仍命中四个触发条件：

| 触发条件 | 当前结果 | 是否触发 |
|---|---:|---:|
| 当前业务 Critical LoRA 安全放行率低于 90% | 78.05% | 是 |
| 当前业务 Critical LoRA 预留显存误差高于 20% | 20.42% | 是 |
| 95% expansion 阈值仍取经验最大值 | 2.3462，20/20 | 是 |
| 比例回归系数不稳定 | M2、M3 均不稳定 | 是 |

历史数据将独立源数量从 19 增加到了 20，但 95% 阈值仍然必须取第 20 个，也就是最大值。它没有解决尾部被单一最大场景控制的问题。

下一步仍是补充 20 个全新业务源、每源 3 个 Critical LoRA 作业，共 60 个作业。完成后重新拟合，再冻结候选并执行全新的正式验证集。

## 10. 验证集治理

原来的 167 条历史 holdout 已被查看、用于旧模型评价和问题诊断，因此现在明确标记为“已消费验证集”。它们可以作为训练/校准证据，但以后不能再次宣称为独立验证结果。

正式发布验证必须满足：

- 在当前模型和第二阶段模型完全冻结之后选择；
- 与当前 19 个业务源、历史公共数据源族和第二阶段 20 个源全部无重叠；
- 验证结果不能回流修改同一候选后再宣称通过。
