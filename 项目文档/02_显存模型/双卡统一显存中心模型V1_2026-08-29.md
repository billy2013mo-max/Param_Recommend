## 1. 要干的事

参数推荐要上平台，Go 侧只应该实现**一套**显存公式。现状是两套：H800 一套、
RTX 4090 一套，各有独立的冻结系数。这一步把两张卡合成一个系数向量。

## 2. 一个前提被推翻了（我上轮说错了）

我上轮说"两套公式不同，H800 走 `physical_allocated_anchor`，4090 走
`analytic_reference` + 28 特征"。**这是错的。** 我把 H800 的第二层拿去和 4090 的
第一层比了。实际结构是两层：

| 层 | 公式 | H800 | 4090 |
|---|---|---|---|
| 第一层（共享） | `analytic_reference × exp(28 特征 @ beta)` | 有 | 有 |
| 第二层（H800 特有） | `allocated_anchor × exp(selector 修正)` | 有，18 行 / 5 个 selector | 无 |

第一层**本来就是同一套代码**：两张卡都调
`h800_challenger_modeling._memory_features(record, "physical_shares")`，
`model_family` 都是 `analytic_reference_log_residual_ridge`，28 个特征名逐字相同、
顺序相同。所以兼容性问题比我说的小得多 —— 缺的只是"一个拟合"，不是"一套契约"。

顺带纠正第二处：我上轮说两卡模型重叠"只有 1.7B"。那是吞吐侧的口径。**显存侧
重叠是 1.7B 和 4B 两个**（H800 有 4B）。

## 3. 对齐探针：零失败

跑 `probe_joint_card_memory_alignment_v1.py`，把两张卡的记录全部过一遍共享的
28 维构建器：

| | H800 | RTX 4090 |
|---|---:|---:|
| 记录数 | 325 | 1136 |
| 成功 / OOM | 232 / 93 | 968 / 168 |
| 28 维特征构建成功 | **325 / 325** | **1136 / 1136** |
| 特征维度 | 28 | 28 |
| 卡容量 | 133 GiB | 22 GiB |
| `analytic_reference` 中位数 | 85.1 GiB | 21.0 GiB |
| distinct selector key | 92 | 118 |
| 覆盖模型 | 1.7B / 4B / 8B / 14B | 0.6B / 1.7B / 4B |

**selector 重叠：H800 的 92 个 key 全部被 4090 覆盖**（`h800_only = 0`），4090 多出
26 个。也就是说不存在"H800 有而 4090 没有"的配置组合，卡维度可以干净地加进去。

配置覆盖对比（说明卡交叉项不是退化特征）：

| | H800 | RTX 4090 |
|---|---|---|
| gpu_count | 1:76, 2:116, 4:133 | 1:438, 2:358, 4:340 |
| zero_stage | 0:76, 2:110, 3:139 | 0:438, 2:415, 3:283 |
| gc | False:154, True:171 | False:506, True:630 |
| packing | **全部 False** | False:1082, True:54 |

## 4. 模型形式

```
reserved_centre = analytic_reference_bytes
                × exp(intercept + 标准化([28 个共享特征, 6 个卡特征]) @ beta)

reserved_upper  = reserved_centre
                × exp(max(success_log_residual_upper, oom_log_residual_lower, 0))
```

共享的 28 个特征**一个字没改**，直接用 H800 那份代码。新增 6 个卡特征：

| 卡特征 | 含义 |
|---|---|
| `is_rtx4090` | 卡截距偏移 |
| `rtx4090_x_log2_gpu_count` | 互联差异（4090 走 PCIe，H800 有 NVLink） |
| `rtx4090_x_zero2` / `rtx4090_x_zero3` | ZeRO 通信 workspace 受互联影响 |
| `rtx4090_x_log2_parameters` | 小卡上模型规模的占比不同 |
| `rtx4090_x_gradient_checkpointing` | 重算 workspace 的卡差异 |

**未知卡策略**：卡特征全置零，退回共享的 28 特征核心。这与 H800 单卡模型面对
陌生卡时的行为一致。

**选型规则（看结果之前就定死的）**：最小化**最差那张卡**的留出 MAPE。
一个靠牺牲一张卡来讨好另一张卡的联合模型，对必须同时服务两卡的平台没用。

40 个候选（4 组卡特征 × 2 种加权 × 5 个 alpha）里选中
`card_full` + `alpha=1.0` + 不做卡均衡加权。

## 5. 精度：两张卡都没退化

5 折 scenario 留出，scenario-equal MAPE：

| 卡 | 联合模型 | 单卡基线（同协议） | 变化 |
|---|---:|---:|---:|
| H800 | **7.80%** | 7.89% | **−0.09pp** |
| RTX 4090 | **7.90%** | 6.77% | +1.13pp |

再跟**老 4090 单卡线自己报的 nested CV** 对比（更严格的协议）：

| | 老 4090 单卡线 | 联合模型 |
|---|---:|---:|
| scenario-equal 中心 MAPE | 9.11% | **7.90%** |

所以：联合模型比老线**好 1.2pp**；比我这份脚本里同协议的单卡基线差 1.1pp。
两个对比方向不同，是因为协议不同 —— 我的单卡基线用的是同一套 5 折 scenario 留出，
老线用的是嵌套 CV。**能下的结论是：合成一套没有让 4090 变差到老线的水平以下。**

## 6. 准入：两张卡零误放行

折外口径（中心和保序裕度都来自没见过这一行的折）：

| 卡 | OOM 召回 | **误放行 OOM** | 误拒率 | 超线成功被放行 |
|---|---:|---:|---:|---:|
| H800 | 100%（93/93） | **0** | 15.4%（33/214） | 0 / 18 |
| RTX 4090 | 100%（168/168） | **0** | 18.7%（151/807） | 0 / 161 |

口径说明（这里我一开始算错过）：**观测峰值本来就超过安全线的成功行，拒掉是对的，
不算误拒。** 4090 有 161 行、H800 有 18 行属于这类（跑起来了但峰值超过容量的 95%），
全部被正确拒绝。第一版我把它们算进误拒，得出 4090 误拒 31.8%，是错的；正确值 18.7%。

对比老 4090 单卡线：OOM 召回 100%、误放行 0、误拒 **15.0%**（64/426）。
联合模型误拒高 3.7pp —— 保序裕度要覆盖两张卡合起来的残差分布，代价在这里。

## 7. 跨卡外推：证明卡特征是必要的

只用一张卡训练（此时卡特征恒为零，无法估计），去预测另一张卡：

| 方向 | 行数 | scenario-equal MAPE | 中位 | p90 | 有偏方向 |
|---|---:|---:|---:|---:|---:|
| H800 训练 → 预测 4090 | 968 | **27.9%** | 15.6% | 62.1% | **+20.0%（系统性高估）** |
| 4090 训练 → 预测 H800 | 232 | 9.6% | 10.3% | 21.5% | +3.2% |

不对称很明显：4090 → H800 能用（9.6%），H800 → 4090 不能用（27.9%，还带 20% 的
系统性高估）。原因是数据量和覆盖：4090 有 1136 行 / 118 个 selector key，把 H800 的
92 个全包住了；H800 只有 325 行。

**这就是卡特征存在的理由**：不带卡维度、只用 H800 拟合，会把 4090 高估 20%。

一个反直觉的观察：拟合出来的卡特征系数在标准化空间里全部很小
（`is_rtx4090` = +0.001，最大的 `rtx4090_x_log2_gpu_count` = −0.032）。
意思是**两张卡放在一起训练时，卡差异几乎已经被 `analytic_reference` 的归一化和
28 个共享特征吸收掉了**，残余卡效应不到 3%。这对兼容性是好消息 —— 一套模型确实
能同时拟合两张卡。但它同时说明 §7 那个 20% 的偏差不是"卡物理差异"，而是
"H800 那 325 行没覆盖到 4090 的配置空间"。

## 8. 留出整个模型

跨两卡训练，留出一个 model_id，按卡分别评估：

| 留出模型 | 训练行数 | H800 MAPE | RTX 4090 MAPE |
|---|---:|---:|---:|

## 10. 已知边界

1. **模型规模不对齐**：H800 有 1.7B/4B/8B/14B，4090 有 0.6B/1.7B/4B，只重叠两个。
   卡特征只锚在两个规模上。
2. **H800 显存记录里 packing 全是 False**（325 行无一例外），4090 只有 54 行开
   packing。packing 的卡差异**没有证据**。
3. **4090 的行大多是温度或功耗受限的**。这对吞吐影响远大于峰值显存，但这不是一个
   干净时钟的样本population。
4. 保序上界是在拟合population上做的折外估计，不是新鲜留出集。§6 的准入数字应当
   当成真实表现的**上界**看。
5. `analysis_only`。要替换平台上那两个单卡冻结模型，需要 Go 侧读卡特征，是单独决策。

## 12. 更正：平台实际读的是哪套契约（2026-08-29 补）

我选契约的方法错了 —— 从 `offline_experiments/artifacts/` 里 grep H800 的显存
artifact，挑到了 `h800_bounded_memory_challenger_v2`，就当成平台在用的。**正确做法
是从 `server_integration` 往里追。** 追下来的链条是：

```
server_integration/build_test_vectors.py
  → H800UnifiedV3ThroughputV5Predictor
      → DEFAULT_MEMORY_ARTIFACT
          = artifacts/h800_unified_bounded_memory_candidate_v3.json
      → DEFAULT_THROUGHPUT_ARTIFACT
          = throughput_v5（双卡，已含 rtx4090）
```

三套显存契约并存：

| # | 契约 | 用在哪 | 特征 | 是否卡感知 |
|---|---|---|---|---|
| 1 | `analytic_reference_log_residual_ridge`（`physical_shares`） | H800 challenger 第一层、4090 老线、**本文** | 28 | 本文加了卡维度 |
| 2 | `bounded_memory_challenger_v2` selector 修正 | 研究分支，18 行 / 5 个 selector | 6 | 否 |
| 3 | **`physics_anchored_shared_bounded_residual`（V3）** | **平台在用** | 38 原始 → 144 基函数 + 独立 risk 头 | **否，`gpu_family: H800`，全文 0 次提到 card/4090** |

验证方式：`server_integration/testdata/test_vectors.json` 里显存中间量的键是
`center` / `risk`，带 `basis_kind` 字段，这是 V3 的形状；全文 `physical_shares`
出现 **0** 次。

### V3 能不能套到 4090 上

能，而且结构上比 #1 更适合跨卡：

| 有利条件 | 证据 |
|---|---|
| 容量是注入参数，不是硬编码 | `fit_h800_unified_resource_partial_v1.py` 全程把 `capacity_bytes` 当形参传 |
| 关键特征已按容量归一化 | `reference_fraction_of_capacity`、`activation_fraction_of_capacity`、`nonactivation_fraction_of_capacity` 等 5 个 |
| 解析参考与 #1 同源 | 都用 `h800_theory_basis.memory_basis`，本文已实测它在 4090 容量下正常工作（参考值中位数 21.0 GiB vs H800 85.1 GiB） |
| 需要的数据集 profile 统计两卡共有 | 6 个数据集在两张卡上都跑过 |

需要做的额外工作（比本文这套多）：

1. 把 4090 的 1136 行过一遍 V3 的 38 维原始特征构建器（含 profile padding 统计）
2. 联合重拟合 center 头（huber 损失 + 删失约束 + correction shrinkage + 144 基展开）
3. **risk 头也要重拟合** —— V3 的准入规则是
   `admit iff max(center, risk × upper_multiplier) ≤ 0.95 × capacity`，
   本文那套保序尾部替代不了它
4. 解掉 `fit_h800_unified_resource_partial_v1.py` 里对 H800 campaign id 的硬绑定
   （`campaign_id == "h800_unified_resource_evidence_20260809_v1"`）

### 本文哪些结论仍然成立

- 两张卡的记录能过同一套特征构建器，零失败（§3）
- H800 的 92 个 selector key 全部被 4090 覆盖，不存在无法对齐的配置组合（§3）
- 联合拟合不会让任何一张卡的中心精度退化到单卡水平以下（§5）
- 卡差异主要被解析参考的归一化吸收，残余不到 3%（§7）
- 不带卡维度、只用 H800 拟合会把 4090 系统性高估 20%（§7）—— 这条对 V3 同样是风险
- 4090 只有三个模型规模，留出一个就退化到 16.6%～19.3%（§8）
