## 1. 背景：改之前是什么样

现有 H800 显存模型三层：

| 层 | 做什么 | 拟合参数 |
|---|---|---:|
| ① `memory_basis()` | 9 个物理分量相加 = `M_analytic` | **0** |
| ② 28 维 ridge | `center = M_analytic × exp(β₀+zᵗβ)`，拟合目标 `log(observed_reserved / M_analytic)` | 28 + 截距 |
| ③ tail | `upper = center × exp(max(0, q95_success, oom_guard))` | 12 桶分位数 |

准入条件：`upper ≤ 0.95 × 容量`（H800 ≈ 132.84 GiB）。

**8/3 的 21-job fresh holdout 结果**（`h800_bounded_memory_v2_fresh_holdout_acceptance_v1.md`）：

| 指标 | 门槛 | 结果 | |
|---|---:|---:|:--:|
| false-safe OOM | 0 | 0 | 通过 |
| 场景等权 P05 upper coverage | ≥95% | 100% | 通过 |
| **admission recall** | ≥95% | **92.3%** | **失败** |
| center MAPE（次门） | ≤20% | 17.4% | 通过 |

安全性全过，卡在误拒。这次改造针对的就是误拒。

## 2. 三个修正

### ① `sequence = min(cutoff_len, profile_max)`

`memory_basis()` 第 251 行把 `cutoff_len` 直接当序列长度，所有 `mbs × sequence × ...` 都建在这上面。

**但运行时是动态 padding，不补到 cutoff。** 两处独立证据：

- 静态画像：`longcontext_16384`（cutoff=16384, mean=8283）的 `padding_utilization` 在 MBS=1 时**恰好 1.0**，随 MBS 增大降到 0.508。若补到 cutoff，该值会恒等于 `mean/cutoff = 0.5055` 且与 MBS 无关。
- 运行时 counter（`results/h800boundedv2fresh-2ab38aeb3d6f5279/metrics/summary.rank0.json`）：`computed_tokens/physical_batches = 1280.5`，而 `mbs × cutoff = 2 × 4096 = 8192` —— **实际只用了 15.6%**。

改后在目标失败 case 上：`M_analytic` **150.54 → 127.68 GiB**，实测 127.40（误差 0.2%）。

同时试过 `p99` 和 `E[batch_max]`，**都引入了新的不安全准入**（丢弃尾部会低估峰值），已排除。`max` 是唯一不丢信息的规则。

### ② Allocator 扩张 floor

`M_analytic` 求的是张量字节和，语义是 **allocated**；准入判的是 **reserved**。1367 条 success 行里比值中位 1.098，但 `lora+zero2+gc_off` 中位 1.412、最大 **2.181**。

**原来的模型从没建这个 gap**，它靠 ①（松的 anchor）虚高把它盖住了。收紧 anchor 后 gap 暴露成 false-safe。

```
upper = max(ridge_upper, M_analytic × 该桶 P95 扩张比)
```

**注意这里有一个我修过的错误**：第一版把 guard 乘在 center/upper 上，导致 8/2 recall 从 91.67% 掉到 50%。原因是 ② 的 ridge 拟合目标本来就是 `log(observed_reserved / anchor)`，**center/upper 已是 reserved 语义**，再乘就是双重计数。改成独立 floor 后正常。

**第二个修过的错误**：第一版把 floor 在容量处截断（理由「reserved 不能超容量」）。这是错的——截断把超容量的 floor 变成恒为 139.83 GiB 的常数，仍大于安全线 132.84，导致所有 14B Full 2 卡候选**无条件被拒**。改为不截断、原样上报。

### ③ tail 与 guard 的桶键加入 `gpu_count`

**这是本次最大的发现，也推翻了我最初的假设。**

我原以为需要按「模型状态占比 vs 激活占比」分层。做完发现 8/3 recall 一点没动（guard 从 1.243 反而涨到 1.247）。继续查才发现真正原因是桶键漏了 `gpu_count`：

```
full/zero3/gc_on 的 tail 残差：
  2 卡 (n=27)  q95 = +0.025  → ×1.025
  4 卡 (n=20)  q95 = +0.234  → ×1.264

full/zero3/gc_on 的 allocator 扩张比：
  混合 P95 = 1.240 ｜ 2 卡 = 1.074 ｜ 4 卡 = 1.262
```

8/3 那批 14B Full 全是 2 卡，却被收了 4 卡的风险费。**ZeRO 下每卡工作集随分片数变化，扩张比自然跟着变**，原桶键把这个维度扁平化了。加上后 guard 从 12 桶增至 20 桶。

## 5. 请重点审查的 6 点

### 5.1 ① 的上界性质是否成立

`profile_max` 是否对所有 MBS 都是有效上界？推理是「batch padded 长度 = max(batch 内 mbs 条) ≤ 全局 max」。

**请检查有没有破坏这个假设的机制**——例如 sortish batching / length grouping / 变长 collator 的对齐补齐（padding to multiple of N）。若存在按长度分组，则某些 batch 的 padded 长度分布会偏向长尾，虽仍 ≤ 全局 max，但会让「①收紧后仍安全」的论证变弱。

### 5.2 ② 的语义与独立性

- 核实「ridge 目标已是 reserved 语义，故 guard 不能作乘数」这个判断。证据：challenger 变体的 LoRA 行 `center/observed_reserved` 分布在 1 附近（1.247/0.759/1.235/1.349/1.235/1.287/1.100/1.415/1.136/0.802）。
- `max(ridge_upper, M_analytic × 扩张比)` 中两条路径**是否真的独立**？两者都以 `M_analytic` 为起点，可能存在隐含相关，导致 max 并不提供额外保障。

### 5.3 ③ 是否数据挖掘

`gpu_count` 这个维度是**从 8/3 失败模式逆推**出来的。物理理由（ZeRO 分片数影响每卡工作集）讲得通，但：

- 训练集只有 1/2/4 卡三档
- guard 分桶 12 → 20，每桶样本更少
- **LOSO upper coverage 已从 95.26% 降到 94.40%**
- guard 自身 LOSO reserved coverage 92.03%，且有 12 行因桶样本不足而 `unavailable`

请判断这是真实机制还是过拟合。**若判定为过拟合，请给出如何用现有数据区分二者的方法。**

### 5.4 残留的 1 个不安全准入

```
8B LoRA / 2卡 / ZeRO-2 / GC off / MBS=1 / cutoff=32768 / seq=12513
  M_analytic  76.74 GiB
  floor       76.74 × 1.680 = 128.92 GiB
  安全线      132.84  →  准入
  实测        137.56  →  实际不安全
```

需要的扩张比 `137.56/76.74 = 1.793`，而该桶（`lora,2,false,2`，n=37）**P95 = 1.680、max = 1.685** —— 超出全部校准范围。

`lora+zero2+gc_off` 是 20 桶里方差最大的（2卡 P95=1.680；4卡 P95=2.067, max=2.181）。

请评估三个处置方案：**该桶改用 max 而非 P95**（1.685，仍不足）／**该桶 fail-closed 不给预测**／**补该桶实验点撑开经验范围**。
