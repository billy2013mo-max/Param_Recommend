# Packing 显存与吞吐模型最终验收实验计划：4～7 卡

日期：`2026-08-10`

状态：业务数据已下载并冻结；GPU 实验尚未启动；本文件不是执行授权。

机器可读设计：`offline_experiments/artifacts/h800_packing_final_4to7gpu_experiment_design_v1.json`

## 1. 直接结论

这一轮可以把 Packing 做成一次完整验收，但不能只把 `平均每 pack 样本数` 直接替换为 unpacked MBS 后看几个点。最终方案会先把这个最简单假设作为强制基线验证：

- T0：直接令 `virtual_mbs = 平均每 pack 样本数`，不增加任何 Packing 吞吐系数；
- T1：如果 T0 不够准，只增加一个全局 Packing 倍率；
- T2：只有 T1 仍不够准时，才使用少量已有派生量做正则化修正。

因此实验会明确回答用户最关心的问题：Packing 和 unpacked MBS 相同时，吞吐是否近似相等；如果不相等，差异能否用一个稳定系数表示。

产品侧不增加用户填写字段，也不保存逐样本 Packing 元信息。上传数据集时只在六个固定 cutoff 上保存少量聚合量：

- cutoff：`1024、2048、4096、8192、16384、32768`；
- 平均每 pack 样本数；
- pack 样本数 P99 和最大值；
- pack 填充率；
- 样本截断率；
- token 保留率。

推荐时继续使用现有配置字段，包括模型、训练方式、卡数、ZeRO、GC、cutoff 和目标 GBS。需要重拟合的是系数，不是产品输入。

最终发布范围明确限制为：H800 140GB、纯文本 SFT、Qwen3 8B/14B/32B、LoRA/FULL、ZeRO-2/3、GC 开/关、4/5/6/7 卡、BF16、无 offload、neat packing 且物理 MBS 固定为 1。

## 3. 当前实现缺口

当前代码还不能直接执行 5、6、7 卡：

- `candidate_generator.py` 的支持卡数是 1/2/4；
- `run_job.py` 会拒绝 1/2/4 之外的卡数；
- `scheduler.py` 的校验和分配只实现了 1/2/4 卡。

因此正式实验的第一个阶段不是建模，而是执行器门禁：

1. 将本轮独立 campaign 的合法卡数改为 4/5/6/7；
2. 5～7 卡任务全部使用单机整池独占，不与其他任务并发；
3. 在真正训练节点采集 GPU UUID、容量和 `nvidia-smi topo -m`；
4. 冻结一组拓扑嵌套的物理 GPU mask，4 卡 mask 必须是 5/6/7 卡 mask 的子集；
5. 每个卡数各跑一条 Packed 和 Unpacked 两步 canary，共 8 个任务；
6. 检查 world size、rank 数、每 rank ledger、原始样本计数、token 计数和 Packing 语义。

当前会话环境无法连接 NVIDIA driver，所以这里只能冻结计划和数据，不能把本机当前 GPU 状态写成已通过。正式训练节点的硬件 preflight 必须作为 Phase 0 的输入重新采集。

## 4. 实验总体结构

### Phase 0：4～7 卡执行器 canary

- 8 个任务；
- Qwen3-1.7B LoRA；
- 每个卡数各 1 个 Packed、1 个 Unpacked；
- 0 warmup + 2 measured optimizer steps；
- 只验证执行与计数语义，不进入模型拟合。

任一卡数出现 rank 缺失、GPU mask 漂移、样本 GBS 对账失败或 Packing attention/loss 语义失败，后续实验全部停止。

### Phase 1：直接验证 `n_pack = virtual MBS`

固定 Qwen3-8B LoRA、ZeRO-3、GC 开启，选择三种平均 pack 占用：约 1.98、4.93、7.27。

每个画像在 4/5/6/7 卡上比较：

- Packed，物理 MBS=1；
- Unpacked，MBS 向下取整到 `floor(n_pack)`；
- Unpacked，MBS 向上取整到 `ceil(n_pack)`。

同一卡数、同一画像内，目标 GBS 同时保证两个整数 MBS 对照可整除，并让 Packed 的平均 GBS 偏差不超过 5%。这一步共有 12 个 matched group、36 个物理 arm。

每个 arm 先运行一次较长的正式测量。如果组内任一 arm 的分块 CV 超过 3%，或观测 Top-2 差距小于 3%，则整组增加一次独立重复，不允许只补对自己有利的一边。最多增加 36 个任务。

这一步会按以下顺序决定模型复杂度：

1. T0 直接替换：Packing 预测值等于 unpacked 模型在 `MBS=n_pack` 处的预测值；
2. T1 全局倍率：在 T0 上只乘一个 Packing 系数；
3. T2 小残差模型：只允许使用 `log(n_pack)`、填充率、cutoff 占模型上限比例、`log(卡数)`、ZeRO-3 和 GC。

使用按业务数据源分组的折外验证，选择第一个通过门槛的最简单模型。若 T0 通过，就不增加 Packing 吞吐系数。

### Phase 2：Packing 显存边界

不再新增 160 个全因子排序拟合任务。吞吐模型复用已有 Packing 历史数据，并只用 Phase 1 补充 4～7 卡 virtual-MBS 关系。

显存边界保留 32 个起始任务，但明确拆成两组：

- 16 个拟合边界：PF05、Qwen3-32B FULL、4/5/6/7 卡乘 4 个 ZeRO/GC 机制；允许用于显存中心和风险头校准；
- 16 个前瞻边界：PH04、Qwen3-32B FULL、4/5/6/7 卡乘 4 个 ZeRO/GC 机制；必须在模型冻结后运行，只能用于最终 MAPE、放行率和 OOM 放行率。

每组从 8K cutoff 开始，并按预冻结阶梯执行：

- 成功则只向更重 cutoff 补一步；
- OOM 则只向更轻 cutoff 补一步；
- 获得成功/OOM 夹逼或完成两步后停止。

初始 32 个任务，每组最多向相邻 cutoff 增加 16 个，因此总上限为 64 个。拟合边界必须先完成，随后冻结最终模型，再运行 PH04 前瞻边界。OOM 是右删失观测：只表示需求超过当时可用显存，不能把卡容量当成精确峰值加入 MAPE。

### Phase 3：离线拟合并冻结

显存候选固定为三层：

- M0：当前 V3 共享中心的 4～7 卡外推基线；
- M1：共享中心加受正则约束的 Packing residual；
- M2：M1 再加入 Packing 与卡数、ZeRO、GC 的交互。

只用成功任务拟合中心。OOM 只进入安全准入头。按业务数据源做分组折外验证，并采用“最简单通过者”规则，避免为了降低训练集误差堆叠 Packing 特例。

吞吐同时冻结。这里不是从零重建吞吐模型，而是使用历史 Packing 证据和 Phase 1 更新现有模型：

- absolute effective samples/s 中心；
- 同场景 pairwise rank head；
- T0/T1/T2 中选出的 Packed 相对 unpacked transfer 关系。

在读取 PH01～PH06 的任何 GPU 结果前，必须冻结：模型系数、特征、风险倍率、准入线、所有候选预测、PH 数据角色和评估代码 SHA。

### Phase 4：四源排序盲测与前瞻显存边界

PH01、PH03、PH05、PH06 各运行 4 个卡数乘 4 个机制，共 64 个 Packed 物理 arm。每个 arm 先运行一次；只有分块 CV 超过 3% 或 Top-2 差距小于 3% 的场景才整组补一次，最多增加 64 个任务。

64 个 arm 在全部成功且无 tie 时可形成 32 个排序场景和 192 个候选对：16 个固定卡数的机制排序场景，以及 16 个固定机制的 4～7 卡排序场景。这已经超过最终门槛，不再增加 72 个重复的 Unpacked holdout 对照。

PH04 按 Phase 2 的前瞻边界协议单独提供 OOM 验收；PH02 只允许在 GPU 启动前发现冻结源损坏时替换对应角色。所有 PH 结果都不得回写本版系数或安全余量。

## 5. 测量口径

### 5.1 显存

- 每次运行先取所有 rank 的 CUDA max reserved，再取最大值；
- 同一物理 arm 的中心真值取成功重复的中位数；
- 安全判断取成功重复的最大值；
- 任一重复 OOM，或同一 arm 出现一次成功一次 OOM，均按不安全处理；
- OOM 不进入中心 MAPE。

报告四项主指标：

1. Packing 成功配置的 source-equal MAPE；
2. Packing 成功配置的普通 MAPE 和 P90 APE；
3. 实际安全配置放行率；
4. 实际 OOM 配置放行率。

若 OOM 数为 0，OOM 放行率必须写 `N/A`，不能写 0%。

### 5.2 吞吐

每个正式性能任务使用 3 warmup + 20 measured optimizer steps，并整节点独占。吞吐真值使用实际 ledger 中消费的原始样本数除以稳态耗时，不能用 `n_pack_mean × pack 数` 代替运行时真值。`n_pack_mean` 只作为预测输入。

主排序单位有两类：

- 同一卡数下的 ZeRO/GC 候选集；
- 同一机制下的 4/5/6/7 卡候选集。

实际吞吐差小于 2% 的候选对记为 tie，不进入主 pairwise accuracy，但必须报告 tie 覆盖率。

Top1 regret 的计算方式用直白口径表示：

> `Top1 regret = (该场景实际最快吞吐 - 模型推荐配置实际吞吐) / 该场景实际最快吞吐`

Hit@10% 表示模型推荐配置的实际吞吐距离该场景真正最快配置不超过 10%。

## 6. 最终验收门槛

### 6.1 Packing 显存

| 指标 | 门槛 |
|---|---:|
| 前瞻精确成功显存 arm | 至少 40 个 |
| 前瞻实际 OOM arm | 至少 24 个 |
| Source-equal MAPE | 不超过 8% |
| 普通 MAPE | 不超过 8% |
| P90 APE | 不超过 15% |
| 实际安全配置放行率 | 至少 85% |
| OOM 配置放行率 | 必须为 0% |
| OOM 放行率单侧 95% 上界 | 不超过 12% |

显存前瞻总体由 Phase 4 的 64 个排序 arm 和 PH04 前瞻边界共同组成；PF05 拟合边界不进入这些指标。最后一项避免只看 `0/N`。如果实际 OOM 不足 24 个，显存安全验收不完成，必须按预冻结的 PH04 相邻 cutoff 阶梯继续补数，不能把分母不足解释成通过。

### 6.2 Packing 吞吐与排序

| 指标 | 门槛 |
|---|---:|
| 至少有 3 个成功候选的排序场景 | 至少 24 个 |
| 非 tie 候选对 | 至少 120 对 |
| 总 pairwise accuracy | 至少 85% |
| 固定卡数机制排序 accuracy | 至少 80% |
| 4～7 卡扩卡排序 accuracy | 至少 80% |
| Top1 平均 regret | 不超过 5% |
| Top1 P90 regret | 不超过 10% |
| Hit@10% | 至少 90% |
| 拟合源分组折外 transfer MAPE | 不超过 12% |
| Packed 绝对 samples/s 的 group-equal MAPE | 不超过 12% |
| 稳态窗口分块 CV 的 P90 | 不超过 3% |

这些排序指标只在真实成功候选之间评价吞吐模型。另外单独报告端到端结果：先经过预测显存门禁，再由吞吐模型选 Top1；端到端 regret 会把显存模型误拒最快候选造成的损失也计算进去。

## 7. 任务预算与停止规则

| 阶段 | 基础任务数 | 条件追加上限 |
|---|---:|---:|
| Phase 0 执行器 canary | 8 | 0 |
| Phase 1 virtual-MBS 对照 | 36 | 36 |
| Phase 2 显存边界 | 32 | 32 |
| Phase 4 Packed 盲测 | 64 | 64 |
| 合计 | 140 | 132 |

如果所有边界 cell 都需要第二步、所有吞吐噪声条件都触发，硬上限为 272 个任务。若 Phase 1 和 Phase 4 全部做两次、但边界不追加，则是 240 个任务。该上限不是必须跑满：

- 显存边界获得成功/OOM 夹逼后立即停止；
- 第 2 次吞吐重复只能由分块 CV 或 Top-2 小差距触发；
- 任何静态 GBS 不可控候选都不进入 GPU 队列；
- 任何实际 OOM arm 不做无意义吞吐重复；
- 基础设施失败只能原配置重试，不能换配置后删除失败结果。

按现有 H800 短探针通常约 1～8 分钟的历史范围，基础轮应预留约 12～30 个整节点小时；32K FULL 和反复初始化可能使实际耗时更高。该区间是工程估算，不是数据观测结论。正式 materialize 时应根据最新实测中位耗时重新生成 wall-time 预算。

## 8. 最终决策规则

- 所有门槛通过：发布本文件声明的 4～7 卡支持域；
- T0 通过：直接使用 `n_pack` 替代 unpacked MBS，不增加吞吐系数；
- T0 失败但 T1 通过：只增加一个全局 Packing 吞吐倍率；
- 只有 T2 通过：使用预注册的少量派生特征，不增加新的产品元信息；
- 某个卡数、训练方式或模型范围失败：只能发布预先声明且样本量独立达标的子域；
- 任一 OOM 被错误放行，或 OOM 数不足：Packing 自动显存准入不发布；
- 所有吞吐候选失败：显存模型可以单独发布，Packing 吞吐推荐继续 shadow；
- Holdout 结果不得用于“修一下再重算本轮指标”。任何修改都必须另起版本和新 holdout。
