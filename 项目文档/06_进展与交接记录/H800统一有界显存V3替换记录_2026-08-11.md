# H800 统一有界显存 V3 替换记录

> 日期：2026-08-11  
> 结论：默认推荐入口已经切为“统一有界显存 V3 + 结构化吞吐 V5”；旧
> physical-shares + V4b 只保留为显式整链路回滚；自动训练执行保持关闭。

## 1. 要解决的问题

旧显存门禁的中心误差和全局安全上界会造成额外误拒，且当前回放中仍存在 OOM
错放。业务目标不是继续维护多条 LoRA/FULL 人工路由，而是提供一个端到端、可
泛化的显存模型，再把安全候选交给吞吐排序器。

本次替换采用统一有界 V3：所有受支持机制共享一个 reserved 中心模型和一个独立
风险模型，不使用历史锚点放行。源 artifact 保持 immutable，不原地修改系数。

## 2. 当前模型与准入公式

设解析参考为 $M_{\mathrm{ref}}$，中心头和风险头的 log-ratio 校正为 $f_c(z)$、
$f_r(z)$：

$$
C=M_{\mathrm{ref}}e^{f_c(z)},\qquad
R=M_{\mathrm{ref}}e^{f_r(z)}.
$$

当前上界和准入规则为：

$$
U=\max(C,1.0170738699R),
$$

$$
A_{\mathrm{memory}}
=\mathbb I[U\le142{,}635{,}080{,}089.6\ \mathrm{bytes}].
$$

数学事实：给定 $C$、$R$ 和冻结倍率后，$U$ 与准入结果唯一确定。

模型假设：物理参考未捕获的主要误差可以在 log-ratio 空间用有界特征校正；独立
风险头能利用 success 尾部和右删失 OOM 下界学习更适合准入的上侧风险。

工程解释：中心负责“预测多少”，风险头负责“按多少放行”。这里的 $U$ 是校准
准入上界，不是 P95。

## 3. 替换依据

### 3.1 531 行同集回放

数据包括 425 个精确 success、106 个 OOM、49 个来源。以下是同一开发/回放集合
上的经验观察：

| 模型 | 来源等权中心 MAPE | 行级中心 MAPE | 中心 bias | P90 APE | 安全放行率 | OOM 放行率 |
|---|---:|---:|---:|---:|---:|---:|
| 旧门禁 | 11.46% | 14.97% | +4.36% | 33.42% | 379/394 = 96.19% | 2/106 = 1.89% |
| 统一 V3 | 8.77% | 7.77% | -2.08% | 16.71% | 381/394 = 96.70% | 0/106 = 0% |

在这三个业务主指标上，V3 在当前回放集合中都优于旧门禁。该结论是数据观察，
不是“任意未来数据都更好”的数学保证。

### 3.2 独立业务盲测当前进度

计划 60 个任务，目前形成 35 个有效观测：34 个 success、1 个 OOM，剩余 25 个
尚未形成有效观测。

| 指标 | 当前值 |
|---|---:|
| 数据集等权中心 MAPE | 14.96% |
| 中心 bias | +9.88% |
| 行级中心 MAPE | 13.58% |
| 中心 P90 APE | 33.11% |
| 安全配置放行率 | 21/30 = 70% |
| OOM 放行率 | 0/1 = 0% |

当前盲测支持“没有观察到 OOM 错放”，但 OOM 分母只有 1，不能据此声称 OOM
风险已经被充分验收。替换后仍需继续做线上/离线回放监控。

## 4. 具体 case

配置：Qwen3-14B、FULL、short-512、4×H800、ZeRO-2、GC 关、MBS=4、
GBS=64、packing=false。

| 量 | 旧门禁 | 统一 V3 |
|---|---:|---:|
| 中心 | — | 117.17 GiB |
| 准入上界 | 134.80 GiB | 121.15 GiB |
| 132.84 GiB 安全线距离 | -1.96 GiB | +11.69 GiB |
| 决策 | 拒绝 | 放行并进入吞吐 V5 |

V3 在该 case 中不是通过降低统一安全线放行，而是使用新中心和独立风险头重新
估计上界。该候选进入吞吐 V5 后得到 3806.58 tokens/s，排在同组第 3。

同组最终第一名是 ZeRO-2、MBS=8、GC 开，V5 预测为 4691.48 tokens/s；第二名
是 ZeRO-3、MBS=8、GC 关，预测为 4620.81 tokens/s。旧 V4b 会把后者排在第一，
因此当前替换确实改变了排序结果，不是只替换版本标签。

## 5. 工程改动

| 改动 | 文件 |
|---|---|
| 新增默认稳定入口和回滚开关 | `offline_experiments/scripts/h800_resource_predictor.py` |
| 接入 V3 准入和吞吐 V5 单输出排序 | `offline_experiments/scripts/h800_unified_v3_throughput_v5_predictor.py` |
| 冻结 V3 运行时特征构造来源 | `offline_experiments/scripts/fit_h800_unified_resource_partial_v1.py` |
| 业务推荐入口切换到稳定入口 | `real_business_validation_20260730/scripts/run_text_recommendations.py` |
| 新增 V3 + V5 接入、原生输出对账和回滚测试 | `offline_experiments/tests/test_h800_unified_v3_throughput_v5_predictor.py` |
| 候选生成/Packing 交接测试切到默认入口 | `offline_experiments/tests/test_candidate_generator.py`、`test_packing_aware_candidates.py` |

没有修改以下旧文件和 artifact：

- `offline_experiments/scripts/h800_physical_v4b_predictor.py`；
- `offline_experiments/artifacts/h800_challenger_modeling.json`；
- `offline_experiments/artifacts/joint_throughput_modeling.json`；
- `offline_experiments/artifacts/h800_unified_bounded_memory_candidate_v3.json`。

这样可以避免影响仍绑定旧源码哈希的运行中实验，也保留可审计回滚路径。

## 6. 验证结果

- V3 + V5 接入、V5 原生输出对账与回滚单元测试：6/6 通过；
- 候选生成和 Packing 交接回归：39/39 通过；
- 冻结 canary `h800ubc3-b09d1d1caf98822c` 对账：reference、中心、risk guard、
  准入上界与冻结 V3 逐字段一致到浮点精度；
- 业务入口回归：300 个候选、6 个业务组均生成有效推荐报告；
- 当前业务报告 schema 已变为
  `sft_h800_unified_v3_throughput_v5_prediction/v1`；
- 示例四候选排序逐项对账 V5 原生 Predictor：有效吞吐和 step time 完全一致；
- 当前默认报告不再包含 `throughput_legacy_memory_binding`，也不加载
  `joint_throughput_modeling.json`。

检查中还发现，当前 `structured_throughput_modeling.py` 因 2026-08-09 增加纯分析
扩展而与 2026-07-28 artifact 的全文件哈希不一致。代码对当前文件与审批时冻结
副本做了抽象语法树级推理前缀对账：除版本标签外，运行时基函数一致；如果后续
推理前缀发生变化，当前入口会 fail closed，而不是静默绕过绑定。

吞吐 V5 冻结产物记录的 H800 固定留出结果为：场景等权 MAPE 14.98%、成对排序
准确率 90.39%、Top-1 regret 1.75%。完整数据集留出为 19.49%、85.40% 和
1.24%。这些是已有实验观察，不是未来业务分布上的误差保证。V5 不把
`dataset_id` 作为拟合身份特征，而是用该标识加载静态长度和工作量画像。

## 7. 回滚和后续验收

显式整链路回滚命令：

```bash
PYTHONPATH=offline_experiments/scripts \
python offline_experiments/scripts/h800_resource_predictor.py request.json \
  --memory-gate legacy_physical_v1 \
  --output /tmp/h800_legacy_rollback.json
```

后续按以下顺序继续：

1. 继续收集独立业务数据，优先增加 OOM、接近安全线和当前误拒的配置；
2. 固定报告三个主指标：中心偏差、安全放行率、OOM 放行率；
3. 记录被 V3 拒绝但实测安全的 case 距离安全线多远，避免只靠整体降阈值处理；
4. 与真实吞吐测量联合验收 Top-1 regret，并检查推荐是否达到可运行最优配置的
   90%；
5. 在 OOM 分母和端到端吞吐证据充分前，保持
   `automatic_execution_allowed=false`。
