# DeepSpeed SFT 训练配置推荐器 Native 标定进展报告

**日期**：2026-07-27
**状态**：阶段性进展报告(**非收尾**);标定证据已从 0 建立到可做有界拟合,但距离"可发布标定 profile"仍有明确差距,详见第 5 节。

---

## 1. 一句话概括

过去几天在 8×H800 上跑了 5 轮 + packing 共约 300 个受控实验,把**可用于标定的 native 实测证据从 0 建到 460 个**,12 个配置族里 **11 个已满足"可进入有界拟合"的门槛**。当前**排序能力**(区分配置好坏)已达到 top-1 ≈ 0.72 / 两两 ≈ 0.75 的水平。但"可发布标定"这一更高门槛尚未达到,且部分卡点**不是靠继续跑实验能解决的**(见第 5 节)。

---

## 2. 本阶段做了什么

在 8×H800(仅用空闲卡,不干扰同机其他任务)上,分批跑了受控 SFT 实验,每一轮都针对上一轮审计暴露的**具体覆盖缺口**:

| 轮次 | 目的 | 规模 |
|------|------|------|
| 密度 | 补吞吐候选密度 | 48 |
| holdout r1 | 建立留出集(holdout)角色覆盖 | 50 |
| holdout r2 | 补足每 selector ≥2 切分单元 + mbs 边界 | 99 |
| calib r3 | 补标定(calibration)角色覆盖 + 变化性 | 116 |
| packing | packed vs unpacked 效果对照(ABBA 四元组) | 80 |
| gap r5 | 收口剩余 selector 的边界/行数 | 16 |

**执行纪律**:每批实验都经过 fail-closed 审批(冻结 design SHA → 干跑校验 queue/provenance/manifest 全绿)才启动;进程组超时清理无 GPU 残留;全程未改动任何实测数据、未放松任何校验。

## 3. 当前如何建模、如何设计实验、如何用实验做校准

> 本节回答方法论层面的三个问题:建模、实验设计、校准闭环。

### 3.1 建模:解析骨架 + 实验校准的比值修正

整体范式是 **"解析公式(analytic backbone)+ 基于实验的比值校准"**,不是纯数据拟合、也不是纯理论:

- **解析骨架**:先用物理量把每个配置的资源占用/吞吐算出一个解析基线(`h800_theory_basis.py`),映射到与 CPU 侧规划器同一套物理量:模型状态、激活、logits、ZeRO 工作区/常驻状态、算子 FLOPs、张量/优化器通信、集合通信载荷。这一步**不拟合、不碰 GPU**,只是把实测观测投影到这些物理量上,产出 `theory_only` 的 bootstrap 基础。
- **校准修正**:实测值 / 解析值 得到一个"修正比值",再用一个**对数线性 ridge 回归**去拟合 `log(实测/解析)`(或直接 `log(吞吐)`、`log(显存)`)随配置特征的变化。当前特征是 **11 维对数线性**:`intercept, log(参数量), log(序列长), log(GBS), log(卡数), log(mbs), is_full, gc, zero2, zero3, packing`。**无交互项**(见 §5.3 的尝试与负结果)。
- **显存与吞吐分开建模**:显存用于**可行性门控**(预测 P95 ≤ 0.95×显存容量才允许),吞吐用于**排序**。OOM 观测按右删失(下界不等式)处理,绝不当作峰值实测。

### 3.2 实验设计:分区角色 + 全局场景留一(LOOCV)

实验不是随便跑,而是围绕一套**可交叉验证、防泄漏**的结构设计:

- **科学切分单元**:`(模型, 训练方式, 数据集, 目标GBS)` 为一个场景;配置族 selector = `(train_type, zero_stage, gc)`。
- **两种角色**(`calibration_partition.role`):
  - `calibration`(标定)——参与拟合;
  - `holdout`(留出)——**完全不参与拟合**,只用于独立验收;
  - 二者的切分单元**互不重叠**(model_length_disjoint 策略),避免信息泄漏。
- **每 selector 的最低覆盖门槛**:标定 ≥6 可行性 + ≥4 吞吐行;留出 ≥4 + ≥2;且需 ≥2 个独立切分单元、mbs 覆盖支持域 `{1,2,4,8,16}` 的边界(有 success 且有 OOM 或 mbs=16 成功)。
- **mbs 域**:`{1,2,4,8,16}`(域外如 mbs=32 仅作边界探测,不进标定——见 §6.1)。
- **每一轮实验都由审计暴露的缺口驱动**(§2 表):审计报告哪个 selector/角色/切分单元覆盖不足,就针对性补哪批,而不是泛跑。

### 3.3 校准闭环:实验 → 导出 → 恢复侧车 → 就绪审计 → 排序评估

一条**全程 fail-closed、可复现**的流水线:

1. **跑实验**(`run_job.py`,原生 v2 执行指纹:GPU UUID/拓扑/运行时逐 rank 存证)。
2. **导出观测** `export_h800_observations.py` → `canonical_h800_observations.jsonl`;只有**完整指纹 + 合格**的才标 `calibration_evidence_eligible`。
3. **恢复侧车** `recover_h800_historical_evidence.py`:逐条重算 source SHA,判定每条能否作标定候选(`calibration_candidate`),从不放松校验。
4. **就绪审计** `audit_h800_calibration_readiness.py`(schema v6):统计每 selector 是否 `ready_for_profile_candidate`、是否 `calibration_publishable`。
5. **排序/预测评估** `stage_decisions.py`:**全局场景留一交叉验证**(leave-one-(model,train,dataset,gbs)-scenario-out),报告 top-1 / 两两 / MAPE。
6. **验证性质**:每一步都标 `bootstrap / theory_only / nonpublishable`——**当前结果明确是"未达发布标准"的诚实中间态**,不是可直接上线的 profile。

**校准哲学**:解析骨架保证外推不失控,实验只提供有界的修正比值;宁可 fail-closed 判"未就绪",不放松校验换取好看的绿灯。

## 4. 排序/预测能力(诚实指标,LOOCV)

> 这是"能不能识别不同配置好坏"的直接衡量,也是本项目最看重的能力。

| 指标 | 数值 | 说明 |
|------|------|------|
| 吞吐候选 **top-1 准确率** | **0.724** | 选出最优配置的准确率 |
| 吞吐候选 **两两比较准确率** | **0.754** | 任意两配置排序正确率 |
| 显存预测 MAPE | 0.177 | |
| 吞吐预测 MAPE | 0.324 | 绝对值仍不准(已知,非本阶段目标) |
| profiler 固定分区 MAPE | 0.050 | |

**结论**:符合此前定的方向——绝对数值不准,但**相对排序基本正确**。排序能力已具备实用价值(识别配置优劣),但尚未达到严格发布标准(如 top-1 ≥ 0.9)。

> ⚠️ 注:上表数值来自 `stage_decisions.json`(7-21 生成,207 个吞吐配置)。见 4.1 的重算与诊断。

### 4.1 排序问题的深入诊断(2026-07-27,纯 CPU,零 GPU)

**关键发现:提升排序的正道是改进模型/特征,不是堆实验。**

1. **重算**:把这几天新增的 460 个 native 点全部纳入后重跑 `stage_decisions.py`——**上表 top-1 = 0.724 纹丝不动**(0.7237 → 0.7237)。原因:新增点多为显存/holdout/packing 角色,进不了吞吐排序回归的训练集。**盲目多跑实验对排序无效**。
2. **真实水平更低**:用全部数据在**只读诊断**里重算(配置数 207 → 613,更多样),baseline top-1 实为 **0.556**——更丰富的配置暴露了线性模型的不足,这才是当前真实排序水平。
3. **瓶颈是模型表达力**:排序回归是 11 特征对数线性 ridge,**无任何交互项**。加 8 个交互特征(如 参数量×序列长、zero3×序列长)在**原始配置口径**下 top-1 **0.556 → 0.611(+5.6%)**——但注意此增益在生产聚合口径下不成立(见 §4.3)。
4. **特征工程有天花板**:再加 6 个 LoRA 专属交互特征反而**降到 0.569**(过拟合——每 fold 训练配置有限,特征维度上限约 19)。
5. **LoRA 是错误重灾区**:错误 fold 中 **LoRA 占 23、full 仅 9**(2.5 倍)。但加 LoRA 特征救不了,提示 LoRA 排不准的根因可能是**数据标签冲突**(此前已发现 LoRA+ZeRO3 存在"同配置既成功又 OOM"),而非特征不足。

**诊断产物**:`/tmp/diag_ranking.py`(只读,未改任何生产代码/数据)。

### 4.2 诊断驱动的针对性实验(2026-07-27,45 个 job)—— 二次实证"数据侧已到头"

按"缺的补缺、不一致的重跑"执行:
- **A) 10 个标签冲突配置各重跑 2 次**(同配置既有 success 又有 OOM):**20/20 全部 OOM**。结论确凿——**原来的 success 是不可复现的异常**(疑似早期共享机内存宽松时侥幸跑过),真相是这些配置在当前环境 OOM 不可行。这解答了 4.1(5)的 LoRA 冲突之谜:**是数据里混了假 success,不是模型预测错**,应以 OOM 为准清洗。
- **B) 9 个低候选(≤3)排错场景补候选**:25 个候选(13 success + 12 OOM)。
  - 过程中发现并修复一个 bug:候选来自聚合配置、缺 `model_path`,首跑 25 个全崩溃 → 回填后重跑(未把失败当成功)。
- **重算 `stage_decisions.py`(1591 行)后**:top-1 = **0.7237 → 0.7237(仍纹丝不动)**,pairwise 0.754→0.759,MAPE 基本不变。

**二次实证结论**:补候选对官方排序分数**无提升**(第一次是 +460 native 点无效,这次是针对性补候选仍无效)。**数据侧已到头**;数据清洗改善的是**正确性**(10 个假 success 已判定为 OOM 真相),不是排序分数。唯一被验证能提升排序的手段是 **§4.1(3) 的交互特征(离线 +5.6%,零 GPU)**。

**产物**:`runtime/pipeline/pending-rerun-gapfill.jsonl`、`/tmp/conflict_templates.json`。

### 4.3 交互特征落地尝试 —— **诚实的负结果,已回滚**

§4.1(3) 离线诊断显示加 8 个交互特征能 +5.6%,遂将其落地进生产代码 `stage_decisions.py`(`resource_features` 11→19 维),测试套件全过。但**用生产口径重算后 top-1 反而下降**:

| 指标 | 11 特征 | 19 特征(交互) | 变化 |
|------|--------|-----------|------|
| **top-1** | **0.7237** | **0.7105** | **−0.013** ❌ |
| 两两比较 | 0.7585 | 0.7415 | −0.017 ❌ |
| 吞吐 MAPE | 0.3227 | 0.2869 | −0.036 ✅(改善11%)|
| 显存 MAPE | 0.1756 | 0.1783 | +0.003 |

**为什么离线 +5.6%、生产 −1.3% 相反?** 评估口径不同:离线诊断用 **617 个原始配置**(每场景候选多),生产 `stage_decisions` 用**聚合配置**(78 个 fold 里 52 个只有 2 个候选)。候选极少时,19 维特征相对训练量**过拟合**,简单模型反而更稳。**离线结论无法迁移到生产的少候选口径。**

**处置**:top-1 是最看重指标,它降了 → **已回滚**到 11 特征(代码 + 测试恢复,已确认;吞吐 MAPE 的改善不足以抵消排序退化,更不能掩盖 top-1 下降)。这是一条被证否的路。

## 5. 当前效果如何、问题在哪里

### 5.1 当前效果(诚实结论)
- **可行性/显存侧**:显存预测 MAPE ≈ 0.176,配合 P95×0.95 门控可用于**过滤明显会 OOM 的配置**——这一侧基本可用。
- **排序侧(核心目标)**:吞吐 top-1 ≈ **0.72**(官方聚合口径)/ **0.58**(全量原始口径),两两 ≈ 0.75。**能识别"明显好/明显坏",但选不准"最优的那一个"**,离高置信推荐(top-1 ≥ 0.9)有明显距离。
- **吞吐绝对值**:MAPE ≈ 0.32,数值不准(本就非目标)。
- **就绪度**:12 个配置族 11 个 `ready_for_profile_candidate`;`calibration_publishable` = False。

### 5.2 问题到底在哪里(已定位,分三层)
1. **模型表达力不足(主因)**:排序回归是 11 维对数线性,无交互项;但**加交互项在生产少候选口径下过拟合**(§4.3)。→ 线性模型 + 少候选评估口径,**特征工程已顶到天花板**。
2. **数据侧已到头**:两次实证(+460 native、+45 针对性)对排序**零收益**;补数据不再是杠杆。数据清洗只改善正确性(10 个假 success→OOM)。
3. **LoRA 是错误重灾区**(占错误 2/3),根因是**数据标签冲突**(同配置既成功又 OOM,已证实 20/20 重跑为 OOM),而非特征——需以 OOM 清洗后再评估。

### 5.3 要真正提升排序,可能需要的更大改动(需先与团队对齐)
- **换评估/建模口径**:当前"聚合配置 + 少候选 LOOCV"既是评估口径也限制了模型复杂度;若改用全量原始配置口径,交互特征的 +5.6% 才能兑现。
- **换模型族**:线性 ridge → 单调性约束的树模型/GAM,可在不爆炸维度的前提下吃下交互——但属于架构级改动。
- 这两项都超出"跑实验/调特征"范畴,应作为独立决策。

## 7. 还差什么(为什么"远没到收尾")

### 7.1 排序能力未达发布标准(核心)
- 见 §5:模型表达力已是主瓶颈,数据侧到头,LoRA 标签冲突待清洗。提升需架构级改动(换口径/换模型族),非跑实验可解。

### 7.2 **不是**跑实验能解决的(需要单独决策/流程动作)
1. **第 12 个配置族(lora / zero3 / gc=False)** 无法达标,原因是**数据污染而非缺实验**:早期密度实验里有一个 `mbs=32` 的点(超出支持域 {1,2,4,8,16}),它令该 selector 的 mbs 边界完整性检查判负。修法是**排除或重分类那一个数据点**——属于数据范围/口径决策。
2. **`calibration_publishable` = False**,存在**硬天花板**:
   - `approved_holdout_acceptance_report_not_supplied`:需要一份独立的 holdout 验收报告(**签署/流程动作**);
   - `historical_recovery_is_not_native_v2_publication_evidence`:发布锚点是**架构性**限制;
   - packing 的 holdout 门槛需 ≥2 个切分单元,但可用模板只有 1 个(`14b@4096`)——结构性不可达。

## 8. 后续方向(建议,按性价比排序)

1. **【零 GPU,先做】清查 LoRA 标签冲突并以 OOM 清洗**:已证实 20/20 重跑为 OOM,LoRA 占排错 2/3,清洗后重评估。
2. **数据口径决策**:确认是否排除/重分类那个 `mbs=32` 密度点 → 可让第 12 个 selector 达标(12/12)。
3. **架构级评估(需对齐)**:排序若要突破 ~0.72,需换评估口径(全量原始配置)或换模型族(单调树/GAM 吃交互);交互特征在当前生产口径下已实证过拟合(§4.3),不能简单合入。
4. **针对性补实验(仅在诊断指明缺口后)**:泛跑与针对性补候选均已实证对排序无效。
5. **流程动作**:若要冲"可发布",需推进独立 holdout 验收报告与 native-v2 发布锚点——需人工/流程介入。
6. **packing**:若需"自动开启 packing"结论,需扩充 holdout 侧切分单元的模板来源。
