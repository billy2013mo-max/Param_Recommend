## What was completed this session

All eight "critical unfinished work" items from the prior handoff are done, tested, and ruff-clean. Everything lives under `Param_Recommend/offline_experiments/`.

1. **Nested tail calibration (Item 1).** Conformal tails are now computed from inner global-scenario out-of-fold (OOF) residuals inside every outer fold, not from the outer-training rows. Helpers `_inner_scenario_oof`, `_assign_inner_folds`; fits memoized by `frozenset` of excluded scenario ids. The prior blocker `conformal_tails_use_same_outer_training_fold_residuals_not_inner_scenario_oof` is retired; `validate_report` now *enforces* `residual_source == "inner_scenario_kfold_oof"` on every fold tail.
   - **Scheme split (decided via grilling + measurement):** the memory tail uses strict leave-one-scenario-out (`MEMORY_INNER_OOF_FOLDS = None`) because it is safety-critical, carries no free grouping parameter, and was *measured* to yield fewer false-safe OOMs (2 vs 3) than grouped K-fold. The throughput tail uses grouped K-fold (`THROUGHPUT_INNER_OOF_FOLDS = 5`) — not safety-critical and ~4× cheaper. My earlier "K-fold is conservative" reasoning was empirically wrong on the safety metric; do not revert.

2. **Right-censored memory tail (Item 2).** Success residuals are exact Kaplan–Meier events; OOM lower inequalities are right-censored. Statistical P95 (`statistical_residual_p95_km`, may be non-identifiable) is reported separately from the operational safety upper bound. Operational guard = `max(censor_lower, safe_limit+1) - reserved_center`; applied residual = `max(0.0, success_conformal, oom_guard) + cohort_inflation` (guard is inside the `max`, so it can only raise P95 — verified). No OOM peak is ever invented.

3. **Cohort/evidence uncertainty (Item 3).** `_cohort_evidence_inflation`: non-negative leave-one-cohort-out excess over the scenario-OOF spread, identifiable only with ≥2 cohorts. On real data there are 2 memory cohorts and the inflation resolves to 0 (cross-cohort spread ≤ scenario-OOF). All evidence tiers are legacy, so `verified_publication_anchor_present=false` and blocker `verified_calibration_anchor_missing` is emitted — a missing anchor stays a blocker, never a multiplier.

4. **Joint memory-gated admission + ranking (Item 4).** `_joint_candidate_summaries` / `_joint_ranking_metrics`: a candidate is rankable only if predicted P95 ≤ 0.95× capacity; regret oracle is the best *measured* safe candidate whose observed peak also clears the line; a predicted-safe candidate that actually OOMs is a safety failure counted separately, never masked as regret. The old throughput-only `_ranking_metrics` was removed.

5. **Minimum-card/scaling policy (Item 5).** `_scaling_pairs` requires both endpoints memory-admitted; a 1.8× claim needs conservative-lower ≥ 1.8 AND measured ≥ 1.8.

6. **Input/artifact integrity (Item 6).** `_validate_basis_integrity` recomputes the basis digest and checks schema before fitting (mismatches become blockers, not silent acceptance); `write_report` is atomic; the report binds `integrity.implementation_sha256` and `fold_membership_sha256`; `validate_report` rejects NaN/Inf and enforces the fail-closed contract.

7. **Machine-readable evidence gap (Item 7).** New `scripts/h800_evidence_gap.py` (+ `tests/test_h800_evidence_gap.py`) derives gaps strictly from the finished calibration report; `creates_gpu_queue=false`, `proposes_campaign=false`, `requires_separately_approved_design=true`. Current output: 11 mechanism-specific gaps in `artifacts/h800_evidence_gap.json`.

8. **Documentation (Item 8, partial by design).** Updated the two docs NOT bound by the recovery report: `offline_experiments/README.md` (new "H800 理论校准审计" section) and `Param_Recommend/项目文档/01_项目总览与使用指南/DeepSpeed_SFT资源配置推荐器设计方案.md` (implementation-progress note). ## LoRA+ZeRO-3 false-safe — diagnosed (CPU-only)

Root cause is NOT the memory formula and NOT calibration. Ruled out: fitted activation liveness for `(lora, gc=False)` = 1.095 (does not shrink activation); the stage3_live cap fix adds only ~5 GiB of a ~50 GiB gap; `censor_lower` is already ≥ capacity for 81/82 OOM (so a capacity-floor guard is a near no-op). Decisive finding: **6 identical `(mbs, seq, gpu)` cells both succeed and OOM** for LoRA+ZeRO-3 — the OOM is driven outside every calibration key (suspected mixed-dtype all-gather runtime defect per design §10.5, or shared-host interference). A deterministic model cannot both admit (usually fits) and reject (sometimes crashes) the same config. This is a **label conflict / data defect, not a model error**. The gap report detects same-config conflicts (`_same_config_label_conflicts`) and emits `false_safe_is_label_conflict_not_model_error`: triage these OOMs as software/infra failure first; never exclude LoRA+ZeRO-3 from the search on this alone.
